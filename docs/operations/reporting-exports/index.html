Recommendation

Decision requested: approve slices R1 through R4 as one ordered implementation wave. R1 and R2 are the minimum useful release. R3 and R4 make the result discoverable and comparable in the product.

  • Persist one canonical run snapshot. Write a schema-validated .quality/reports/runs/<runId>.json from the execution result before the mutable sidecar can be replaced by a later review.
  • Render, do not re-collect. HTML, Markdown, JSON, and SARIF all read the same snapshot. Derived formats are downloaded or published as CI artifacts; only the canonical JSON is standing truth.
  • Keep both trend meanings. The existing Git-backed score curve remains the commit/release trend. A new run trend reads canonical snapshots and compares only the same repository, kind, scope, and level.
  • Design for the organization that exists. The Markdown output is a bounded, standalone pipeline summary and never assumes that a pull request body or comment exists.

External interop evidence

  • The organization documents its normal maintainer flow as a 0-PR, agent-driven pipeline in managed worktrees. Pull requests remain supported for community work, so an export contract must work with and without them.
  • The OASIS SARIF 2.1.0 standard defines run identity, partial fingerprints, and baseline state. Baseline state is meaningful only after a comprehensive comparison to a prior run.
  • GitHub's supported SARIF subset recommends stable relative paths and partial fingerprints, and uses primaryLocationLineHash for result matching. The current renderer emits a Quality Studio fingerprint key but not that GitHub-specific key.

§3Why a review dies in the app

There is no single missing download button. The missing piece is a durable result boundary.

The unsafe reconstruction trap

Do not filter current sidecars by reviewedAt, provider runId, or usage paths. A sweep can reuse fresh observations, files can finish concurrently, a later sweep can overwrite a sidecar, and the sweep id is not stored in that sidecar. Such a report can look precise while assigning findings to the wrong run.

§5Recommended run report contract

Create quality-run-report.v1 beside, not inside, the existing quality-report.v1. The existing model answers “What is the repository's current quality?” The new model answers “What happened in this review sweep?”

SectionRequired contentSource in current code
runRun id, repository id and display name, kind, scope unit id/level/path, state, completeness, revision, created/started/finished times, model, CLI type, and force flag. ReviewRunManifest plus ReviewRunStatus
subjectOrdered target paths and subject hashes plus a deterministic manifest hash. Never include the absolute repository root.ReviewRunPlanTarget
executionReviewed, reused-fresh, failed, skipped, and cancelled counts; aggregate outcome; sanitized errors; usage, cost, cap, estimate, and deviation. ReviewRunResponse and usage ledger
observationsOne ordered item per file plus an optional aggregate item: outcome, produced-by-this-run flag, sidecar path and SHA-256, reviewed hash, provider operation run id, grade, summary, findings, deterministic evidence, and lifecycle state as observed at capture time. Snapshot the sidecar bytes returned by ReviewRunner; extend the fresh-skip return path to identify the reused sidecar.
deltaPrior comparable run id and stable-fingerprint sets for new, persisting, resolved, and state-changed findings. If there is no comparable baseline, set status to unavailable, not zero.Finding fingerprints plus prior canonical run snapshot
summaryRun score only when its completed scope supports the existing score calculation, finding counts, highest severity, and explicit partial reason.Reuse QualityReportBuilder grade and finding semantics

Storage

.quality/reports/runs/<runId>.json is repository-owned and may be committed like review sidecars and usage ledgers. Quality Studio writes atomically but never commits it. HTML, Markdown, and SARIF stay derived unless a pipeline publishes them.

Revision and resume

A capped run can resume under the same id. Increment revision and replace the canonical snapshot after every terminal transition. Trends select the highest revision per run id, so cap/resume does not create duplicate points.

Fresh reuse

skipped-fresh includes a copy of the reused observation with producedByRun: false. It contributes to scope context but is not counted as a newly produced review or finding.

Partial truth

Failed, cancelled, and capped reports remain exportable with completeness: partial. Missing units stay visible. Partial reports never publish a comparable score point.

Security and portability defaults

  • Omit absolute repository paths, credentials, environment variables, and raw prompts.
  • Retain structured finding evidence already allowed by review-meta; existing secret sensors must continue to redact secret values.
  • HTML must escape every dynamic value, contain no script, make no network request, and include a restrictive Content Security Policy suitable for a saved local file.
  • Paths remain repository-relative with / separators in every format.

Run point payload

  • Run id, revision, finished time, state, completeness, model, and CLI type.
  • Score and grade when comparable; otherwise null plus a precise reason.
  • Active findings by severity and lifecycle state.
  • New, persisting, resolved, and state-changed finding counts from stable fingerprints.
  • Reviewed, reused-fresh, failed, and skipped unit counts.
  • Input/output tokens, duration, cost, estimate deviation, and cap outcome.

Presentation rule

Connect only comparable complete runs. Render failed, cancelled, and capped runs as quiet event markers with their partial reason. This prevents a partial 20-file run from appearing as a quality improvement over a complete 149-file run. Default to the last 30 points, matching the current backend recent-run limit, with pagination for older snapshots.

Finding movement

Use the existing stable fingerprint as the join key. “New” means absent from the immediately prior complete run in the same series; “persisting” means present in both; “resolved” means present only in the prior run. A lifecycle transition such as open to waived is state-changed, not resolved. A run with no baseline reports delta status unavailable.

§8The skip-the-pull-request pattern

The internal maintainer pipeline normally has no pull request, so neither a PR comment nor a PR check summary can be the primary result surface. The portable pattern is: write a Markdown summary, print it to the run log, publish all three human/CI artifacts, and return the gate status after artifacts exist.

Target shell sequence after R2

set +e
quality report . --run "$QUALITY_RUN_ID" --format markdown --output quality-run.md --fail-on high
gate=$?
quality report . --run "$QUALITY_RUN_ID" --format sarif --output quality-run.sarif
quality report . --run "$QUALITY_RUN_ID" --format html --output quality-run.html
sed -n '1,160p' quality-run.md
# CI publishes quality-run.md, quality-run.sarif, and quality-run.html here.
exit "$gate"

  • Generic pipeline: Markdown is visible in logs and all formats are ordinary artifacts. No forge API is required.
  • GitHub push pipeline: append Markdown to $GITHUB_STEP_SUMMARY and upload SARIF on the push event. GitHub documents SARIF upload on push and scheduled workflows; a pull request event is not required.
  • Managed worktree result: copy the HTML, Markdown, and SARIF files into the task result directory. The task result view becomes the sharing surface.
  • Community pull request: the same Markdown may also be pasted into a PR summary, but no behavior depends on that optional surface.

§10Approval packet

Approve as written

  1. Approve R1 through R4 in order, with R1 and R2 as the first release boundary.
  2. Approve canonical JSON as durable truth; HTML, Markdown, and SARIF remain replaceable projections.
  3. Approve repository + kind + scope unit id + level as the run trend series key.
  4. Approve 20 active findings as the Markdown default summary limit, with an explicit omitted count.
  5. Approve baseline state only for comprehensive comparable runs; otherwise export delta as unavailable.
  6. Approve 0-PR-first delivery: log summary plus artifacts on push/managed-worktree pipelines, with PR reuse optional.

Deliberate exclusions

This wave does not redesign the current repository scorecard, change finding lifecycle semantics, auto-commit generated reports, add cloud hosting, send data to a forge, infer model effectiveness, or introduce a report database. Those choices are not required to stop reviews from dying in the app.
