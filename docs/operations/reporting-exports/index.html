Reporting and exports that outlive the review screen

Decision in one page

Recommendation: keep the existing repository snapshot report, but add a separate immutable review-run-report.v1 artifact captured at the review-operation boundary. Render JSON, calm standalone HTML, concise Markdown, and SARIF from that one snapshot. Add numbered revisions because a capped run can resume under the same run ID.

  • Run truth and repository truth remain distinct. A run report answers what this execution reviewed, produced, skipped, spent, and failed. The existing quality report answers what the repository says now.
  • Capture before sidecars can change again. A later run can overwrite the same review sidecar. Reconstructing an older run from current sidecars would be false history.
  • One snapshot, four adapters. JSON is canonical. HTML is for humans, Markdown is for push pipelines, and SARIF is for CI and code-scanning consumers. Adapters must not invent data absent from JSON.
  • Two trend lines, never blended. Run history is keyed by scope and kind. Repository quality history stays Git-backed and commit-addressed.
  • No pull request dependency. The primary pipeline surface is the job summary and archived artifacts on a push to main. A PR comment integration is explicitly out of scope.

§1Current repository state

The following findings come from the checked-out code, committed review data, schemas, tests, and one current report invocation. They are not inferred from a desired architecture.

§1.1 A capable current-state exporter already exists

QualityReportRenderer supports Markdown, HTML, JSON, and SARIF, and the CLI writes output before evaluating gates. The API exposes the same report builder at GET /api/report and GET /api/repos/{repoId}/report. The useful core should be reused, not replaced.

§1.2 The current report is not a review-run report

The current report builder enumerates the review sidecars present now, projects the current finding lifecycle state, scans current staleness, and reconstructs Git history. Its model has repositories, scorecards, trends, and findings, but no review run ID, selected scope, per-run outcome, skipped files, errors, token cap, estimate, or estimate deviation. Evidence: QualityReport.cs:30-105, 125-213.

UI review orchestration persists a different record under .quality/runs/<runId>/:

The exact-run evidence gap

ReviewRunner atomically replaces the standing sidecar and returns only its path, reviewed hash, agent run ID, inputs, and usage (ReviewRunner.cs:31-33, 147-190). The job service records that the file finished but does not snapshot the sidecar (ReviewJobs.cs:468-497, 999-1015). A later review of the same unit can replace the sidecar. Therefore an old run cannot be reported exactly from current repository state.

§1.3 The browser is a terminal status list, not an exit surface

The review panel shows the eight newest rows, progress, spend, pause, cancel, resume, deviation, and the first error. There is no open, copy, or download action (frontend/src/app/review-panel/review-panel.html:5-18). The frontend client starts, polls, pauses, resumes, and cancels runs, but never calls /report (frontend/src/app/quality-api.ts:491-599). The export API exists outside the user flow.

§1.4 The human outputs are too thin

The Markdown renderer lists a finding's severity, lifecycle state, source, title, and first location, but omits its description, recommendation, other locations, review rationale, and run provenance (QualityReport.cs:555-627). HTML is that Markdown escaped into one <pre>, not a semantic document (QualityReport.cs:628-635). JSON and SARIF carry more detail than the human report.

§2The required reporting boundary

The product needs two explicit report subjects. Treating them as one model creates either false run history or an impoverished repository report.

SubjectQuestion answeredSource of truthIdentity
Review runWhat did this execution attempt, observe, spend, skip, and fail?Immutable snapshots captured as each operation completes, plus the durable run manifest and statusrepositoryId + reviewRunId + revision
Repository snapshotWhat is the standing quality truth now, and how did committed truth change?Current sidecars, finding state, scans, and Git historyrepositoryId + generatedAt + commit

Recommended canonical artifact

Add review-run-report.v1.json. Capture the complete projected observation at the same operation boundary that writes the sidecar, not by rereading mutable sidecars at export time. Store it through ReviewRunStore under .quality/runs/<runId>/artifacts/r<revision>/report.json. The directory remains operational data, not committed quality truth.

§2.1 Revisions are required, not optional polish

The current state machine classifies capped as terminal, but Resume can return the same run to queued with a higher cap (ReviewRunStore.cs:159 and ReviewJobs.cs:914-952). Overwriting a shared partial report after resume would break auditability. Each transition to capped, done, failed, or cancelled must freeze the next numbered revision. A stable latest endpoint may resolve to the newest revision; a revision URL never changes.

§2.2 Capture semantics

  • Done operation: capture the exact metadata JSON returned by the write boundary, including grade, rationale, summary, findings, projected lifecycle state, analyzer evidence, reviewer, usage, input hash, and subject hash.
  • Skipped fresh: capture the verified fresh observation and mark operationState: skipped-fresh. A null review result is insufficient for the report.
  • Failed, skipped, or cancelled: record the operation state, bounded error detail, target subject hash, and timestamps. Never invent a grade or findings.
  • Aggregate review: capture it as a separate unit with its aggregate controls and exclusions.
  • Concurrent writes: the snapshot bytes must come from the same in-memory document that is atomically written, or be read under the same write lock and checked against the returned agent run ID. A later sidecar is not acceptable.
  • Legacy runs: return a typed report-unavailable result when no observations were captured. Do not backfill from current sidecars.

§3Proposed formats and examples

All four representations render the same canonical fields. Filenames are deterministic and contain no repository root: quality-run-<safe-repository-id>-<run-id>-r<revision>.<ext>.

§3.1 Canonical JSON

The model below is intentionally run-scoped. Repository-wide scorecard, comparison, and Git trend remain in quality-report.v1.

{
  "$schema": "https://agent-orchestrator.dev/quality/schemas/review-run-report.v1.json",
  "schemaVersion": 1,
  "run": {
    "id": "review-7f31...",
    "revision": 2,
    "repository": { "id": "payments", "name": "Payments" },
    "subject": { "path": "src/Payments", "level": "module", "kind": "security" },
    "execution": { "state": "done", "createdAt": "...", "finishedAt": "..." },
    "engine": { "cliType": "codex", "model": "...", "force": false },
    "counts": { "total": 18, "reviewed": 15, "fresh": 2, "failed": 1, "skipped": 0 },
    "usage": { "inputTokens": 48210, "outputTokens": 6371, "durationMs": 192004 },
    "estimate": { "inputTokens": 45110, "outputTokens": 7100 },
    "deviation": { "inputTokensPercent": 6.87, "outputTokensPercent": -10.27 }
  },
  "summary": { "score": 82, "grade": "B", "activeFindings": 4 },
  "units": [
    {
      "path": "src/Payments/ChargeService.cs",
      "operationState": "done",
      "subjectHash": "sha256:...",
      "review": { "grade": { "score": 78, "band": "C" }, "findings": [ ... ] }
    }
  ],
  "integrity": { "contentHash": "sha256:..." }
}

Required schema details: define every nested object, enum, timestamp, fingerprint, and nullable field. The current quality-report.v1.schema.json leaves trend items and several nested arrays effectively untyped; the new contract should not repeat that weakness.

§3.2 Calm standalone HTML

The HTML report should read as a small engineering document, not a screen dump. Use the same calm document grammar as this dossier: a restrained header, outcome box, small facts table, finding sections, and provenance at the end. It must contain the full finding description and recommendation that current human exports omit.

OrderSectionContent
01Run outcomeDone, partial, failed, or cancelled in text and icon; scope, kind, revision, timestamps
02Executive summaryGrade only when evidence exists; reviewed/fresh/failed/skipped counts; active findings
03FindingsSeverity, lifecycle state at completion, rule, every location, description, recommendation, source
04Units and failuresPer-unit grade/state, skipped-fresh units, failures without fabricated quality claims
05Cost and methodEstimate versus actual, CLI/model, inputs hash, subject hash, deterministic sensor provenance
06IntegrityRun ID, revision, schema, generated time, repository commit if available, canonical JSON hash

Partial reports must look partial

A capped or failed revision uses an explicit partial label and says which units lack observations. It does not calculate a scope grade from only the successful subset unless that value is labeled reviewed subset.

§3.3 Markdown summary

Markdown is a compact pipeline surface, not a lossy duplicate of HTML. Default to the outcome and active findings, then include collapsible or lower-priority operational details only where the renderer supports plain Markdown safely.

# Quality review: security · src/Payments

**Done · revision 2 · 15 reviewed · 2 fresh · 1 failed**

§3.4 SARIF 2.1.0

Reuse the existing severity, fingerprint, relative URI, and suppression behavior. Change the subject from one SARIF run per repository snapshot to one SARIF run per review-run revision.

{
  "$schema": "https://raw.githubusercontent.com/oasis-tcs/sarif-spec/main/Schemata/sarif-schema-2.1.0.json",
  "version": "2.1.0",
  "runs": [{
    "tool": { "driver": { "name": "Quality Studio", "rules": [ ... ] } },
    "automationDetails": { "id": "quality-studio/payments/review-7f31/r2/" },
    "invocations": [{ "executionSuccessful": true }],
    "results": [{
      "ruleId": "QS-AUTH-004",
      "level": "error",
      "message": { "text": "Unsafe authorization fallback: ..." },
      "partialFingerprints": { "qualityStudioFingerprint/v1": "sha256:..." },
      "locations": [{ "physicalLocation": {
        "artifactLocation": { "uri": "src/Payments/Auth.cs" },
        "region": { "startLine": 88 }
      }}],
      "properties": { "reviewRunId": "review-7f31...", "revision": 2, "state": "open" }
    }],
    "properties": { "kind": "security", "scope": "src/Payments", "state": "done" }
  }]
}
  • Mapping: critical/high to error, medium to warning, low/info to note.
  • Lifecycle: open and accepted remain active results; waived and false-positive receive accepted external suppressions; resolved observations are omitted from active results but remain counted in run properties if captured.
  • Failures: execution failures belong in invocations.toolExecutionNotifications, not as fake code findings.
  • Validation: retain the local profile test and also validate against the official SARIF 2.1.0 schema. The current test validates only schemas/sarif-2.1.0-output.schema.json, a deliberately smaller profile.

§4Zero-PR pipeline delivery

The operator mandate says the organization runs with zero pull requests. The relevant industry pattern is the direct-to-trunk variant of trunk-based development, also described as committing straight to the trunk. Quality evidence therefore has to attach to the pushed commit and CI run, not wait for a PR comment.

§4.1 Current CI evidence

.github/workflows/build.yml triggers on both push and pull request, but runs only restore, build, test, and security scan. It never calls quality report and never uploads an artifact. Its only permission is contents: read (build.yml:3-10, 24-34).

Recommended delivery pattern

  1. On every push to main, build a report bundle once from the checked-out commit.
  2. Append summary.md to the CI job summary. This is the primary human surface.
  3. Archive report.html, report.json, report.sarif, and summary.md even when the quality gate exits 1.
  4. Optionally upload SARIF to the code-scanning provider in deployments that grant the required permission. The portable SARIF artifact remains the base contract.

Proposed CLI after slice S4:

set +e
dotnet run --project src/quality-cli -- report . \
  --bundle artifacts/quality \
  --fail-under 80 \
  --fail-on high
quality_exit=$?
set -e

cat artifacts/quality/summary.md >> "$GITHUB_STEP_SUMMARY"
exit "$quality_exit"

--bundle does not exist today. It should build the model once, write all four formats atomically, then evaluate gates. Artifact upload steps must use the CI provider's always condition so exit code 1 does not discard the report. Existing single-format commands remain compatible.

SARIF upload is an adapter, not the source of truth

GitHub code scanning requires an upload step and typically security-events: write; the current workflow does not grant it. Do not couple report generation to that permission or to one vendor. Generate and archive valid SARIF first, then upload where enabled.

§5Trends across runs

The existing Git curve is valuable but it is not a run curve. It suppresses commits where the mean score did not change, cannot show capped or failed runs, and has no run usage or estimate. Keep it and add a separate run series.

SeriesX-axisComparatorMeasuresSource
Run historyfinishedAt and run revisionExact repositoryId + path + level + kindReviewed-subset score, active/new/resolved findings, done/fresh/failed/skipped, tokens, cost, duration, estimate deviationImmutable run report JSON
Repository qualityGit author time and commitRepository and kindStanding per-kind score, review coverage, active finding counts, fresh/stale/policy-drift/missingCommitted sidecars and finding state

§5.1 Run comparison rules

  • Compare only the same path, level, and kind. A file security run and a project code run do not form a curve.
  • Include every terminal revision in the operational history, including capped, failed, and cancelled.
  • Exclude partial revisions from the main quality-score line by default. Show their reviewed-subset score only with a partial marker and never connect it as if scope were complete.
  • Use stable finding fingerprints for new, persisting, and resolved deltas. Titles and line numbers are not identity.
  • Display model/CLI changes and force runs as annotations because they affect comparability.
  • Do not invent points for legacy runs that lack captured observations.

§5.2 First useful UI and report

Add a scope-filtered trend block above the run list: latest complete grade, delta from the prior comparable complete run, active finding delta, last five run outcomes, and usage per run. The full HTML export adds a small table of comparable revisions. The current Git trend remains labeled Committed repository trend.

§7Implementation slices

Each slice has an independently reviewable outcome. S1 is the correctness floor. S2 through S5 must not reconstruct exact-run evidence from mutable sidecars if S1 is absent.

S1 · Capture the immutable run artifact contract

approve first

  • Add a fully specified schemas/review-run-report.v1.schema.json and typed core model.
  • Extend the review execution result so the exact written observation is available to the job service for both completed and skipped-fresh operations.
  • Persist per-operation snapshots and freeze numbered report revisions through ReviewRunStore.
  • Add reportRevision to durable status. Increment only when a terminal snapshot is successfully frozen.
  • Capture capped partial revisions and allow a later resumed revision without mutating the earlier artifact.
Acceptance: restart recovery preserves observations; concurrent runs cannot misattribute a sidecar; every terminal state gets a schema-valid revision; capped then resumed produces two immutable revisions; legacy runs return typed unavailable; absolute roots and source content are absent.

Primary seams: ReviewRunner.cs, ReviewRunStore.cs, ReviewJobs.cs, and ReviewRunStoreTests.cs.

S2 · Render and serve the four run formats

depends on S1

  • Add pure renderers from the run JSON model: semantic calm HTML, detailed Markdown, JSON, and SARIF.
  • Add repository-scoped routes for revision inventory, an immutable revision, and latest: /api/repos/{repoId}/review/runs/{id}/reports/{revision}?format=....
  • Return correct media type and a sanitized Content-Disposition filename. Active runs return 409 with a stable problem type until a revision exists.
  • Keep current /report endpoints and current-state model unchanged except for shared safe primitives.
Acceptance: all adapters are deterministic from one JSON fixture; HTML encodes every untrusted field and works without script/network access; Markdown includes full descriptions and recommendations; SARIF validates against local and official schemas; waived/false-positive mappings match current behavior.

S3 · Put exports in the run UI

depends on S2

  • Add Open report plus Download Markdown, SARIF, and JSON to terminal run rows.
  • For a resumed capped run, show available revision count and label old revisions partial.
  • Open HTML in a new first-party route or tab; downloads use the backend response and never rebuild data in the browser.
  • Keep pause, cancel, and resume actions unchanged. Use the existing frontend token scale and standard button/menu primitives.
Acceptance: done, failed, cancelled, capped, resumed, unavailable-legacy, and permission-denied states have component tests; one browser test downloads each media type and verifies filename and content.

S4 · Make push CI a first-class report consumer

can follow S2

  • Add quality report --bundle <directory>; build current repository state once and render all four files.
  • Update the repository workflow so push-to-main writes Markdown to the job summary and archives the full bundle under an always condition.
  • Keep gate exit codes 0, 1, and 2. Artifact generation must complete before a gate failure exits.
  • Add optional SARIF upload as a separately permissioned step. Do not require a PR or a PR comment.
Acceptance: a fixture push with a failing quality threshold still has four downloadable artifacts and a job summary, while the job ends failed; generation errors end with code 2 and do not publish a deceptively complete bundle.

S5 · Add honest run trends

depends on S1; UI follows S3

  • Build a read model over captured revisions, keyed by repository, path, level, and kind.
  • Return complete and partial points, finding fingerprint deltas, outcome counts, usage, cost, duration, and model annotations.
  • Add the compact scope trend to the review panel and a comparable-run table to HTML/Markdown.
  • Rename the existing trend label to Committed repository trend and enrich future points with coverage and finding counts in a later schema version only if the contract is versioned.
Acceptance: same-scope runs compare; mixed scopes never do; partial points are not connected to the complete score curve; repeated equal scores remain visible as runs; Git history remains byte-for-byte independent of ignored run artifacts.

§8Guardrails and non-goals

  • No source code in exports. Locations, hashes, evidence summaries, and recommendations are sufficient. This reduces accidental disclosure when HTML is shared.
  • No absolute repository roots. Existing current reports already omit them; preserve that boundary.
  • No report from mutable current state for an old run. Typed unavailable is preferable to false precision.
  • No external fonts, scripts, or CDNs in HTML. The report must remain readable as a downloaded file.
  • No PR comments as the primary Markdown destination. The push job summary is the mandated path.
  • No report database in this wave. Local run artifacts plus Git-backed standing truth are enough to prove the model.
  • No automatic thresholds chosen by the product. --fail-under and --fail-on remain explicit operator policy.
  • No silent retention policy. Run artifacts remain under the existing ignored run directory. A future retention slice must expose age/size settings and must not delete revisions while they are being served.
  • Encode every output field. Finding titles, descriptions, recommendations, paths, model names, and error text are data. HTML, Markdown, headers, and SARIF each need format-specific escaping tests.

§9Approval block

Proposed operator decision

Approve Recommendation B and slices S1 through S5 in order. JSON is canonical; HTML, Markdown, and SARIF are adapters. Review-run revisions are captured immutably under the existing durable run store. Repository-wide reports and their Git-backed trend remain separate. Push-to-main job summaries are primary; PR integration is not required.
