Quality Studio · QS-62 · Decision dossier

Persist the run, not just the latest review

Quality Studio can resume a review after an API restart in the same checkout. It cannot reconstruct the run after its ignored working folder or checkout disappears. Add a tracked, immutable run archive beside the existing recovery journal, and make two archived runs directly comparable.

Status decision pending Phase decision ready Evidence cut 11 August 2026 Source QS-62

Recommendation for approval

Keep .quality/runs/<runId>/ as the ignored, mutable crash-recovery journal. On every stopped attempt, materialize a tracked archive at .quality/run-history/YYYY-MM/<runId>/. Store one immutable run manifest, append-only operation and finding observations, and one create-only record per attempt. Extend the existing usage ledger with operationId; do not duplicate detailed token entries or introduce a database.

Approval effect: one backend-owned storage contract, one deterministic diff contract, five implementation slices, and no Quality Studio CLI Git ownership.

01Decision and boundary

The product currently has three different meanings of persistence. They should remain separate and be connected by stable identifiers.

LayerPurposeCurrent ownerDecision
Working recoveryResume queued, running, paused, or capped work after process failure..quality/runs/Keep mutable and ignored. It is a cache, not history.
Standing quality truthLatest grade, findings, reviewer, hashes, and threads for one unit and review kind.Review-meta sidecars plus .quality/findings/state.jsonKeep as the current projection. Do not turn it into a run log.
Historical run truthWhy a sweep ran, what each operation produced, its spend, its typed verdict, and how it differs from another run.Missing as a tracked product contract.Add .quality/run-history/ and history/diff APIs.

Explicit ownership boundary

The API/backend writes and reads archive files. It never commits, pushes, merges, or manages worktrees. In a managed workspace, the platform-owned post-run path makes repository artifacts durable in Git. In an ordinary checkout, they follow the repository's normal commit workflow, matching the existing token-ledger policy.

What cannot be reconstructed today

  • The run-level quality result. ReviewRunStatus has an operational state but no typed verdict or per-operation grade/finding snapshot.
  • Per-operation identity. The status accumulates token counts. The detailed ledger has provider runId and sweep reviewRunId, but no operation ID or attempt number.
  • Prior observations without a matching Git commit. A successful review atomically replaces its unit sidecar. Finding lifecycle mutations replace the current record for a fingerprint. Git can preserve either only after a commit boundary.
  • A deterministic run-to-run comparison. Existing change reviews already compare grade snapshots and stable finding fingerprints across commits, but review-run APIs expose no equivalent.
  • A portable history index. ReviewJobService.List reads the in-memory dictionary, not a tracked archive.

Data reality in this checkout

The evidence cut contains 20 tracked .quality/changes/*.json records and 12 tracked files matching review-meta or *.meta.json naming, but no tracked monthly usage JSONL and no live run files. The contracts exist; past review runs must not be fabricated from the absence of run data.

05Recommended file contract

.quality/
  runs/                                  # existing mutable recovery journal, ignored
    <runId>/
      manifest.json
      progress.jsonl
      status.json

  run-history/                           # tracked product history
    2026-08/
      <runId>/
        run.json                         # immutable identity, plan and configuration
        operations.jsonl                 # append-only completed/failed operation records
        findings.jsonl                   # append-only finding observations
        attempts/
          0001.json                      # create-only capped/failed/cancelled/done snapshot
          0002.json                      # created only if the capped run resumes

  usage/
    2026-08.jsonl                        # existing detailed token ledger, schema v1/v2/v3
  findings/state.json                    # current lifecycle projection

Contract invariants

  • Every archive document has $schema and schemaVersion. The current run-store records have neither; migration must not silently call them v1.
  • run.json is create-only. It includes enqueue-time target hashes, prompt identifiers/hashes when known, effective review-input hashes, and the current Git commit plus dirty-state flag when available. Per-target hashes remain authoritative for dirty worktrees.
  • operationId is generated by the backend before agent execution and is stable across recovery of that operation. It is carried into operation, finding and usage records.
  • An operation record is appended only after the sidecar result is atomically written, or after a terminal operation error is known. A running marker remains only in the ignored journal.
  • Each stopped attempt gets the next create-only number. capped is a stopped attempt, not an immutable end of the logical run. A later resume adds another attempt and never rewrites the earlier one.
  • Detailed token fields live in the usage ledger. Attempt records contain reconciled totals and references to ledger month(s), review run ID and operation IDs.
  • History readers use the highest valid attempt number as the latest run state. A malformed newest artifact is surfaced as history-corrupt; it is not silently omitted.
  • The application never auto-deletes tracked history. Cleanup of ignored recovery folders is allowed only after the corresponding archive attempt has been flushed successfully.

Minimum schema set

SchemaRequired core fields
run-record.v1runId, repositoryId, createdAt, subject identity, kind, targets and hashes, configuration, cap/estimate, source revision.
run-operation.v1operationId, ordinal, attempt, unit/path/level, state, start/finish, provider run ID, reviewed/input hashes, result sidecar, typed verdict and grade.
run-finding.v1operationId, fingerprint, finding ID, rule ID, severity, title, locations, state at observation.
run-attempt.v1Attempt number, outcome, completeness, timestamps, per-attempt and cumulative counters/spend, error codes, cap, estimate deviation, ledger references, quality summary.
usage-ledger.v3All v2 fields plus operationId and attempt. Existing v1/v2 lines remain valid and are never rewritten.

06Outcome, verdicts, findings, and time

Do not collapse execution outcome into a quality verdict

A completed run is not automatically a passing run. Store two independent facts:

  • Operational outcome: done, failed, cancelled, or capped, with completeness and file/aggregate counters. These values already exist in the run service.
  • Typed quality verdict: preserve the producer's semantics. Code and performance operations store grade score/band. Security stores pass/warn/block/unavailable and its combination rule. Future flow or change verdicts use their own named type rather than being coerced into a universal pass/fail.

The attempt summary may contain deterministic rollups such as lowest grade, worst security verdict, active finding counts and highest active severity. It must not invent a repository-wide pass threshold. Existing report gates remain explicit through --fail-under and --fail-on.

Finding roles remain distinct

ArtifactMeaningChange behavior
Review sidecar findings[]Latest observation for one unit and kind.Atomically replaced by a later successful review.
findings/state.jsonCurrent lifecycle decision for a stable fingerprint.Replaced atomically; revision and optimistic timestamp protect mutation.
Run archive findings.jsonlWhat one operation observed, including lifecycle state at that time.Append-only. Never becomes the current lifecycle owner.

Timestamp vocabulary

Persist UTC ISO 8601 values from the backend clock. Do not infer chronology from file modification time or Git author time.

  • createdAt: accepted/enqueued.
  • startedAt and finishedAt: each attempt and operation.
  • reviewedAt: result observation written to its sidecar.
  • usageRecordedAt: existing ledger timestamp, explicitly retained as the operation usage event time.
  • archivedAt: archive attempt flushed. This is durability time, not review time.

07Run history and diff

History API

  • GET /api/repos/{repoId}/review/history?cursor=&limit=&kind=&path=&outcome= reads tracked archives, newest attempt first, with cursor pagination. It is not constrained by RecentRunLimit.
  • GET /api/repos/{repoId}/review/history/{runId}?attempt= returns manifest, selected attempt, operations and findings.
  • GET /api/repos/{repoId}/review/history/{runId}/diff?against={otherRunId} returns a deterministic comparison. An optional attempt selects a capped snapshot; the default is the latest valid attempt.
  • Existing /review/runs stays the active/recent operational endpoint during migration, then composes active rows with archived summaries without changing pause/resume behavior.

Comparison rules

Default comparison requires the same repository, review kind and root unit identity. Target-set changes inside that scope are valid and shown. Different root units require an explicit override and are labelled scope-changed.

DimensionDeterministic resultExisting basis to reuse
Comparabilityexact, scope-changed, policy-changed, model-changed, or incomplete. Multiple labels may apply.Subject and review-input hashes already separate code drift from policy drift in review metadata.
Scope and inputsAdded/removed/persisting targets; changed subject hashes, prompt hashes and effective input hashes.ReviewRunManifest.Targets and review-meta subjectInputs/reviewInputs.
ExecutionOutcome, completeness, failed/skipped operations, duration, cap, spend and estimate-deviation delta.ReviewRunStatus, ReviewEstimateDeviation and the usage ledger.

Finding fingerprints include path, normalized primary snippet and rule ID. If both runs name Git commits, the diff service should reuse the existing rename-map technique for pure moves. Without a usable revision pair, it must show the direct new/resolved result and label rename correlation unavailable.

UI slice

Add a History entry beside the live runs panel. The history view supports filters, run detail, and selection of exactly two comparable runs. The diff first shows comparability warnings, then scope, quality, findings and economy. Live polling remains limited to queued/running rows; archived history is fetched on demand.

08Migration and legacy truth

  1. Dual-read first. Add versioned archive schemas and readers. No current file is renamed or reinterpreted.
  2. Dual-write stopped attempts. Continue writing the current recovery journal. At done/failed/cancelled/capped, the backend creates or extends the tracked archive and reconciles its attempt total against the ledger.
  3. Backfill only complete local evidence. For every still-present .quality/runs/<id>, create an archive with provenance migrated-from-run-store-v0. Preserve unknowns; do not infer a verdict from done.
  4. Keep ledger history honest. Read v1, v2 and v3. V2 groups already identify a sweep through reviewRunId; they can enrich a migrated archive. V1 remains a provider-run singleton. No historical line is rewritten.
  5. Expose usage-only legacy groups. When a ledger group has no run store, show it as legacy-usage-only with spend and known path/kind/model. Do not synthesize plan, outcome, findings, verdict or timestamps that are not present.
  6. Start cleanup after proof. After two releases of dual-read and a test that rebuilds history from a clean clone, ignored terminal journals may be deleted after successful archive flush. Non-terminal journals remain recovery state.

Review sidecar Git history and the 20 existing change-review records stay valid. They may be linked to a run when identifiers prove the relationship, but they are not mass-converted into fictional run records.

Approve these defaults

  • Tracked archive root: .quality/run-history/YYYY-MM/<runId>/.
  • Existing .quality/runs/ remains the ignored recovery cache.
  • One logical run may have multiple immutable attempt records.
  • Usage ledger advances additively to v3; old rows are never rewritten.
  • Verdicts remain typed by review producer; operational done never means quality pass.
  • No automatic deletion of tracked history and no Quality Studio Git mutation.
  • Implement RP-1 through RP-5 in order.

Deliberately deferred

Cross-repository analytics, raw transcript retention, remote object storage, a database index, retention compaction and universal pass/fail policy are not required for run durability or two-run diffing. Add them only after archive size and query measurements show a concrete need.
