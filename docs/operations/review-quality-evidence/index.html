Decision dossier · QS-61 · Source snapshot 3e0b655

Make every review finding inspectable, reproducible, and learnable

Quality Studio already stores exact ranges, stable identities, lifecycle decisions, analyzer provenance, token usage, and restart-safe run progress. The missing layer is a coherent finding evidence contract and a presentation that exposes it. This dossier defines that target and the slices to reach it without discarding the working foundations.

01Decision and options

The product needs one evidence plane with two projections: an evidence-first finding detail for a reviewer, and an immutable run/outcome stream for history and model-quality analysis. A UI-only patch would make the current gap less visible without producing trustworthy data.

OptionWhat shipsAssessment
A. Highlight onlyRender current line/column ranges as selected spans.Useful fast relief, but evidence stays free text, runs stay non-portable, and TE-38 remains empty. Include as S1, not as the endpoint.
B. Sidecar v3 onlyTyped evidence and provenance in review metadata.Improves the contract, but leaves review flow, suppression, run history, and outcomes fragmented.
C. Evidence plane recommendedExact-span UI, structured finding observation, independent assessment/resolution, scoped suppression policy, terminal history, and TE export.Closes all four operator concerns while reusing current code and repository-owned storage.
D. External review databaseMove findings and runs into a new service.Not justified. It adds deployment and authority boundaries before the existing local contracts are exhausted.

Recommendation

Choose C, delivered incrementally. S1 is independently releasable. S2 through S4 establish the durable contract. S5 connects the resulting operational evidence to the already delivered TE-38 receiver.

Compatibility rule

Readers continue to accept review-meta v1/v2. A v2 description maps to problem, recommendation maps to remediation, location becomes an anchor, and the optional evidence string becomes a visible legacy-claim item. It must not be upgraded to observed or verified evidence.

04Evidence and reproducibility

A finding is actionable when a reviewer can locate the claim, distinguish the strength of its evidence, replay the check when appropriate, and see who or what produced it.

Evidence classRequired fieldsTrust rule
source-spanAnchor, excerpt/content hashes, runner-captured summaryRequired for every file finding. The runner captures it after validating the model range; the model never supplies the trusted hashes.
deterministic-resultSensor, producer/version, rule, result hash, artifact referenceMachine fact with producer provenance. Keep separate from the agent grade, matching the existing deterministic-evidence contract.
test-resultTest id, command, exit/result, timestamp, environment and artifactVerified only when emitted by an executor. Quoted model prose is not a test result.
runtime-observationTrace/log/HTTP reference, bounded excerpt hash, time and environmentObserved behavior. Secrets and unrestricted logs stay out of the sidecar; use confined artifact references and redacted excerpts.
external-referenceStable standard/advisory id, version and applicability noteSupports a rule or risk frame, but never proves that the local defect exists without a source, analyzer, test, or runtime fact.

Reproduction status vocabulary

StatusMeaningUI
verifiedAt least one retained executor/sensor attempt reproduced the observed result on a named revision/environment.Show command/result and the newest attempt first.
specifiedConcrete steps and expected/observed behavior exist, but no retained execution proves them.Normal default for agent review because current prompts forbid tools.
not-applicableA replay is not meaningful, for example a local clarity issue. A reason is required.Do not show this as verified.
blockedAttempt was prevented by missing service, credentials, platform, data, or another named dependency.Show the blocker and permit a verification follow-up task.

Interaction contract

  • Finding card: severity, title, path:line:column, assessment/resolution, strongest evidence class, reproduction status, and source kind. Description remains one line.
  • Editor: selected exact span uses a token-derived background and underline; other findings use restrained underlines and the existing severity marker. Overlap opens a keyboard-accessible chooser.
  • Detail: problem and impact first, then captured code, typed evidence, reproduction, origin, recommendation, assessment, resolution, suppression, discussion, and task handover.
  • Stale finding: retain the captured excerpt with a “captured evidence” label; only highlight current source when the anchor content hash matches or anchor healing succeeds.
  • Accessibility: status always has text or an icon as well as color; selecting a finding moves programmatic focus to its detail and exposes the range in the accessible name.
  • Design system: use the existing --studio-*, --space-*, radius, syntax token, pane, status, and severity primitives. Add semantic finding-span tokens centrally, not component-local colors or badge shapes.

06Assessment and ignore list

Call the UI surface “Ignore list” for operator recognition, but store explicit suppression rules. Ignoring controls presentation and scoring; it never deletes the observation or rewrites whether a human confirmed it.

Safety and migration rules

  • Default “Ignore this finding” creates an exact fingerprint rule. Broader path/rule scopes require an explicit dialog that previews current matches before save.
  • No title, description, or arbitrary regular-expression matching. Use stable fingerprint, rule id, normalized repository path glob, review kind, and source kind.
  • Suppressed findings remain queryable and counted separately. Confirmation rate never treats suppression as dismissal.
  • Migrate current accepted to confirmed/open, waived to confirmed/risk-accepted, false-positive to dismissed/obsolete, and resolved to unassessed/fixed-by-absence. Preserve the original event and label this as a compatibility projection, not newly observed human evidence.

07Run state and durable history

The current store should not be described as purely volatile. It already survives an API restart and resumes unfinished work. The actual gap is that the data is disposable, machine-local orchestration and cannot serve as portable terminal history.

08Per-model review-quality evidence

TE-38 state: receiver delivered, operational feed absent

Token Economy card TE-38 delivered commit 2b368472cd1af0a5e5385a87f2da718c778191d5. That commit is on origin/main and is an ancestor of tag v0.3.1. It contains the schema, fixture, append-only importer, cohort aggregator, confidence gates, generated model knowledge, and tests. The retained integration report records 320 passing tests. Its committed aggregate contains one excluded fixture and zero eligible operational runs, so every model remains unknown / insufficientEvidence and review routing returns no candidate.

TE-38 correctly treats Quality Studio data as observational. Its current gates are at least 20 operational runs, at least 20 assessed findings, and at least 70% finding-outcome coverage. A gated confirmation rate is a precision signal over findings the reviewer emitted. It cannot measure missed findings or recall, and it cannot establish that the model caused the outcome.

Required TE contract alignment

TE-38 v1 says one immutable artifact per run and has one singular reviewAspect. That is not a lossless representation of a Quality Studio sweep with multiple operations and aspects. It also cannot enrich an already imported immutable run when assessments arrive later. S5 should version the bridge, not guess:

  • Add an immutable observationId and parent sourceRunId, plus explicit review kind, aspect, operation id, and evidence cutoff time.
  • Accept append-only assessment observations or revisioned derived outcome snapshots without rewriting the terminal run.
  • Group by executed model, resolved thinking level, CLI, review kind/aspect, prompt version, and comparable scope. Show sample and assessment coverage beside every rate.
  • Keep current TE-38 gates and observational label. Add controlled seeded-defect comparisons before making recall or model-superiority claims.

09Implementation slices

Each slice has a reviewable boundary and acceptance proof. The sequence avoids a flag day and produces value after S1.

S1 · Quality Studio

Exact-span finding highlight on review-meta v2

Scope: Segment each syntax-token line at finding range boundaries, add selected/overlap state, scroll card selection to the primary anchor, show path:line:column on cards, and keep whole-line treatment secondary.

  • Use current ReviewFinding.locations; no backend or schema change.
  • Add pure range/token segmentation tests for single-line, multi-line, Unicode, end-of-line, and overlapping findings.
  • Add Playwright coverage and light/dark screenshots using central tokens and shared primitives.
  • Accept when: the selected columns, not just the line, are visually and programmatically identifiable, and virtual scrolling still renders the correct segment.
S2 · Quality Studio

Review-meta v3 finding evidence and execution provenance

Scope: Add the v3 contract, runner-captured excerpts/hashes, typed evidence, reproduction status, source revision, and requested/executed model plus thinking-level provenance. Keep v1/v2 readers.

  • Extend StartReviewRequest, estimate/start parity, manifest, executor factory, CliRunRequest.ThinkingLevel, run metrics, usage, reviewer identity, schemas, C# records, TypeScript API, and prompt output.
  • Runner creates trusted source-span evidence after current range validation. Legacy evidence remains labelled as a claim.
  • Render evidence/reproduction/origin sections in the detail, reusing the attack-coverage evidence/provenance grammar.
  • Accept when: a v3 round-trip proves requested and resolved route, source hashes, typed evidence and reproduction; v1/v2 fixtures still load; an agent cannot claim deterministic provenance or verified execution.
S3 · Quality Studio

Human assessment, resolution, and scoped ignore policy

Scope: Introduce append-only assessment events, an independent resolution projection, and .quality/findings/suppressions.json with exact-first UI and match preview.

  • Mutations remain API/service-owned with optimistic concurrency; the browser never edits state files directly.
  • Add filters and counts for unassessed, confirmed, dismissed, disputed, open, planned, fixed, risk-accepted, and suppressed.
  • Compatibility projection retains all v1 lifecycle records and original timestamps.
  • Accept when: exact and scoped rules survive restart, expiry re-exposes findings, broad rule preview matches the stored projection, observations remain present, and confirmed/dismissed counts ignore suppression and automatic disappearance.
S4 · Quality Studio

Immutable terminal review history

Scope: Preserve the existing active store and create one committed terminal record at terminal transition, plus an Active/History UI split.

  • Terminal record joins manifest, actual operation routes, hashes, sidecar references, findings, outcomes available at completion, errors, caps, estimate deviation, and usage.
  • Create-only and idempotent by run id/content hash. Add a union-safe merge rule or per-run file layout; never rewrite prior terminal records.
  • Recovery can recreate a missing terminal record from a terminal active directory, but conflicting content is surfaced as corruption.
  • Accept when: API restart, active-directory deletion, and a fresh clone with committed history all retain the same terminal run view; no terminal artifact contains repository absolute paths or unrestricted model output.
S5 · Token Economy then Quality Studio

TE-38 v2 bridge and evidence cutoff export

Scope: First version the TE receiver for parent-run/operation/aspect and later assessment events. Then add a Quality Studio exporter and contract fixture against that schema.

  • Token Economy keeps append-only ingestion, actual route checks, confidence gates, observational labels, and null suitability below gate.
  • Quality Studio exports every eligible terminal operation, including zero-finding runs. Missing outcome coverage remains null, never zero.
  • Generated per-model views show N, dates, aspects, route, files, emitted findings, confirmed/dismissed, assessment coverage, precision, and “recall unavailable”.
  • Accept when: a real non-fixture QS run imports idempotently, a later assessment event increases coverage without rewriting the run, invalid model/level/CLI combinations stay ineligible, and no routing candidate appears before the gates pass.
