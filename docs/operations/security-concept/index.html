A consolidated security concept that extends the existing hardening dossier with what an operator-driven review session actually observed: the availability failure a non-returning review operation adds to the threat model, deterministic evidence that corroborates the authorization-to-command chain, and two sensor findings that change what the deterministic layer can be relied on to do.

02Threat-model delta: the availability dimension

The hardening dossier reasons about confidentiality and integrity: what a spawned process can read, execute, and transmit, and how a poisoned model response can travel downstream. It assumes, reasonably, that a review operation runs and returns. Today's session showed that assumption does not hold on this host, and that its failure mode is an availability problem the existing register did not weigh: a single review operation that never returns freezes the whole review service.

This is the natural completion of hardening finding F-03 ("work and spend caps are enforced after an operation, not before it"). F-03 established there is no pre-flight bound; today shows there is also no post-launch reclaim. Between them, a single operation has unbounded wall-clock license and can hold the entire service.

03Findings from today's runs

N-01 · The claude review path returns nothing and wedges the queue Critical · availability

Seven review runs were started through cliType=claude, model claude-sonnet-5, across security and code kinds on both repos: 110 files queued in total. Over roughly sixteen minutes of active running plus repeated probes, the aggregate was zero usage operations, zero findings, zero tokens, and zero cost. The first run (review-85d631c, task-server security, 24 files) held two files in the running state from 10:35:11Z until it was cancelled at 10:51:32Z without completing a single file. Inspection of the host showed no reviewer CLI child process attached to the QualityStudio.Api server, yet a fresh single-file run enqueued after every prior run had been cancelled still never transitioned out of queued within 60 seconds.

Security reading

Whatever the root cause — a stalled CLI, or an await in the review runner that does not observe the attempt-cancellation token — the exploitable property is the same: the review service has no watchdog. A repository or operation that induces a non-returning review, whether by accident on this host or deliberately on a hostile input, removes the service for every tenant behind the same single-reader queue. Under the hardening dossier's Gate-B ambition (review untrusted third-party repositories), an adversary who can make one operation hang has a reliable availability attack. The mitigation is not model choice; it is a bounded, reclaimable worker.

Root cause was not isolated in-session and is deliberately not asserted here. The observable, reproducible facts are recorded in results/todays-runs-evidence.json: run ids, startedAt/cancelled timestamps, and the wedged-worker probe.

N-02 · The requested deep-review model cannot start a run High · assurance

The session order specified claude-opus-5 for deep review. The model catalog (/api/models, policy version 2026-07-24) lists claude-opus-5 with routing status unsupported and availableForNewRuns=false; ReviewModelCatalog.Resolve therefore rejects it before a run can begin. claude-sonnet-5 is fallbackOnly but runnable. The catalog's own recommendation for a module-scope security review is gpt-5.6-sol at xhigh (correctness floor sol-xhigh), i.e. a codex route, and every claude selection is flagged overrideBelowFloor.

The security consequence is bounded assurance: the strongest review the operator intended to run cannot be dispatched through the supported catalog, so the review layer's confidentiality-and-integrity guarantee is capped below the intended level even before the N-01 availability failure. This reinforces the hardening dossier's own principle — no model can raise the guarantee above the process boundary — with its converse: on this host the intended model cannot be reached at all.

05Sensor availability and scale

N-03 · The boundary sensor does not scale to a large repository High · availability

The boundary-inventory sensor completed on Quality Studio (144 files) in about 1.4 seconds. On Agent Studio (a 1269-file frontend plus a large .NET backend) the same endpoint did not return within a 300-second client timeout. Because security reviews attach non-deterministic sensors and the deterministic-evidence collector runs the enabled sensors at run start (ReviewJobs.cs), an unbounded sensor is both a direct availability limit and a second way to wedge a security run before the model is ever consulted. This is the sensor-path instance of R-03 / S2 input-bounding, which the hardening dossier scoped to review input and file reads but not to the sensor sweep itself.

N-04 · Most deterministic sensors are unavailable by default Medium · assurance

Of eight configured sensors, only three produced evidence in this environment. The rest are unavailable: roslyn, eslint, and sarif require a per-repository reportPath; tsc requires a configured command; and dependencies reports "npm could not be launched".

Two-edged reading

Command-backed analyzers are exactly the host-command-execution surface F-01 warns about, so "disabled until an explicit, host-owned profile exists" is the correct default and matches slice S0. But the same default means a security review presently runs with almost no deterministic corroboration, which pushes the burden of proof onto unverifiable model prose (see the sibling quality concept: agent reproduction status is specified, never verified). The resolution is not to loosen the default; it is to ship the host-owned analyzer profiles of S0/S1 so that corroboration returns without reintroducing free-form command execution.

07Prioritized mitigations

M-1 · A review-operation watchdog and a resilient queue Approve now

  • Give every review operation a versioned wall-clock timeout. On expiry, fail the file, record a diagnostic, and continue — never leave a file in running indefinitely.
  • Decouple run supervision from the channel reader so a stuck run cannot head-of-line-block the queue. A cancelled or timed-out run must free the reader within a bounded interval even if a child process ignores its cancellation token; kill the process tree if needed.
  • Surface a queue-health signal (oldest running age, reader-parked duration) so a wedge is visible instead of silent.
  • Exit: a fixture operation that never returns is reclaimed within its timeout; a run enqueued after a wedged run reaches running; the wedged process tree is gone.

M-2 · Bound the deterministic sensor sweep Required for large repos

  • Apply per-sensor wall-clock and output-size limits to the sensor sweep and the run-start evidence collector, not only to review input (this is the sensor-path half of S2).
  • On timeout, degrade to a bounded partial result or a typed "sensor unavailable: exceeded budget" and let the security run proceed without corroboration rather than hang.
  • Exit: the boundary sensor on Agent Studio returns a bounded result or a typed budget error inside its limit; a security run on a 1269-file repo starts its model phase.

M-3 · Keep the S0-S6 hardening slices as the target

Nothing observed today weakens the QS-58 recommendation. S0 (close the authorization-to-command chain; host-owned analyzer profiles) and S1 (isolated, resource-bounded workers) subsume the deeper form of M-1 and M-2: bounded workers give wall-clock, CPU, and process quotas by construction. M-1 and M-2 are the pre-S1 emergency brakes that make the service survivable today. The deterministic corroboration in N-04 argues for prioritizing the host-owned analyzer profiles inside S0 so security reviews regain evidence without free-form command execution.

M-4 · Align the review route with the catalog Config

Either restore a supported deep-review model in the catalog, or make the default security route follow the model-routing policy's own recommendation (codex gpt-5.6-sol at xhigh for module-scope security). Running every review as an overrideBelowFloor claude selection is a standing assurance gap that should be a deliberate, recorded decision rather than a silent default.
