A stable taxonomy for quality observations

Quality Studio versions its files, but not the meanings inside them. The result is a coherent review envelope around incompatible aspect, evidence, verdict, lifecycle, and model-history semantics.

Status decided Phase implementation delivered Analyzed 11 August 2026 Quality Studio 3e0b655 Source task QS-67

Recommendation

Approve Option B and its five slices. Introduce quality-studio/core@1.0.0 as an independently versioned term catalogue, represent verdicts as typed assessments on separate axes, store evidence as typed references, and append one immutable observation for every model or sensor run. Keep review-meta.v1/v2 readable and keep the current sidecar as a projection during migration.

04Findings

F1. Schema versions are carrying unversioned meanings high

ReviewMetaDocument correctly pins v1/v2 envelope URIs, but an aspect is only {id,title,grade}. The schema accepts any ID matching a lexical pattern. Nothing states which correctness, architecture, or dependencies definition was applied, whether its meaning changed, or which aliases are equivalent. ReviewTaxonomyTests protects only the three review kinds and five hierarchy levels.

Impact: a schema-compatible document can be semantically incomparable with another schema-compatible document.

F2. “Verdict” names at least three different axes high

Flow and attack coverage express assessment outcome. Security expresses enforcement posture and availability in one enum. Change review expresses direction of change. Change aspect verdicts express qualitative concern. Treating these as one flat vocabulary would erase meaning; leaving them unrelated prevents system-wide queries.

F3. A model rerun replaces quality history high

Freshness compares the requested model with reviewer.model. A different model therefore triggers a new review, but ReviewRunner writes to the same unit/kind sidecar with overwrite enabled. QualityReportBuilder reads only those current sidecars. The append-only usage ledger can prove that models ran and what they cost, but cannot recover their grades, verdicts, aspects, evidence, or findings.

The attack-coverage ledger already demonstrates the correct pattern: immutable judgements include agent, model, thinking level, prompt and catalogue hashes, evidence, tokens, and disagreement. The general review path should adopt that observation pattern without adopting attack-specific values.

F4. Evidence has four incompatible shapes high

A general ReviewFinding stores optional evidence as a string. Security wraps machine JSON in that string. Deterministic analyzer results carry separate nested findings and provenance. Attack coverage uses typed {kind,reference,summary} evidence. Flow findings have a path but no evidence collection. The quality report drops finding evidence entirely.

Impact: consumers must parse strings opportunistically, cannot validate locators or hashes uniformly, and cannot ask which evidence supports a verdict or finding.

F5. Producer provenance can be wrong, not merely absent high

FindingSourceKind has only deterministic; agent provenance is encoded by the absence of source. Security sensor findings are appended to top-level findings without the structured source property. The quality report labels every top-level finding agent without inspecting its embedded machine-sensor evidence. This can misattribute a deterministic result to a model.

F6. Lifecycle identity is coupled to one model’s wording and range medium

The v1 fingerprint hashes path, normalized primary code snippet, and agent-selected ruleId. State is keyed by that fingerprint. A changed range, a broad built-in rule ID, or a model choosing another rule can split one issue. More seriously, the latest replacement review automatically resolves a previous finding that is absent. A model comparison can therefore mutate shared lifecycle state by disagreement.

F7. Extension behavior is syntactic and lossy medium

review-meta.v2 allows root x-* properties and rejects unknown nested properties. The typed reader skips unmapped members; its conformance test proves the future field disappears when the document is serialized again. Open aspect strings allow additions, but there is no namespace, catalogue digest, deprecation, replacement, or unknown-term aggregation rule.

F8. Canonical spelling already drifts medium

The shared finding-state projection emits false-positive, while flow-review v1 emits falsePositive. Review schemas use camel case for some enums and kebab case for others. Exact string consumers must already carry aliases, but no alias registry exists.

06Target taxonomy

The target separates structure, vocabulary, policy, and history. A model change creates another observation. It does not change term meanings, overwrite an earlier observation, or silently settle lifecycle state.

Extension contract

  • Every observation pins one core catalogue and zero or more extension catalogues by reverse-DNS ID, SemVer, and SHA-256 digest.
  • Extension terms use their declared prefix, for example com.acme:resilience.backpressure. They cannot redefine a core term.
  • Unknown same-major terms remain visible and round-trip unchanged, but are excluded from aggregates that do not understand them. The UI labels them unrecognized term.
  • An unknown taxonomy major is quarantined as structured-but-unsupported. Raw JSON remains inspectable; no verdict or grade is inferred.
  • All schema objects use an explicit extensions dictionary backed by preserved JSON data. Root x-* keys remain readable as legacy extensions only.

Model identity and fair comparison

requestedModel and effectiveModel are separate. Provider, CLI/agent, thinking level, model revision when available, route policy version, prompt/profile version, taxonomy digest, review-input hash, and subject hash are retained. Missing values are unknown; they are never defaulted from the current platform policy after the fact.

A per-model quality record may be grouped by model, but a model comparison is marked controlled only when subject hash, profile version, prompt hash, taxonomy digest, and applicable evidence set match. Otherwise the UI labels it observational or confounded. This follows the platform routing policy’s warning that historical route outcomes are observational and that thinking level is part of the route.

Finding identity and lifecycle

  • observationFindingId identifies the finding inside one immutable observation.
  • occurrenceFingerprint is a versioned exact correlation key. Existing v1 fingerprints are retained as aliases.
  • issueId identifies a cross-observation issue after exact or reviewed correlation. A model name is never part of it.
  • Lifecycle is an append-only event stream keyed by issueId. An observation cannot directly set accepted-risk, waived, false-positive, or resolved.
  • Automated resolution requires a versioned reconciliation policy and basis observation IDs. Omission by a different model does not resolve an issue.

10Approval-ready implementation slices

T1. Contract and catalogue foundation first

Scope: add schemas/quality-taxonomy.v1.schema.json, schemas/quality-observation.v1.schema.json, the core catalogue JSON, C# contract types, preserved extension data, and a pure legacy mapping library. Do not change writers.

  • Pin exact terms, descriptions, aliases, deprecations, ordering, and allowed assessment axes.
  • Add conformance vectors for every row in section 8 and reject unknown majors without discarding raw data.
  • Prove extensions survive deserialize/serialize and do not participate in core aggregation without an installed catalogue.

Acceptance: schemas validate positive/negative fixtures; every current verdict/state spelling maps deterministically; no production output changes. Size: M. Dependency: none.

T2. Immutable observation dual-write and full route provenance

Scope: append .quality/observations/YYYY-MM.jsonl after every successful general review. Extend review request, run manifest, agent result, and usage link with provider, requested/effective model, thinking level, and routing-policy version. Continue writing review-meta.v2 unchanged.

  • Derive idempotent observationId from run ID, unit ID, kind, subject hash, input hash, and taxonomy digest.
  • Use the append/write-through and malformed-line tolerance already proven by UsageLedger.
  • Record unknown when the runner cannot report thinking or provider; never infer a level from model name.

Acceptance: two forced runs on the same unit with different models leave two observations and one current sidecar; both join to their usage entries; replay does not duplicate a line; a crash before sidecar projection leaves a recoverable observation. Size: L. Dependency: T1.

T3. Typed evidence, producer provenance, and issue lifecycle v2

Scope: convert locations and sensor facts into typed evidence, make producer kind explicit, introduce issueId plus versioned occurrence fingerprints, and add append-only lifecycle events. Keep the current state snapshot as a derived compatibility file.

  • Fix security-sensor provenance in the projection and ensure report/SARIF exports do not label it agent-authored.
  • Keep every legacy fingerprint as an alias; correlation never deletes or rewrites it.
  • Require an explicit or policy-backed resolution event. A different model’s omission is not enough.

Acceptance: agent, deterministic sensor, and human sources round-trip; evidence refs resolve; lifecycle tests cover model disagreement, reopen, expiry, and idempotent replay; v1 state remains readable. Size: L. Dependency: T2.

T4. Observation-backed projections and per-model records

Scope: make QualityReportBuilder, repository dashboard, and current-sidecar generation read the observation store through one reducer. Add per-model/profile aggregates without changing default score policy.

  • Current selection is a versioned policy based on subject/input freshness and review profile, not latest timestamp alone.
  • Expose model, thinking level, sample count, subject/profile comparability, grade, assessment, and finding counts.
  • Label comparisons controlled, observational, or incomplete from hashes and missing provenance.

Acceptance: existing report fixtures retain current totals; model A and model B are both queryable; selecting the current observation is deterministic; unknown taxonomy terms remain visible and excluded from unsupported aggregates. Size: L. Dependency: T3.

T5. Domain adapters and migration tool

Scope: emit common observations from security combination, change review, deep-flow review, and attack coverage while retaining their v1 domain files. Add quality taxonomy migrate --dry-run|--apply.

  • Backfill one partial observation per current v1/v2 sidecar and current flow report. Join usage only by exact run ID.
  • Import attack observations without losing assessment IDs, disagreement, evidence, thinking level, or catalogue hashes.
  • Import change documents on the change axis and preserve their four aspect judgements.
  • Produce a machine-readable migration report with imported, skipped, ambiguous-source, unknown-model, and error counts.

Acceptance: dry-run performs no writes; apply is idempotent; old files are byte-identical; every migrated value matches section 8; ambiguous facts remain explicitly unknown. Size: L. Dependency: T4.

12Acceptance invariants

Non-negotiable data invariants

  • No model run overwrites or deletes another model run’s observation.
  • No observation changes human lifecycle state directly.
  • No absent, unknown, unavailable, or unsupported value is converted to pass.
  • No policy disposition is stored as if it were an evidence assessment.
  • No extension term is silently coerced into a core term.
  • No per-model comparison is called controlled unless subject, profile, prompt, taxonomy, and evidence applicability match.
  • No migration rewrites v1/v2 sidecars, usage ledgers, attack ledgers, flow reports, or change reports.

Final recommendation

Adopt the small common semantic kernel, not a universal workflow schema. Preserve every producer’s domain details through extensions and adapters, but require all new records to state who produced them, which exact evidence they used, which taxonomy and policy meanings apply, and which immutable model run they belong to.
