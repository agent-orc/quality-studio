01Scope and method

Six parallel deep reads covered the core library (61 files, 17,318 LOC), the API host (16 files, 5,802 LOC), the Angular frontend (3,663 LOC plus 1,154 LOC of specs), the concept and its documents against the code, the test suite and the three workflows, and the review output the product wrote about its own repository on 2026-09-01 (128 file sidecars, 430 findings, 15 runs, one monthly ledger). Every load-bearing claim was then re-verified in the code. Locally the .NET suite ran with Category!=MachineBound (231 passed, 1 skipped, 1 Windows file-lock failure in test cleanup) and the frontend suite ran headless in Chrome (53 passed). Board state came from the Agent Studio API, CI history from the GitHub API.

Not exercised: a live review run against the API during the assessment, the remote runner host, Linux behaviour beyond CI logs, and the published website in detail. Token costs are catalog prices, not invoices.

Reading

The finding layer is trustworthy with a caveat at critical and high; grades, severities, and the completeness claim of a run are not. Structural defects (monoliths, clones, cross-file inconsistency) are invisible by construction because every review runs on the file level. The product can be read as a source of work items; it cannot yet be used as a gate.

06Operator decisions

D-1 · Levels: deliver function and namespace reviews, or stop promising them

The README, the concept and the website promise five levels. The product reviews one. Function nodes exist in the tree and are refused by the review engine; namespace nodes are derived and never reviewed; module reviews reuse the file prompt over concatenated content.

  • Option A Deliver: a function prompt with its own economy (a function review must cost a fraction of a file review), a namespace and module prompt with architecture as an aspect, and reviews at those levels executed at least once on this repository. Effort 6 to 9 days, on top of the compiler-grade derivation now landing.
  • Option B Reduce the promise to Project, Module, File; keep Function and Namespace as roadmap in the concept's research box; align README and website. Effort 1 day.
  • Recommendation B now, A as a later slice once module and project passes (P-2) have proven their value. The current state, regex-derived ids under a contract that promises compiler ids and a level nothing can review, is the most expensive of the three.

D-2 · What stays versioned next to the code

QS-102 moves every .quality/** output out of the analysed checkout into a data root and leaves open which artefacts stay versioned. Moving everything out solves the dirty-integration problem and removes the product's distinguishing promise.

  • Option A Everything in the data root; the checkout is read-only for the studio; explicit exports only.
  • Option B Slim sidecars stay tracked (unit, hash, grade, finding fingerprints with titles and locations, review inputs hash); fat artefacts move to the data root (reports, run journals, ledgers, finding bodies, captured excerpts). A merge-driver rule keeps sidecars mergeable: keep the version whose hash matches the merged content, otherwise the newer one, which then shows as stale.
  • Option C Everything stays tracked as today.
  • Recommendation B. It keeps "the repository owns its review truth" true, removes 34 percent of the tracked tree, removes exploit-grade finding prose from a public repository, and keeps the integration checkout clean. Slice P-4 specifies it.

D-3 · Security hardening scope before any hosted use

The security dossiers (QS-W12, QS-W13) are decision-pending while card QS-68 carries a note that all recommendations were blanket-approved. The two statements contradict each other and should be made unambiguous.

Operator scope recorded on 2026-09-06

Operation stays 100 percent local for now; a multi-user team deployment is not planned. The target is one container image that hosts the API and the built UI, with Agent Studio as an API client authenticated by an API token. The Hosted mode's bearer client credentials already provide that token; the UI still has to send it, and Local mode still needs a loopback guard. Options A and B below therefore cover the planned scope; C stays the target for any later hosted use.

  • Option A Authorization half of S0 only (delivered by QS-68). Hosted use with trusted repositories only.
  • Option B Full S0 (host-owned analyzer profiles instead of free commands) plus a loopback guard for Local mode, or a usable Hosted mode for the UI. One to two days. Closes the trivially exploitable chain.
  • Option C The target architecture: isolated short-lived workers with a read-only snapshot and a result broker (S1), input bounds (S2), end-to-end secret handling (S3), data-only rendering and handover (S4), credential lifecycle (S5), supply-chain gate (S6). Fifteen to twenty-five engineering days. Only then foreign repositories.
  • Recommendation B immediately, C confirmed as target and scheduled slice by slice. Until S1 and S2 land, reviews stay limited to repositories the operator controls. Slice P-6 carries B.

D-4 · Rule library scope

The operator wants the rule library expanded for every review kind. Today it is dead code with nine authored rules. The decision is about scope and ownership: a repository-owned library that ships with the product (rules under rules/, generated catalogue embedded, overrides under .quality/inputs/), or an operator-owned library synchronised from an external source of truth. Recommendation: repository-owned, versioned with the product, with per-technology sections for code, security and performance; every finding then carries a real ruleId instead of built-in:code. Slice P-5.

07Implementation slices

Each slice is independently reviewable and names its exit evidence. Effort is an engineering estimate.

P-1 · Evidence gate and calibration · 4 to 6 days

  • A finding that contradicts deterministic evidence (a compile claim against a green build sensor, a secret claim against a clean gitleaks run) is not persisted unless reproduction.status is reproduced; the rejection is recorded on the run.
  • The boundary sensor fires only when authorization is absent or the data flow demonstrably bypasses PathConfinement; multiple routes with the same defect become one finding with a location list.
  • Sensor unavailability leaves the score alone and sets a completeness field on the grade; the projection and the UI show it as such. Grades are normalised for unit size so that a 6-line file cannot earn an A by being short.
  • Invalid JSON or an out-of-subject location triggers exactly one re-ask with the error text before the file is failed; aspect ids are canonicalised before persistence.
  • Exit evidence: a re-run over this repository with zero persisted findings that contradict sensor evidence, at most one security finding per route class, and 15 security grades that differ from each other.

P-2 · Module and project passes · 4 to 6 days

delivered 2026-09-06 on work/repository-level-analysis: module and project prompts of their own, with architecture, structure, boundaries, duplication and consistency as aspects and the aggregate security pass as a threat analysis over the derived boundary inventory that closes with a prioritised mitigation plan; ReviewPromptBuilder selects by (level, kind) and records the template that ran; the aggregate subject is a budgeted member digest - sizes, current grades, member findings, derived structure, boundary inventory, proportional source with real line numbers - instead of concatenated members; a cross-file finding persists every occurrence as a related anchor with its own captured excerpt, and its citations of member findings are checked against the sidecars before they are recorded. Still open in this slice: the performance kind runs the file template at every level and has not been executed over this repository, and the exit evidence below needs a real sweep - the branch was built and tested without agent runs.

  • Own prompt templates for module and project reviews with architecture, structure and duplication as aspects; the module pass receives the member file summaries and grades, not the concatenated source.
  • Class rollups across files: the same defect class (case-insensitive containment, sequential pipe reads, missing timeouts) becomes one finding with N locations.
  • The performance kind runs once over this repository; test code enters the scope with its own aspect set.
  • Exit evidence: at least one module sidecar per src/ project and one project sidecar, each with a structural finding a file review cannot produce (the 1,433-line host, the four execution-sequence clones).

P-3 · Process runner · 3 to 4 days

  • One ProcessRunner with a versioned wall-clock timeout, concurrent drain of both streams, and kill of the entire process tree on timeout, cancellation and shutdown; all git, dotnet, npm and gitleaks call sites use it, including the five git-runner copies.
  • matchTimeout on every regex that runs over repository content; retry with backoff on provider rate limits instead of failing the file.
  • Builds on QS-93 (operation watchdog) and QS-96 (sensor runner leak).
  • Exit evidence: a fixture process that never exits is killed within the budget; no orphaned child after a cancelled run on Windows and Linux.

P-4 · Slim sidecars and the repository manifest hash · 3 to 5 days

  • Implements D-2 Option B on top of QS-102's data root; migration keeps existing sidecars readable.
  • A repository-level manifest hash over all in-scope file units and the review-inputs hash is computed by the scan and written to scan results, run manifests and run reports, so a whole scan is current or stale in one comparison and identical content on two branches yields identical evidence.
  • A .gitattributes merge driver for sidecars with the rule above; cross-process locking for ledger and finding state.
  • Exit evidence: a full studio run leaves git status clean except for changed slim sidecars; two branches with identical content produce the same manifest hash.

P-5 · Rule library · 5 to 8 days

  • Generate catalogues/rule-catalogue.v1.json from rules/ with the script the README already names; embed it; wire RuleCatalogueResolver.RenderAsReviewInputs into ReviewPromptBuilder behind the existing inputs budget; add GET /api/repos/{id}/rules with traces.
  • Author rules per technology for code, security and performance; each finding carries the matching ruleId.
  • Exit evidence: a review of this repository in which every finding's ruleId resolves to a catalogue entry, and the QS-W11 measurement can name the rule set it ran under.

P-6 · Operations and S0 · 4 to 6 days

  • Analyzer commands come from host-owned profiles; client configuration selects a profile id. Local mode refuses to bind a non-loopback address, or Hosted mode becomes usable from the UI with an interceptor and a credential flow.
  • Size limit on GET /api/file, cached sensor availability, bounded dashboard cache, error handler and reindex for the sidecar file watcher, pinned gitleaks digest in the repository.
  • A Dockerfile that publishes the API and serves the built frontend; a documented prerequisites section (pre-authenticated agent CLI, .NET 10, Node 22, git).
  • Exit evidence: the two security tests from QS-68 extended with a profile-only command test; a container that answers /health and serves the shell.

P-7 · Frontend gates and error path · 3 to 5 days

  • Status-code-aware errors with retry through an HTTP interceptor; no demo content for a real path (the same-day fix removes the fallback; this slice adds the UX).
  • ESLint at error severity for accessibility and correctness rules; the perf harness in build.yml; assertion-free evidence scripts moved out of tests/.
  • Specs for the app shell, the repository dialog and attack coverage; hover no longer selects; focus trap and Escape for every dialog; the code viewport is keyboard-scrollable.
  • Exit evidence: npm run lint can fail; a perf regression fails CI; every dialog passes the keyboard checklist.

P-9 · Cost transparency and budgets · 2 to 3 days

  • Landed the same day: every ledger entry carries its estimated cost at the synchronized snapshot price, the host logs each operation's spend (event ReviewOperationUsage), GET /api/usage totals cost over the history and counts unpriced operations, and the price catalog is the Token Economy snapshot rather than the runner's seed.
  • Remaining: show cost per run and per operation in the usage history and the run panel; a repository-level cost budget next to the existing token cap (DefaultReviewTokenCap) with a recorded stop reason; an explicit subscription mode for CLIs metered in usage windows (no cap by design, costs still estimated and logged); a catalog-staleness signal when the snapshot's newest price entry is older than a configured age.
  • Budgets are cost budgets, not time budgets. Timeouts in P-3 are an availability mechanism for hung processes, not a product feature.
  • Exit evidence: a run started without a model shows its model, model source and running cost in the UI; a run with a cost cap stops with the cap named in its stop reason; the usage view shows the sweep total in the ledger's currency.

P-8 · Cleanup and honesty · 2 to 3 days

  • Remove src/quality; one name for package, assembly and namespace; a single typed reader for sidecars with runtime schema validation; one AtomicJsonFile helper with fsync; unit-id resolution through the hierarchy cache.
  • README working state, concept date, and website aligned with what the code does; D-1 applied.
  • Exit evidence: no second quality assembly in the solution; the README's status block names the current card range.
