Performance after QS-54

QS-54 shipped and made repeat switches fast on its fixture. Fresh rebase measurements show that the real large repository still spends seconds deriving cold state and returns a 29 MB tree. Review parsing is not the problem; model time and terminal notification are.

Status decision pending Phase decision-ready Measured 11 August 2026 Source base e9623e6 Measured revision d0847d2

Recommendation

Approve the four bounded slices in section 8: lazy tree transport first, persistent startup snapshots second, review-run push events third, and bounded dashboard-cache retention fourth. Keep the current model-routing correctness floor unchanged. The plan targets the measured local overhead without trading review quality for speed.

02Method and limits

Measurements ran on Linux 6.8, .NET SDK 10.0.301 / runtime 10.0.9, Node 22.23.1, Chromium 149.0.7827.55, and an Intel i7-8700 with 12 logical CPUs and 62 GiB RAM. Every backend startup sample spawned a new Release API process. Startup requests began immediately after /health responded, so the result includes contention with QS-54 background prewarming exactly as a first operator session experiences it.

The mandated base reconciliation found no refs/heads/develop on the configured origin; origin/HEAD advertises origin/main. The worktree was therefore fetched and rebased to fresh origin/main at e9623e6, then only the two QS-59 salvage commits were replayed. No newer operation dossier was overwritten.

  • Startup: five Quality Studio process starts and three Agent Taskboard process starts; project and tree requested concurrently after health.
  • Large-repo steady state: one prewarmed Agent Taskboard process, then 20 concurrent project-plus-tree requests.
  • Memory: a generated Git repository with 1,603 tracked Angular/TypeScript files; five warm invalidations before baseline, then 100 distinct dirty states and project requests.
  • Review: one live runner-default Codex review of an isolated 12-line C# file; a separate 10,000-iteration strict-parser probe with a 12,644-byte, 30-finding response.
  • Rendering: the real Angular application with a controlled local API. The API became terminal 100 ms after queueing; the product's 1,500 ms polling code was not changed.

Interpretation boundary

The live review is one external model sample, sufficient to locate the dominant phase but not to characterize provider variance. The repository does not contain the prompt-named AGENTS.md, docs/start/README.md, contribution guide, design-principles document, filesystem contract, or model-routing policy at this commit. No model or thinking-level change is therefore proposed. The live probe used the runner default without an override.

One timing gate remains host-sensitive

The production Angular build passes at 476.18 kB against the 480 kB error ceiling, but leaves only 3.82 kB headroom and still exceeds the 350 kB warning threshold by 126.18 kB. The API suite's MachineBound 5,000-file projection test measured 302 ms against 150 ms in the suite, then passed when rerun alone. Keep both thresholds: split initial code toward 450 kB and schedule machine-bound timing gates in an isolated performance profile.

07Top three cost blocks

1 · External model execution

14.534 s in one 14.834 s review. Parsing is 0.108 ms median, so parser tuning cannot move end-to-end latency.

Correctness-bound: measure phases; do not downgrade routing.

2 · Cold hierarchy + projection

7.60–9.10 s prewarm total on 3,927 real files. The first request then waits 5.69–7.31 s on the cache lock.

Persist verified snapshots across process restarts.

3 · Presentation after the work

29.1 MB recursive tree makes warm switching 696 ms p95; review polling adds 1.412 s after terminal state.

Lazy tree transport + push review events.

Resource risk · retained projections

+18.1 MiB anonymous RSS after 100 states. Not ranked by immediate latency, but it is deterministic code debt and a small bounded fix.

Keep current and previous state only.

08Approval-ready implementation slices

Slice P1 — Lazy tree contract and honest timing approve first

  • Add a versioned tree query that returns one level at a time with hasChildren, cursor/limit, ETag, and per-node aggregate facts. Keep the current endpoint during frontend migration.
  • Load children when a standard explorer row expands; retain virtualized rendering and per-repository browser snapshots.
  • Remove recursive descendant flattening from every response node by deriving aggregate coverage/review counts once in the immutable snapshot.
  • Time projection, JSON serialization, bytes, and total response completion. The current TreeLoaded stopwatch ends too early.
  • Increase production-build headroom while touching the shell: defer at least 26.18 kB of non-initial review/administration code and leave the 480 kB error budget unchanged. Target 450 kB or less.

Expected gain: root payload from 29.1 MB to below 1 MB (>96% reduction), real warm project-plus-tree from 301.69 ms median / 696.43 ms p95 to below 150 / 500 ms, and at least 26.18 kB (5.5%) raw reduction versus today's initial bundle. Acceptance: production build passes at ≤ 450 kB initial, expand-to-visible p95 < 100 ms for cached children, identical grade/finding/coverage facts, keyboard behavior unchanged.

Slice P2 — Persisted verified startup snapshot

  • Persist the versioned hierarchy plus bounded dashboard projection in API-owned state under the host content root, never inside a registered repository.
  • Key by repository id, schema version, normalized root, Git HEAD/index/worktree fingerprint, global-input fingerprint, and input budget. Write atomically; reject corrupt or mismatched entries.
  • Hydrate before queueing background refresh. Keep /health as liveness and expose snapshot readiness separately so the UI can distinguish live, restoring, and rebuilding.
  • Preserve the current cold rebuild as the correctness fallback.

Expected gain: remove the observed 5.98–7.66 s hierarchy scan from valid restart paths (76–81% of process-to-usable in the three paired samples). With P1, target process-to-usable below 2.0 s median and 3.0 s p95 on the same 3,927-file repository. Acceptance: five restart samples, plus corrupt-cache, changed-index, dirty-file, and changed-global-input tests.

Slice P3 — Push review state and phase telemetry

  • Publish review-run transitions from the application-owned ReviewJobService over server-sent events; keep the existing 1,500 ms poll as reconnect/fallback.
  • Update the existing review-run signal from events and refresh tree/project/file only after terminal state, coalesced once per run.
  • Record promptPreparationMs, agentMs, parseMs, identityAndMergeMs, persistMs, and notificationMs. Do not put partial phases into the committed usage ledger until its schema is versioned.
  • Leave model and thinking-level routing untouched pending the repository's authoritative policy document.

Expected gain: terminal-to-visible from 1,411.72 ms median to below 100 ms p95 (>92% reduction); render cost already measures below 14 ms. Single-call model time is expected to remain provider-bound until phase data supports a correctness-safe optimization. Acceptance: five controlled completions, reconnect fallback, duplicate/out-of-order transition tests.

Slice P4 — Bounded projection retention

  • Replace root + GitState accumulation with a per-root slot holding the current projection and at most one previous state needed by in-flight readers.
  • Remove slots when a registry entry is archived or its root changes. Add observable cache entry count and estimated retained bytes.
  • Bound frontend project/tree snapshots to currently registered repositories and clear archived ids.

Expected gain: eliminate the observed +18,520 KiB retained growth. Acceptance: the same 100-state probe ends within 5% of baseline anonymous RSS after GC opportunity, cache cardinality remains bounded, and no stale state is served.
