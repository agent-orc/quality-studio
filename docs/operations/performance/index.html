05Top three cost blocks

#1 Model execution followed by range rejection

Evidence: 112.623 seconds model p50, 99.87% of server time, with zero usable results from three returned responses. Parser and render measurements are orders of magnitude smaller.

Root: the output contract depends on model-authored numeric ranges. Validation occurs only after the expensive response is complete and usage is recorded. Production does not retain enough phase/outcome detail to distinguish parsing, re-anchoring, and persistence.

Fix: add explicit review phase telemetry; send a stable line-numbered subject and exact evidence-anchor contract; resolve exact anchors deterministically to ranges; and allow one bounded location-only repair when the anchor cannot be resolved. The repair must retain the original finding text, record provenance, validate again, and never trigger an automatic full Terra rerun. A bounded structured repair may use the policy's gpt-5.4-mini high-thinking role exception; the primary review remains Terra-medium.

Expected gain: recover failed output without repeating a 112.623-second median primary call. Acceptance target is at least 9 usable reports in 10 forced reviews, repair p95 at or below 10 seconds, and no silent range clamping. This improves failed-review time-to-usable; it does not claim to remove the base primary-model latency.

#2 Repeated multi-solution hierarchy construction

Evidence: the large cold scan is 7.167 seconds, 81.49% of the 8.795-second snapshot. The returned hierarchy has 13 project roots, 22 module nodes, 13,581 file nodes, and only 2,130 unique file paths. That is 6.38 file-node occurrences per unique path. Agent Studio has 3,927 tracked files. The existing 5,000-file initial-dashboard test also failed its 150 ms budget in five of five fresh processes, with a 194 ms median and 184-291 ms range.

Root: RepositoryHierarchyBuilder.BuildDotNet builds a root for every top-level solution. BuildModule recursively enumerates and reads a project directory for each solution membership; namespace extraction reads source content before the source reader processes it again. Legitimate solution membership is represented by duplicating full descendant trees.

Fix: create one canonical project/source graph per Git state, parse each project and source file once, and represent solution membership as references. Cache file-derived namespace, function, metric, and finding projections by content identity.

Expected gain: at least 70% lower large-repo scan time, from 7.167 seconds to at most 2.15 seconds. Removing duplicate paths alone reduces the measured response shape by 53.27%; the scan target is conservative relative to the observed 6.38× file-node repetition.

#3 Full eager hierarchy on the usable path

Evidence: the actual tree response is 29,119,333 bytes and 28,563 nodes. Warm tree HTTP is 403.08 ms p50 and 1,078.37 ms p95. Browser switching is 1,012.4 ms p50 and 1,425.2 ms p95, with zero of five large switches meeting the 500 ms budget. The default repository passes five of five at 70.5 ms p50.

Root: TreeNodeResponse.From recursively materializes every descendant, while QualityApi.selectProject waits for both project and tree responses before announcing usable state and stores the complete snapshot. Functions that are not visible in a collapsed tree still cross the API boundary and are parsed on the UI thread.

Fix: return a canonical shallow tree for switch readiness, load function children on file expansion, enable Brotli response compression, and use a Git-state ETag for unchanged snapshots. Structural reduction is required because compression alone does not avoid JSON parse and object allocation.

Expected gain: filtering the actual response to unique paths without function nodes yields 2,559,616 raw bytes and 147,228 Brotli bytes, reductions of 91.21% and 89.61% respectively. Set the release target to 3 MB raw, 200 KB Brotli, and large-switch p95 below 500 ms.

07Options and recommendation

Option A: observability only

Add startup and review phase timings, keep the current hierarchy and output contracts.

Trade-off: lowest implementation risk, but it leaves the measured 8.8-second cold work, 29.12 MB payload, 1.0-second UI switch, and discarded model results unchanged.

Option B: tree transport relief

Add compression and lazy function loading without changing the hierarchy builder.

Trade-off: improves network and browser work quickly. It does not remove repeated source reads, duplicated project membership, projection cost, or failed review output.

Option C: remove duplicated work end to end Recommended

Land phase telemetry and output recovery, canonicalize repository derivation, move details behind lazy boundaries, persist snapshots by Git state, and bound caches.

Trade-off: broader contract work, with migrations needed for tree consumers and canonical report provenance. It is the only option that addresses all three measured cost blocks while preserving the routing policy.

Recommendation

Approve Option C. Sequence observability and replay fixtures first, then land review recovery and hierarchy/tree changes behind compatible API fields. Do not accept compression as the large-repo fix by itself, and do not lower the primary model route to meet a latency target.

08Implementation slices for approval

P0 · Measurement contract and CI subjects

Scope: promote the QS-59 probes into deterministic harnesses; add an actual multi-solution fixture with shared project membership; emit startup, review prompt/model/parse/identity/persist, tree serialization, response-byte, browser parse/map, and outcome phases. Persist phase data in the canonical report and structured server events.

Acceptance: one command produces the five baseline families; every forced review has phase totals and outcome; tree events include raw bytes and node counts; CI retains JSON artifacts. Timing overhead stays below 1% in the 5,000-iteration parser/render microbench.

Gain: no direct latency claim. It closes the current non-model envelope and cost-catalog blind spots before optimizations land.

P1 · Review output anchoring and bounded repair

Scope: render stable line-numbered subjects, require exact evidence anchors, deterministically map unique anchors to ranges, and add one provenance-recorded location-only repair for missing or ambiguous anchors. Reject ambiguous repair rather than clamp. Keep the primary route at Terra-medium; use only the governed Mini-high bounded structured-decision exception for repair.

Acceptance: at least 9 of 10 forced reviews produce a range-valid report; repair p95 is at most 10 seconds; no full primary rerun is automatic; primary and repair model/thinking provenance are in the report; below-floor override remains false.

Expected gain: avoids repeating a 112.623-second median primary call when only location identity is invalid. It converts the measured zero-of-three usable-result failure mode into a bounded recovery path.

P2 · Canonical hierarchy graph and one-read derivation

Scope: parse each solution, project, and source file once per Git state; retain solution membership as references to canonical module/file identities; share namespace, symbol, metric, finding, and coverage derivations; preserve all current logical solution views.

Acceptance: the pinned Agent Studio subject preserves 13 solution memberships and 11 unique modules without descendant duplication; hierarchy scan is at most 2.15 seconds; cold projection is at most 800 ms; regression tests cover a project included in multiple solutions.

Expected gain: at least 70% hierarchy-scan reduction and at least 48% projection reduction on the pinned subject. The raw canonical tree is at least 53% smaller before lazy loading.

P3 · Shallow switch payload, lazy symbols, compression, and ETag

Scope: make switch readiness depend on project plus shallow canonical tree; fetch function/symbol children on expansion; enable Brotli; return a Git-state ETag and honor conditional requests; cap browser snapshot retention without changing the visible selection model.

Acceptance: pinned large tree is at most 3 MB raw and 200 KB Brotli; five of five large switches meet 500 ms, p50 is at most 250 ms, and five of five transition events meet 100 ms; default-repo switch p95 does not regress beyond 110 ms; expanded file symbols match the former eager response.

Expected gain: approximately 91% structural payload reduction based on filtering the measured response, plus conditional zero-body reuse for unchanged Git states.

P4 · Persisted snapshots, bounded caches, and startup scheduling

Scope: persist versioned canonical hierarchy/dashboard snapshots keyed by repository identity, commit/index state, and schema; derive changed files incrementally; add size/age bounds for API Git-state caches and browser snapshots; schedule background prewarm after readiness with cancellation and concurrency limits.

Acceptance: unchanged large-repo restart snapshot is at most 750 ms; startup p50 is at most 650 ms and p95 at most 1,000 ms; API RSS growth from operation 100 to 500 is at most 10%; browser heap growth from switch 25 to 100 is at most 5%; cache eviction tests cover Git-state churn.

Expected gain: removes more than 90% of the measured 8.795-second unchanged cold snapshot and makes the currently stable memory result an enforced bound.

Limits on interpretation

  • Measurements are from one Linux host: Intel Core i7-8700, 12 logical CPUs, 62 GiB RAM, .NET SDK 10.0.301, Node 22.23.1. Use changes and budget gates, not cross-host absolute comparisons.
  • All HTTP measurements are loopback. Remote network latency is absent.
  • The review sample is n=3 and intentionally forced; it establishes cost dominance and a repeatable failure mode, not a distribution for all files or review kinds.
  • Parser/render microbenchmarks use a valid one-finding sample and the actual partial canonical report. Production phase telemetry is still required before attributing the complete 149 ms non-model envelope.
  • The 91.21% payload estimate filters the actual response in memory. It predicts the structural opportunity; P3 must prove the production result and semantic equivalence.
  • The memory soak uses static Git states. P4 adds a churn-specific bound because current cache keying can retain successive states.
