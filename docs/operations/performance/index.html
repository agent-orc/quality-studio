Quality Studio performance

What Quality Studio actually costs on a real host and two real repositories: startup, repository switch, review-run latency, memory over a long session, and behaviour at large-repository scale. Every number below was produced by two reproducible harnesses committed with this dossier; the three dominant cost blocks are named with the evidence that identifies them and with fixes the operator can approve as slices.

Status decision pending Phase decision ready Measured 2026-08-24, Release build, Local mode QS commit e31089c Large target agent-taskboard ffe887a0, 5,116 tracked files

Key findings

QS-54 delivered what it promised, and the promise is narrower than the operator experience. Background prewarm works: host startup is unaffected by registry size, and a warm /api/project costs 31.87 ms on a 5,116-file repository. But the warm dashboard is only one of the two requests on the switch critical path, and the snapshot it warms is discarded by the next write to the repository.

  • The repository tree is the switch. On agent-taskboard the warm critical path is 664.89 ms, of which /api/tree?path= is 659.10 ms and the dashboard QS-54 optimised is 31.87 ms. The tree returns 33.87 MiB. The documented < 500 ms click-to-usable contract is exceeded by the backend alone in 7 of 7 samples, before any browser work.
  • The tree emits 6.1× more file nodes than the repository has files. 15,961 file nodes for 2,596 distinct paths; frontend/src/dev-mode.ts appears 12 times. This is an adapter overlap, not repository size.
  • The endpoint already supports the cheap answer and nobody asks for it. A conditional request returns 304 in 38.11 ms with 0 bytes. The word If-None-Match does not occur anywhere in frontend/src.
  • Any write to the repository costs a full cold rebuild, inline. An 81.95 ms coverage sensor scan made the next dashboard request on agent-taskboard cost 16,143.72 ms. The prewarmer only fires at registration, never on invalidation.
  • Review preflight is synchronous and linear in subject size. POST /api/review/estimate costs ~164 ms per subject file inside the HTTP request: 198,976.86 ms for a 1,215-file module, before a model is consulted.
  • Memory is not the problem today. 640 requests across two repositories moved resident set from 313.20 to 336.54 MiB with no monotonic trend. The unbounded structures that exist are real but did not dominate at measured scale.
  • The requested model-vs-parsing-vs-rendering split cannot be produced. The review path emits no phase telemetry at all — no qs.* event, no Server-Timing, no ActivitySource — and the CLI review operation does not return on this host. Instrumentation is a prerequisite, not an optimisation.

Why a delivered optimisation stopped covering the case

QS-54 instrumented and cached exactly one endpoint. /api/project got a projection cache, a Server-Timing header, and the qs.repository.switch.backend event. /api/tree — the other half of the same Promise.all — got none of the three, so it was invisible to the QS-54 measurement and remains invisible in production telemetry today. The QS-54 browser harness used a 1,600-file synthetic TypeScript fixture whose adapter emits no function-level nodes; on a real mixed .NET repository the same endpoint returns 34,809 nodes. The optimisation is correct. Its measurement was scoped to the wrong half of the request pair.

04Cost block 1 — the repository tree response Dominant

Where the size comes from

RepositoryHierarchyBuilder.Build (RepositoryHierarchyAdapters.cs:20-46) runs the .NET adapter and the Angular adapter over the same repository and concatenates their roots. The Angular adapter emits one project per discovered angular.json workspace project; agent-taskboard yields 13 projects, and shared sources under frontend/src land under each of them. The result is 15,961 file nodes for 2,596 distinct paths — 6.1× amplification that is a property of the adapter composition, not of the repository.

The handler itself adds fixed cost per request that is unrelated to the payload: CoverageSnapshot.Load, a FindingStateStore read, and a fourth git subprocess for rev-parse --verify HEAD (Program.cs:411,421-422) on top of the three git spawns ComputeGitState already performs (RepositoryHierarchyCache.cs:86-88). A single switch therefore spawns six git processes.

The client cannot use what it is sent

The tree view renders an overscanned 40-row window (frontend/PERF.md). It needs the roots plus the currently expanded paths. It is sent 34,809 nodes, retains all of them in treeSnapshots per repository (quality-api.ts:436,519) with no cap, and logs nodeCount: tree.nodes.length — the root count, 13 — so the 33.87 MiB is invisible in client telemetry as well.

05Cost block 2 — snapshot invalidation is a full inline rebuild Dominant

The hierarchy snapshot is keyed by a hash of HEAD, the index, and the bytes of every dirty or untracked file (RepositoryHierarchyCache.cs:84-114). Any accepted write to the repository produces a new key, and the next request rebuilds the whole hierarchy and projection inside that request, under the per-repository lock. The prewarmer only enqueues a repository at registration and at host start (RepositorySnapshotPrewarmer.cs:35-53); nothing re-warms after an invalidation.

06Cost block 3 — the synchronous review path Dominant

Per file it reloads the repository scope, re-resolves review inputs, loads and heals threads, loads the coverage snapshot, and spawns a blocking git rev-parse (ReviewRunner.cs:295-325). Two configuration facts that make it worse

  • ReviewJobs:MaxConcurrency is unreachable in the shipped configuration. appsettings.json ships DefaultReviewTokenCap: 100000, so ResolveCap always returns a cap (ReviewJobs.cs:329-335), so item.HasCap is true (:728), so RunAsync takes the strictly sequential branch (:465-472) and the Parallel.ForEachAsync branch with MaxConcurrency: 2 (:476-482) never runs.
  • One review executes at a time, process-wide. The queue is a single-reader channel whose reader awaits RunAsync inline (ReviewJobs.cs:391-395). MaxConcurrency would only ever have governed files within a run.

08What could not be measured, and why

The task asked for a review-run latency breakdown separating model calls from parsing and rendering. That breakdown cannot be produced from the current build, and the reason is structural rather than environmental.

The review path emits no phase telemetry

There is no qs.* event, no Server-Timing header, no ActivitySource and no Meter anywhere in the review path. Two scalars exist: ReviewQueued (ReviewJobs.cs:215-218) covers the whole enqueue, and ReviewCompleted (:501-503) covers the whole run. A third, ReviewRunner.cs:217, fuses the model call, parsing, a second subject re-hash, a third file read, finding-identity merging and the sidecar write into a single number. The only model-isolated signal is UsageRecorded.durationMs, and it is reported by the CLI rather than bracketed as a phase boundary.

On top of that, the model phase did not execute here. Both queued runs reached state: running and stayed there with usageOperations: 0 and usage.durationMs: 0 — the same behaviour the 2026-08-18 session recorded as finding N-01. What the measurement can bound:

PhaseStatusEvidence

Deterministic sensor sweepmeasured§06 — 0.06 s to > 600 s per sensor per scan

Slice P-5 below closes this gap by mirroring the pattern that already works: qs.repository.switch.backend emits a phases object and a Server-Timing header, and that is precisely why cost block 2 could be attributed to the scan in one request.

09Options and recommendation

Three coherent responses exist to the switch-latency breach. They are not mutually exclusive, but they differ sharply in cost and in what they concede.

Option A — Widen the budget

Raise the click-to-usable contract from 500 ms to, say, 1,500 ms and record agent-taskboard's 664.89 ms as passing.

Cost: nothing. Concedes: the contract stops being a contract. The p95 of 1,395.78 ms would still sit at the new ceiling, and the number grows with every repository the operator onboards. It also leaves the 33.87 MiB transfer and the browser-side retention untouched.

Not recommended. The budget is not the thing that is wrong.

Option B — Extend the QS-54 pattern to the tree

Give /api/tree what /api/project already has: a projection cache keyed by Git state, a Server-Timing header, and a qs.* event. Warm it in the prewarmer alongside the dashboard.

Cost: moderate, and it mirrors an accepted design. Limit: caching a 33.87 MiB response does not make it smaller. Serialisation and transfer remain; the win is bounded by whatever fraction of the 659.10 ms is projection rather than serialisation, and that fraction is currently unmeasured because the endpoint has no phase telemetry.

Necessary but not sufficient on its own.

Option C — Send less recommended

Use the conditional request the endpoint already implements, remove the adapter duplication, and stop shipping subtrees the client cannot render.

Cost: the first step is a handful of lines in loadTree. Evidence: 304 in 38.11 ms with 0 bytes, measured; 6.1× file-node amplification, measured; a 40-row render window, documented. Every step has a number attached before it is built.

Recommended, sequenced as P-1 → P-2 → P-3 so each step is independently verifiable.

On cost block 2 there is no real option

A snapshot that is invalidated by the product's own writes and never re-warmed will keep charging the operator the full rebuild. The only question is whether the rebuild is moved off the request (re-warm on invalidation) or made cheaper (single-pass build), and the answer is both — P-4 first, because it is smaller and its effect is the 16.1-second number.

Recommendation

Approve P-1 through P-5 as a single wave, in order. P-1 and P-4 are small and carry the largest measured deltas; P-2 and P-3 remove the cause rather than caching the symptom; P-5 is the prerequisite for ever answering the review-latency question that prompted this dossier. P-6 is hygiene and can be deferred without risk. The one thing that should not be deferred is P-5: until the review path emits phases, every future review-performance claim will be as unfalsifiable as the ones this dossier had to leave open in §08.

10Implementation slice plan

Each slice states its before-value from this dossier, the change, and an exit criterion the committed harnesses can check.

P-1 · Take the conditional path on the tree Approve now · smallest change, largest measured delta

  • Before: repeat warm switch to agent-taskboard = 659.10 ms of tree time and 35,519,812 bytes. Conditional request on the same snapshot = 38.11 ms and 0 bytes.
  • Change: QualityApi.loadTree (quality-api.ts:514-530) already retains the previous tree per repository in treeSnapshots. Retain its ETag alongside it, send If-None-Match, and on 304 reuse the snapshot and mark the transition complete. Do the same for loadProjectDashboard, whose ETag is equally unused.
  • Watch out: the ETag covers Git state, the requested path and the coverage timestamp (Program.cs:412-413), so a 304 is only safe for an identical path parameter. Key the retained tag by (repositoryId, path).
  • Exit: a second switch to an unchanged repository completes within 100 ms of backend time and transfers zero tree bytes; tree-payload-perf.mjs reports the 304 on the client path, not only on the probe.

P-2 · Emit each file once Approve now

  • Before: 15,961 file nodes for 2,596 distinct paths on agent-taskboard; frontend/src/dev-mode.ts emitted 12 times. Quality Studio shows 0 duplicates, so this is specific to multi-project workspaces.
  • Change: in RepositoryHierarchyBuilder.Build (RepositoryHierarchyAdapters.cs:20-46), assign each repository file to exactly one owning module — most-specific project directory wins — instead of letting every discovered Angular project claim shared sources.
  • Watch out: node ids are content-addressed (RepositoryHierarchyBuilder.cs:193-198) and appear in persisted review metadata and finding state. Changing which module owns a file changes its id. The slice must include a compatibility check against existing .quality/reviews sidecars, or the ids must be made ownership-independent first.
  • Exit: filePathsEmittedMoreThanOnce is 0 for both targets; total nodes on agent-taskboard drop from 34,809; no existing review sidecar loses its anchor.

P-3 · Bound what the tree returns Approve with P-2

  • Before: 33.87 MiB delivered to a view that renders a 40-row window; a single-module subtree is already 344.27 ms and 7,038,002 bytes, so today even the narrow request is not cheap.
  • Change: return roots plus one level by default and let the client request children per expanded path, or accept a depth parameter. The client's flattening and overscan logic is unchanged; only the fetch boundary moves.
  • Watch out: explorer.ts auto-expands ancestors of the selected path, so the contract must let the client ask for a path's ancestor chain in one request or the change trades bytes for round trips.
  • Exit: first tree response for agent-taskboard is under 1 MiB; the warm critical path fits the existing 500 ms contract on the 5,116-file target with margin; tree expand stays under the 50 ms budget in frontend/PERF.md.

P-4 · Re-warm on invalidation Approve now · owns the 16-second number

  • Before: an 81.95 ms sensor scan made the next dashboard request cost 16,143.72 ms; the request after it cost 32.46 ms. Ordinary editing costs 915.04 ms median on a 349-file repository.
  • Change: re-queue a repository in RepositorySnapshotPrewarmer whenever the product itself writes into it — after a sensor scan that persists, after a review run publishes its sidecar — and debounce. The prewarmer already exists, is already off the request path, and already emits qs.repository.prewarm; only the trigger set is missing.
  • Watch out: do not re-warm on every filesystem event, or a repository under active editing will rebuild continuously; debounce and coalesce, and keep the existing dedupe key (RepositorySnapshotPrewarmer.cs:43-46).
  • Exit: the sensor-invalidation measurement shows the first request after a scan within 2× of the warm value on both targets; qs.repository.prewarm is emitted after a persisting scan.

P-5 · Give the review path the phases the switch path already has Approve now · prerequisite

  • Before: two scalars for the whole review; the model call, parsing, re-hash, re-read and sidecar write are fused into one number (ReviewRunner.cs:217). The breakdown this dossier was asked for is unavailable.
  • Change: emit qs.review.run.phases with the same shape as qs.repository.switch.backend (Program.cs:476-491): enqueueMs, sensorSweepMs, promptMs, modelMs, parseMs, persistMs, reportMs. Bracket the model call in ReviewAgent.RunAsync explicitly rather than inferring it from CLI-reported usage.
  • And, in the same slice, stop doing the preflight in the request: the estimate is 198,976.86 ms for a 1,215-file module and is not cached. Either return an estimate computed from the already-built hierarchy without rendering prompts, or move prompt rendering behind the queue and let the client poll.
  • Watch out: the estimate feeds the token and cost caps, so a cheaper estimate must stay conservative in the same direction; document the new method string in the estimate.method field the API already returns.
  • Exit: a completed review run emits one event whose phases sum to the run duration; POST /api/review/estimate on a 1,215-file module returns in under 2 s.

P-6 · Hygiene Defer if capacity is short

  • Single-pass hierarchy build: read each source file once and evaluate the scope decision once (RepositoryHierarchyBuilder.cs:88,96,108,167-171). The scan is 20,774 ms of agent-taskboard's 23,764 ms cold prewarm, so this is the largest remaining lever after P-2 — it is listed here only because P-1 through P-5 have better evidence-to-effort ratios.
  • Bound ProjectDashboardService.cache (ProjectDashboard.cs:105) to the current Git state per repository, matching what RepositoryHierarchyCache already does correctly.
  • Evict terminal entries from ReviewJobService.runs and release ReviewMetaIndex watchers for archived repositories.
  • Drop retained browser snapshots for repositories that are archived or removed (quality-api.ts:436-437,502).
  • Reconcile ReviewJobs:MaxConcurrency with DefaultReviewTokenCap: today the shipped cap makes the concurrency setting unreachable. Either make the sequential branch conditional on the cap actually binding, or remove the setting so the configuration does not promise something it cannot deliver.
  • The frontend initial bundle is 478.30 kB against a 480 kB error budget. Not a latency problem, but the next component added to the initial chunk fails the production build.

Limitations. One host, one CPU, one run per configuration except where a sample count is given; medians of 5 to 7 samples are reported, not confidence intervals. Both repositories were measured as fresh clones, so their working trees were clean at the start — a repository with many dirty files pays more in ComputeGitState than measured here. The model phase of a review run did not execute in this environment, so §06 covers everything the review path does around the model and nothing about the model itself; the parsing and rendering costs in §08 are bounded by code inspection rather than measured. Browser-side interaction budgets were not re-measured — frontend/PERF.md remains the reference — and the 33.87 MiB tree payload's cost inside Angular is therefore an unmeasured addition on top of the backend numbers in §02, not part of them. The expected gains in §10 are stated as exit criteria to be verified by the committed harnesses, not as predictions.
