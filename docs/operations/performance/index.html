01The measurable result

Two of the five requested measurements already exist as real, current-code-verified numbers (project switch, and the file-size dimension of large-repo behavior). Three do not exist anywhere in the repository today — process startup, a phase split for review-run latency, and any memory-growth measurement — and this dossier does not invent numbers for them. Instead it reports the structural evidence (code paths, cache classes, instrumentation gaps) that explains why they are unmeasured and what the cheapest next measurement would be.

The honest scope of “before-values”

Every millisecond figure below is either quoted from PERF.md / frontend/PERF.md (both re-verified against the current commit) or newly derived by reading the instrumentation code that produces those figures. Where no instrumentation exists, the section says so explicitly instead of estimating a number that nobody measured.

02Startup cost

Status: unmeasured. No timing evidence exists for API cold start, DI container build, or the Angular bundle's initial load.

Nothing in PERF.md, frontend/PERF.md, docs/, or scripts/ times process startup, DI graph construction, or the Angular bootstrap path (verified by grep across all four locations). The one relevant fact in the code is a design decision, not a measurement: the QS-54 prewarmer is explicitly built to avoid adding to startup latency — RepositorySnapshotPrewarmer.ExecuteAsync opens with await Task.Yield() before touching any repository, with the comment “Keep host startup non-blocking: the API becomes reachable while snapshots warm in the background” (src/QualityStudio.Api/RepositorySnapshotPrewarmer.cs:51). That is good design intent, but it is not evidence that startup is fast — only that the largest known per-repository cost (hierarchy scan) was deliberately kept off the startup critical path.

Frontend bundle budgets are enforced (350 KB warning / 480 KB error, per frontend/PERF.md:68), which bounds bytes shipped but was never converted into a bootstrap-time measurement in the existing Playwright harness.

What QS-54 did not close

Prewarm moves the cold cost off the operator's click, it does not remove the cold cost. The prewarm queue is a single-reader Channel (RepositorySnapshotPrewarmer.cs:12–13): registrations are warmed one at a time, so total time-to-fully-warm for N large repositories still scales linearly, and it is currently invisible — only a per-repository qs.repository.prewarm event exists, not an aggregate “queue drained after Xms for N repos” signal. A repository that changes Git state after its initial warm (a new commit, a branch switch) re-pays the same cold cost on the next request that observes the new state, because the cache keys on GitState (RepositoryHierarchyCache.cs:44–52) — this is correct invalidation, but it means “warm” is a moving target on active repositories, not a one-time cost.

04Review-run latency breakdown

Status: the model-call / parsing / rendering split the mandate asked for does not exist in the code. Only two coarser numbers are instrumented, and neither is currently populated with real data on this host.

A review run (ReviewJobs.RunAsync) wraps a single Stopwatch around the entire run — deterministic-sensor collection, every per-file model call, and the aggregate rollup — and logs one total on completion: “Completed review {ReviewRunId} ... in {ElapsedMilliseconds} ms” (src/QualityStudio.Api/ReviewJobs.cs:448 starts the timer, :501–503 logs it). A second, coarser number — usage.DurationMs — is self-reported by the CLI subprocess per operation and persisted to the monthly usage ledger (ReviewJobs.cs:864; ledger format in docs/usage-telemetry.md). Neither splits model-call time from our own response-parsing or finding-persistence time; there is no Stopwatch anywhere inside RunFileAsync or around the parse/persist step.

One structural cost driver is visible without new instrumentation: per-file reviews run through Parallel.ForEachAsync with MaxDegreeOfParallelism = Math.Clamp(options.MaxConcurrency, 1, 16), and MaxConcurrency defaults to 2 (ReviewJobs.cs:118, used at :479). A module-level review of, say, 24 files runs effectively 12-deep even before any single file's latency is known — so total run time is bounded below by fileCount / 2 × (single-file latency) regardless of where that single-file latency goes.

No completed run exists on this host to measure end-to-end, either

The sibling quality concept dossier (2026-08-18 session) found that all seven review runs dispatched on this host that day completed with 0 operations, 0 findings, 0 tokens — the review path itself did not return (docs/operations/quality-concept/index.html, finding N-01 in the companion security dossier). The review-runs-*.json evidence files under that dossier's results/ show every file entry as “state”: “cancelled” with startedAt: null. This dossier cannot report a real review-run latency number, phase-split or not, until that operational gap closes — reporting one would mean fabricating it.

05Memory growth over long sessions

Status: no measurement exists, but the code shows unbounded growth by construction — this is a structural finding, not a benchmarked number.

Both caches introduced for QS-54 are process-lifetime ConcurrentDictionarys with no eviction path:

  • RepositoryHierarchyCache.slots — ConcurrentDictionary<string, CacheSlot> keyed by repository root, populated via GetOrAdd (src/AgentOrchestrator.CodeQuality/RepositoryHierarchyCache.cs:25,47). Each slot holds a full immutable hierarchy snapshot for that repository's current Git state.
  • ProjectDashboardService.cache — the same pattern, keyed on root + GitState (src/QualityStudio.Api/ProjectDashboard.cs:105,117–118), holding a full dashboard projection.

Neither class contains TryRemove, Clear, a TTL, IMemoryCache, or a size limit anywhere (grepped both files; zero matches). Archiving a repository only sets a soft Archived = true flag on the registry entry (src/QualityStudio.Api/RepositoryRegistry.cs:163) — nothing notifies either cache, so an archived repository's snapshot and dashboard projection stay resident for the rest of the process lifetime. Growth is bounded by the number of distinct (repositoryRoot, GitState) pairs ever observed, not by the number of currently-registered repositories. On a long-lived host that cycles through many repositories, or one repository churning through many commits under active development, each new Git state adds a new resident entry that is never reclaimed.

No existing test or harness exercises this path — there is no long-session or many-repository soak test in tests/ to attach a real growth-rate number to. That gap is itself part of slice 2 below.

Extrapolation, not a measurement

Scaling agent-taskboard's 2.40 ms/file linearly to a hypothetical 10,000-file repository projects to roughly 24 seconds of cold scan time (and proportionally longer if directory depth grows faster than file count, which the flat-fixture comparison above suggests it does). No repository this large has ever been measured, and no timeout, pagination, or degradation code exists anywhere in RepositoryHierarchyCache or the hierarchy builder (grepped for “timeout”, “pagination”, bounded .Take( calls — zero matches). A 24-second cold prewarm is tolerable today only because QS-54 keeps it off the operator's request path; it is not tolerable if it also blocks every other queued repository behind it in the single-reader prewarm queue (see §03).

08Options and recommendation

For cost block 1 — review-run phase visibility

OptionEffortTrade-off
A. Do nothing until operational runs return (blocked on the security concept's M-1)noneKeeps the black box; every future review-latency decision stays a guess even after M-1 lands, because the instrumentation still won't exist.
B. Add phase-level Stopwatchs now, independent of M-1 (recommended)smallAdditive only — mirrors the existing qs.repository.switch.backend/qs.repository.prewarm pattern already shipped for QS-54, so it's a proven shape, not a new convention. Produces real data the moment M-1 lets any run complete.
C. Rebuild the review pipeline around a tracing library (OpenTelemetry spans)largeRight long-term shape, but far more than this gap needs; defer until phase counts prove worth the investment.

For cost block 2 — cache growth

OptionEffortTrade-off
A. Generic LRU / IMemoryCache with a size cap on both cachesmediumGeneral fix, but risks evicting a hot, actively-switched repository's snapshot under memory pressure — reintroducing the cold-path cost QS-54 just removed.
B. Evict on archival, leave the active-repo case unbounded (recommended)smallMatches the actual risk: the registry already tracks archival as a lifecycle event (RepositoryRegistry.cs:163); wiring the existing event to TryRemove on both caches removes the only currently-reachable unbounded-growth path (repeated archive/re-register cycles) without touching the hot path.
C. Ignore until a soak test shows real growthnoneDefensible short-term given no measured harm yet, but leaves a known-unbounded structure with zero alarm if usage patterns change.

For cost block 3 — prewarm queue at scale

OptionEffortTrade-off
A. Parallelize the prewarm queue (multiple readers)mediumShortens total warm-up time but multiplies concurrent cold-scan I/O load; needs a concurrency cap to avoid starving the API's own request handling during startup.
B. Do this before deciding whether A is even needed.

09Implementation slice plan

Slice 1 — Review-run phase instrumentation (cost block 1, option B)

Add Stopwatchs around three existing phases inside ReviewJobs.RunAsync / RunFileAsync: deterministic-evidence collection (already a separate call, ReviewJobs.cs:456–464), the per-file model call (CreateRunner(item).ReviewIfNeededAsync, :534), and result persistence/aggregation. Emit a new qs.review.run.phase structured log event per file, matching the JSON shape already used for qs.repository.prewarm. No behavior change, no new dependency. first slice — unblocks measurement of everything else on this path

Slice 2 — Evict caches on repository archival (cost block 2, option B)

Give RepositoryHierarchyCache and ProjectDashboardService an Evict(string repositoryRoot) method and call it from RepositoryRegistry's existing archive path (RepositoryRegistry.cs:163), right after the Archived = true write. Bounded blast radius: only fires on an explicit operator action that already exists.

Slice 3 — Aggregate prewarm-queue signal (cost block 3, option B)

Track queue depth and cumulative duration across RepositorySnapshotPrewarmer.ExecuteAsync's processing loop and log one qs.repository.prewarm.queue-drained event ({queuedCount, totalDurationMs, largestSingleMs}) when the channel empties. Turns §06's extrapolation into a real number the next time a realistically large repository set is registered, and is the evidence needed before deciding whether queue parallelization (option A) is worth its concurrency risk.

All three slices are additive-only (new events, new eviction call, no removed behavior), each independently shippable, and none touches the QS-54 prewarm/cache design that is already verified working. Recommended order is 1 → 2 → 3: slice 1 has the highest leverage (unblocks the core product's cost visibility) and the lowest risk (pure logging).
