Architecture and implementation dossier · QS-91

Quality analysis is an in-process library

The first package slice turns the existing Quality Studio kernel into a publishable NuGet boundary with a named-analysis facade. Agent Studio pipelines, the CLI, and CI can call the DLL directly. The Quality Studio API remains an adapter and the Angular UI remains a client of that API.

Status: first slice implemented Evidence cut: 12 August 2026 Source baseline: 59941d8 Publication: not performed
Decision Use AgentOrchestrator.CodeQuality as the in-process analysis package. Do not route repository analysis through the Quality Studio HTTP API. Keep the package in this repository for now; reconsider repository extraction only when the release, compatibility, and public-source criteria in section 07 are met.

Where HTTP concerns leaked

The actionable leak was AgentStudioTaskClient: it used HttpClient, knew Agent Studio URLs and headers, serialized task API payloads, and performed project discovery from inside the package. It now lives in QualityStudio.Api, with its tests alongside the API tests.

The core still uses HttpClient only for analysis-owned Gitleaks tool provisioning, and System.Net.WebUtility only for report encoding. Those are library implementation details, not an API-host dependency. An assembly-boundary test proves that the core has no Microsoft.AspNetCore* reference and no Agent Studio HTTP client type.

03 · Stable programmatic surface

QualityAnalysisCore is the public facade. A caller supplies an absolute or relative repository path, one or more stable analysis names, per-analysis string configuration, optional repository/path scope, and an explicit write policy. The result contains one named result per request plus a flattened ReviewFinding list.

var result = await QualityAnalysisCore.CreateDefault().RunAsync(
    new QualityAnalysisRequest(
        repositoryPath,
        [new NamedQualityAnalysis(QualityAnalysisNames.Boundaries)]));

foreach (ReviewFinding finding in result.Findings)
    Consume(finding);

PersistArtifacts defaults to false. This keeps pipeline and CI calls read-only unless the hosting backend intentionally requests repository-owned .quality output. The package never performs Git commits, pushes, merges, or worktree management.

The default registry exposes boundaries, coverage, dependencies, eslint, gitleaks, roslyn, sarif, and tsc. Tool absence is returned as availability/provenance rather than translated to an HTTP status.

05 · QS-90 rule-library boundary

QS-90 is content, not the execution engine. The desired dependency is one way: a host selects and version-pins an immutable rule-library snapshot, then supplies its resolved content/configuration to the core. The core records rule identity and provenance while remaining agnostic to catalogue discovery, marketplace installation, or UI editing.

  • The first-slice package has no QS-90 package reference.
  • Repository and global review inputs remain caller-supplied content; named deterministic analyses accept per-analysis configuration.
  • The existing four-entry Guidelines UI starter catalogue moved from the core into the API as a compatibility adapter, so it is not shipped as analysis-core policy.
  • Versioned execution prompts and the attack/model protocol snapshots remain in the core because they define current executor behavior. They should not become a general-purpose rules marketplace.

07 · Operator question 2: extract the core repository?

Recommendation: do not extract now.The package boundary creates the necessary decoupling without immediately adding a repository, feed, release, and coordinated-version boundary. Extraction remains an operator decision after the criteria below are observable.
CriterionKeep in this repository nowEvidence that would support extraction
Release cadence couplingThe facade, finding contracts, sensors, API adapters, and CLI are still stabilizing together. One repository gives atomic contract/refactor tests.Core releases on a materially different cadence for at least two release cycles, and most core changes no longer require API/CLI changes.
Cross-repo versioning versus the 0-PR pipelineA separate repository would require publish-before-consume ordering, feed/bootstrap availability, dependency update PRs or an exception to the 0-PR flow, and cross-repository compatibility tests.Agent Studio can consume pinned packages without adding PR/manual coordination, supports rollback and compatibility matrices, and has an accepted pre-release promotion path.
Public-repository policyThe current repository is Apache-2.0 and already contains prompts, sensors, and contracts, but package namespace ownership and the policy for future QS-90 content have not been reconfirmed for extraction.The operator approves what code/rule content may be public, NuGet organization and ID-prefix ownership are confirmed, maintainers and disclosure/security handling are assigned.
Consumer pressureKnown consumers are first-party and can use a package built from this repository.Two or more independently released consumers need a supported SemVer contract and cannot reasonably track this repository.
Operational ownershipOne CI can test core, CLI, and API together and retain the package without publishing it.A separate owner accepts release automation, vulnerability response, deprecation policy, compatibility CI, documentation, and feed availability.

If the criteria are met, extraction should preserve history, begin from a tagged package contract, and leave package-based consumers in this repository. Until then, a physical repository split would create coordination cost without improving the runtime or security boundary.
