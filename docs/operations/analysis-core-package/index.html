Analysis-core package split for Quality Studio

The operator's 2026-08-12 architecture directive asks Agent Studio to consume Quality Studio analysis as an in-process library, not the HTTP API. This dossier inventories what already exists, packages it, proves in-process consumption with a standalone prototype, and answers the operator's two questions - is the core useful without the UI, and should it move to its own repository.

01Current-state inventory

The good news first: the split the directive asks for is largely already there. AgentOrchestrator.CodeQuality already has no ASP.NET or hosting dependency, and every consumer in this solution already reaches it in-process.

One boundary detail is worth naming precisely rather than glossing over: AgentStudioTaskClient.cs lives inside the core project and wraps System.Net.Http.Json to push a finding-derived task card to Agent Studio's own /api/tasks endpoint - the "handover" feature the root README already documents as a decided, separate integration direction (Quality Studio calls Agent Studio, not the other way round). It is wired up and invoked only from QualityStudio.Api/Program.cs. This does not block packaging - it is base-class-library HttpClient usage, not an ASP.NET dependency, and the API project keeps working unchanged either way - but every consumer of the packaged library today would receive this HTTP-push-shaped type whether or not it needs it. Recommendation: leave it in place for slice 1; consider relocating it to the API layer in a follow-up slice, since conceptually it is a delivery concern, not an analysis concern.

02Target split

Given the inventory, the target split is a formalization, not a rewrite:

  • Analysis core (AgentOrchestrator.CodeQuality, now packable as a NuGet package): the stable programmatic surface is QualityReportBuilder.BuildAsync(IReadOnlyList<QualityReportRepository>) - run named analyses (sensors + optional agent review kinds) over a repo path and a small config record, get back QualityReportDocument with the shared QualityFinding model. No web dependency, already proven true by the inventory above.
  • HTTP API / UI hosting (QualityStudio.Api): unchanged. Keeps repository registry, path confinement, review-run orchestration, and the Agent Studio task-handover push. It is a caller of the core, exactly as it already is.
  • CLI (quality, quality-cli): unchanged. Already the reference example of "consume the core in-process, no server needed."
  • Rule library (QS-90): content the core consumes (guideline catalogues, installed per repository), not a layer with its own hosting concerns. It stays inside the core's boundary - a caller passing a repo path already gets whatever guidelines are installed there.

What did not need to change

No project moved, no namespace moved, no consumer's code changed. The csproj that was already the hub of the star topology gained packaging metadata (IsPackable, PackageId, PackageReadmeFile) and a README; nothing else in src/ was touched except the one place that proves the package works (section 05).

03Question 1 — is the core useful without the UI studio?

Yes - and it already is, today, inside this repository

Three concrete standalone consumers, none of which touch QualityStudio.Api:

ConsumerStandalone today?What the package must include for it

Agent Studio pipeline step (AGT-2655), a different repositoryproven by prototype, not yet realA published feed reachable from Agent Studio's own restore (today: nothing beyond nuget.org is configured anywhere in this repo, so real use needs either a public NuGet.org publish or a private feed both repos can reach); an explicit, pinned version (the core is pre-1.0 - surface may still move); the QualityFinding/QualityReportDocument contract kept stable across patch releases; and the caller passing a real git-repository root, not an arbitrary subfolder - the prototype run in section 05 hit exactly this rough edge (QualityReportBuilder's trend loader shells out to git log assuming root is the repository's top level).

So the operator's expectation is confirmed with names attached, not asserted: the core is not merely theoretically separable, it is already exercised standalone by CI on every push, and quality-cli is a production example of "in-process, no UI, no server." The only genuinely new consumer is the external one (AGT-2655), and slice 1 (section 05) proves that path works mechanically without requiring the "findings reach the QS UI later, not live" tradeoff the directive explicitly accepts to be exercised for real - that tradeoff only matters once the API's own review-run pipeline is the one being bypassed, which is Agent Studio's call to make on its own schedule.

04Question 2 — do we extract the core into its own repository?

Not now. Publish from this repository first; extract only if a concrete trigger fires.

CriterionWhat it says today
Release cadence couplingCore, API, CLI, and UI still ship together from one repo (root README.md: "no package published to NuGet yet", cards through QS-52 all landed here). Nothing today asks the core to release on a different cadence than its in-repo consumers.
Cross-repo versioning cost vs. the 0-PR pipelineToday a core change and its API/CLI consumer change land in one PR, in this repo. Extracting turns every core change into: a PR in the new core repo, a publish, then a version-bump PR here for the API/CLI and a version-bump PR in Agent Studio. That reintroduces exactly the kind of cross-repo coordination overhead the operator's own directive is trying to remove by choosing "in-process library" over "HTTP API" - it would be strictly better than the HTTP round trip, but not free, and not yet earned by more than one external consumer.
Public-repo policyquality-studio is already public (Apache-2.0, github.com/agent-orc/quality-studio, public website). A second public repository means new ownership, CI, issue tracking, and security-review sign-off for a package that has exactly one external consumer candidate today. build.yml already has a tag trigger (tags: ['v*.*.*']) that a future "publish on tag" step can hang off without a new repository at all.

Concrete triggers to revisit

  • The core needs a release cadence genuinely independent of the API/UI (e.g. AGT-2655 needs a fix faster than the next UI release, repeatedly).
  • More than one external, differently-owned repository depends on the package.
  • The core's own CI time or code ownership starts to conflict with API/UI iteration speed inside this repo.

None of the three holds today. The recommendation is to wire package publishing into this repository's existing tag-triggered build once the operator wants a real (not local-feed) release, and to leave the repository question open until one of the triggers above actually fires.

Limitations. The prototype proves the packaging and in-process mechanics, not a real cross-repository dependency - it consumes a local folder feed, not a published one, and lives inside this repository rather than in Agent Studio's. It also surfaced (rather than fixed) a genuine rough edge: QualityReportBuilder currently requires its root to be a git repository's top level, which any external caller passing an arbitrary subdirectory will hit; that is a pre-existing behavior of the core, unrelated to packaging, and is called out in section 03 rather than silently patched here. The extraction recommendation in section 04 is a decision aid, not a decision - the operator record says that choice stays open.
