QS-91 · architecture and first delivery slice · 27 August 2026

Quality analysis belongs in the server process

Agent Studio should reference Quality Studio analysis as a library, run it over the repository already present on the server, and receive Quality Studio findings directly. The API remains a UI host and remote product boundary; it is not the pipeline integration boundary.

Inventory Target split Standalone value Repository decision First slice Evidence

Decision at a glance

Use the DLL in process. Agent Studio pipeline steps call IQualityAnalysisRunner; they do not call Quality Studio over HTTP. Findings can be imported into the Quality Studio UI asynchronously later.
Do not extract a repository now. Package and release boundaries are established in this repository first. Extraction remains an operator decision after the criteria below show a durable benefit.

HTTP-only concern found and resolved

AgentStudioTaskClient, its HTTP DTOs/options, and its tests lived in the core even though only QualityStudio.Api used them. They now live in the API project. This removes outbound task-handover HTTP and Agent Studio project discovery from the package surface while leaving API behavior and routes unchanged.

Portable operations that stay in the core

Filesystem reads, repository-relative path checks, Git inspection, analyzer subprocess execution, and optional pinned-tool acquisition are analysis implementation concerns, not ASP.NET hosting concerns. They stay behind library APIs. The package does not perform Git commits, pushes, merges, or worktree management.

The dependency direction is callers → core. The API also references the core as a host. The browser references only the API. Agent Studio does not need an API round trip to analyze a repository already mounted in its server process.

Stable programmatic surface

IQualityAnalysisRunner.RunAsync(
    QualityAnalysisRequest(repositoryPath, namedAnalyses, scope, path, persistMetadata))
    → QualityAnalysisResult
      → analyses[]: availability + provenance + ReviewFinding[]
      → findings: flattened Quality Studio ReviewFinding[]

Analysis names are explicit and case-insensitive. Each selection owns its configuration dictionary. Unknown names, duplicate selections, missing repositories, and unsupported scopes fail explicitly. Tool absence is returned as an unavailable analysis, never as a false pass.

QS-90 rule-library boundary

The rule library is versioned content consumed by analysis/review code. It must not reference the API, UI, repository registry, or pipeline host. Repository/global inputs and analysis configuration remain neutral core contracts. A rule-library adapter may materialize those inputs or provide a sensor, but the core package must not depend on the rule publisher. This keeps rule cadence and engine cadence separable.

3. Operator question 1: useful without the UI?

Yes. The UI is an inspection and authoring surface, not a prerequisite for analysis.

The package therefore includes the finding/review contracts, named orchestration, built-in sensors, provenance/availability, hierarchy and input primitives, and embedded prompts/catalogues needed by its runners. It excludes HTTP routes, authentication, UI DTOs, hosted job services, repository registration, and Agent Studio task handover.

4. Operator question 2: extract the repository?

Recommendation: no extraction now. Publishable packaging provides the integration boundary without immediately paying a cross-repository coordination tax.
CriterionKeep together while…Extraction signal
Release cadence couplingCore, API, CLI, schemas, and rule consumption change together and need atomic tests.The core has an independently supportable cadence and Quality Studio regularly consumes older/newer compatible versions.
Cross-repo versioning versus 0-PR pipelineOne change can update core, caller, tests, docs, and package proof in a single branch/PR.Independent ownership outweighs dependency-update PRs, compatibility matrices, feed promotion, and rollback coordination.
Public-repository policyPackage and source share the same visibility, licensing, disclosure, and release controls.Operator policy explicitly requires a distinct public/private boundary and approves the resulting source, security, and release process.
Consumer diversityPrimary consumers remain Quality Studio, its CLIs, Agent Studio, and the same CI estate.Multiple independently governed products require the core without Quality Studio release coupling.

Revisit extraction only after these signals are measured. If approved later, first establish package compatibility tests and automated feed promotion, then move history without changing the public API in the same operation.
