Decision dossier · QS-91 · 26 August 2026

Quality analysis runs as an in-process library

The first package slice turns the existing analysis project into a publishable, host-neutral NuGet package, proves one real CLI caller, and removes an HTTP integration concern from the core. The API and UI remain separate hosts and retain their current behavior.

Status: first slice implemented Package: AgentOrchestrator.CodeQuality 0.1.0-preview.2 Repository decision: no extraction now

Directive implemented. Agent Studio pipeline integration should reference the package DLL and call AnalysisRunner.RunAsync against the already-mounted repository. It should not call Quality Studio over HTTP. Findings may be imported into the Quality Studio UI later through a separate persistence/synchronization step.

HTTP leakage found and resolved

AgentStudioTaskClient, its target options, and its Agent Studio request/response DTOs lived in the analysis project even though only the API host used them. They now live in QualityStudio.Api, and their tests moved to the API test project. This removes product-to-product HTTP integration from the NuGet surface.

The core still uses HttpClient inside the Gitleaks resolver/scanner to acquire the pinned external analyzer. That is analyzer runtime infrastructure, not Quality Studio HTTP transport or UI hosting. It remains injectable and is only activated when that named analyzer is selected.

2. Target split

Analysis core

Stable CLR contracts, named-analysis orchestration, QS ReviewFinding, hierarchy and review services, analyzers, provenance, and extension points. No ASP.NET, repository registry, hosted worker, or UI.

HTTP API

Authentication, request validation, route contracts, repository registration, job lifecycle, persistence, external HTTP adapters, and projection of core results.

UI host

Angular product surface and API client behavior. It visualizes persisted or API-projected findings and need not be present when analysis runs.

Stable programmatic surface

var result = await new AnalysisRunner().RunAsync(new AnalysisRequest(
    repositoryPath,
    [AnalysisNames.Boundaries, AnalysisNames.Dependencies],
    new AnalysisConfiguration { PersistArtifacts = false }));

IReadOnlyList<ReviewFinding> findings = result.Findings;

The request identifies a local repository, one or more named analyses, scope, optional per-analysis settings, and whether repository artifacts may be persisted. Each execution returns availability, QS findings, tool provenance, and optional rule-set identity. Library callers default to no artifact writes.

Rule library boundary (QS-90)

The core does not reference or package a QS-90 rule-library implementation. Rule content enters through IAnalysisRuleProvider as a versioned AnalysisRuleSet; one-run settings can override it. This allows rules to evolve and be distributed independently without placing storage, registry, UI, or HTTP concerns in the core. Existing embedded review prompts and analyzer catalog snapshots remain implementation resources, not the external rule library.

3. Operator question 1: useful without the UI?

Yes. The UI is a later inspection and workflow surface, not a prerequisite for producing findings.

The package therefore includes orchestration, canonical findings and review contracts, analyzer interfaces and built-ins, hierarchy/staleness support, provenance, configuration inputs, and agent-review adapters. It deliberately excludes API auth/routes, UI assets, host lifecycle, Git workspace mutation, and result synchronization policy.

4. Operator question 2: extract to another repository?

Recommendation: do not extract now. Publish and consume the package from this repository first. Extraction is a separate operator decision after the library boundary has real consumers and release evidence.
