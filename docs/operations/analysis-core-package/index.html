Decision dossier · QS-91 · 26 August 2026

Quality analysis as an in-process package

Agent Studio should call Quality Studio analysis as a server-side DLL. The repository already contains a capable analysis library; this slice gives it a stable package surface, removes host-only HTTP integration from it, and proves consumption through the real CLI.

Status first slice implemented Package QualityStudio.Analysis.Core 0.1.0 Proof caller quality-cli Repository extraction not performed

Decision implemented. Keep analysis in-process. Keep the core project in this repository for now. The UI and HTTP API remain hosts around the library, not prerequisites for analysis.

HTTP leakage assessment

  • Removed: AgentStudioTaskClient, its endpoint DTOs, and options belonged to API integration. Moving them to the API preserves endpoint behavior while keeping them out of the package.
  • Retained deliberately: Gitleaks uses HttpClient only to resolve a pinned analyzer binary when the host has not supplied one. That is tool acquisition inside an analyzer, not Quality Studio API transport. Hosts can provide a local executable and avoid download.
  • Not a dependency: the boundary sensor recognizes ASP.NET and HttpClient syntax in repository source. These are strings and parsing rules, not web-framework references.
  • Verified package boundary: the core assembly has no Microsoft.AspNetCore.* reference; a test protects this invariant.

2. Target split

Standalone hosts skip the first two boxes and reference the DLL directly. Dependency direction is always inward: hosts depend on core contracts; the core never depends on hosting concerns.

Stable programmatic surface

ContractPurpose

QualityAnalysisResultCombined Quality Studio ReviewFinding values plus per-analysis availability and provenance.
ListAnalyses()Discovers names, versions, and supported scopes without an HTTP catalogue endpoint.

The first-party set is boundaries, coverage, dependencies, eslint, gitleaks, roslyn, sarif, and tsc. Unavailable tools produce explicit unavailable results rather than false passes.

Rule library boundary (QS-90)

The rule library is content consumed by an analysis, not host code and not UI state. A named analysis receives a rule-library path, selection, or version through its configuration dictionary. The core package owns loading/validation contracts when a rule-backed analyzer is added; the rule content remains independently replaceable. No API client, database contract, or authoring UI is introduced into this boundary.

3. Operator question 1: is the core useful without the UI?

Yes. The UI is a later presentation and triage surface. It is not on the execution path for any of the standalone consumers below.

Standalone consumerHow it uses the packagePackage capabilities required
Agent Studio pipeline steps (AGT-2655)Load the DLL in the server-side pipeline, analyze the already-present task checkout, evaluate findings, and attach/upload results later.Named execution, cancellation, deterministic and model-backed analyses, QS findings, provenance, explicit unavailability, configurable no-persist mode.
quality-cliquality analyze <name> [repo] calls QualityAnalysisCore directly and emits JSON for people or automation.Default analyzer catalogue, config forwarding, stable JSON-friendly result models, meaningful exit codes.
CIA test or build host references the package, runs selected checks in the checked-out workspace, and converts severity/availability into its own gate policy.Headless execution, deterministic ordering/deduplication, no web host, no UI assets, no mandatory persistence.

The package must include contracts, the façade, built-in sensors/reviewers, embedded prompts/catalogues, finding models, provenance, cancellation, and local process abstractions. It must exclude HTTP endpoints, authentication, repository registry/authorization, task handover, UI assets, and workspace Git lifecycle. Checkout creation, commits, pushes, and task-worktree handling stay with platform/backend orchestration.

4. Operator question 2: should the core move to its own repository?

Recommendation: do not extract now. Keep a hard project/package boundary in this repository, publish the NuGet artifact, and revisit repository extraction only after usage data shows independent ownership or cadence. Extraction requires a separate operator decision.

CriterionKeep here while…Extract when…
Release cadence couplingCore contracts, API projection, CLI behavior, and QS rule evolution commonly change together.Core releases have a materially independent cadence and compatibility window with named maintainers.
Cross-repo versioning costThe 0-PR pipeline benefits from one atomic change and immediate project references; extra package bumps would create coordination without isolation value.Automated publication, dependency update, compatibility tests, rollback, and provenance make cross-repo upgrades routine.
Public-repository policyPackage source, embedded prompts/catalogues, and dependencies are acceptable under Quality Studio's current public repository and license policy.The package has a separately approved public home, security ownership, disclosure policy, and dependency/license posture.
Consumer pressureAgent Studio and CI can consume a published package from this repository without source ownership.Multiple teams need independent governance, support guarantees, or contributions that the monorepo blocks.

5. Delivered first slice

  1. AgentOrchestrator.CodeQuality.csproj now packs as QualityStudio.Analysis.Core 0.1.0 with license, repository, description, tags, and an English package README.
  2. QualityAnalysisCore provides discovery and multi-analysis in-process execution over a repository path and configuration.
  3. quality-cli is the real proof caller through the new quality analyze command.
  4. The Agent Studio HTTP client and its tests moved to the API host. API routes and the UI-facing contract are unchanged.
  5. Tests cover execution, deduplication, configuration forwarding, first-party discovery, unknown names, and absence of ASP.NET assembly references.
