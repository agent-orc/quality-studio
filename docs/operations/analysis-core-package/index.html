QS-91 · implementation dossier · 12 August 2026

Quality analysis is now an in-process package

The first package slice gives Agent Studio pipelines, the Quality CLI, and CI jobs a direct .NET entry point. The Quality Studio API and Angular UI retain their existing behavior; HTTP is a hosting concern, not the analysis transport.

Decision summary

Use the core without the Studio UI: yes. Publish QualityStudio.Analysis, call it in process, and return the canonical Quality Studio ReviewFinding model.
Extract to another repository: no, not now. Keep source, tests, rule-content integration, API adapters, and package publication in this repository until independent cadence or policy creates a measurable benefit.

The implemented proof is the real quality-cli command quality analyze [path] --analysis <name>. It constructs AnalysisRunner directly. No API endpoint or loopback HTTP call is involved.

Integration-base note

HTTP leakage found and resolved

AgentStudioTaskClient.cs previously lived in the analysis project even though it models and calls Agent Studio HTTP endpoints. The class, its options, and transport DTOs now live in QualityStudio.Api; its four tests moved to the API test project. The analysis package has no ASP.NET dependency and never calls the Quality Studio API.

The gitleaks adapter can use HttpClient to acquire its pinned external scanner binary. That is tool acquisition, not Quality Studio analysis transport or web hosting. It remains injectable and does not change the operator directive: repository inputs and findings stay in process.

Direct consumersAGT-2655, quality-cli and CI call the core without API/UI

The dependency direction is one-way: hosts and automation depend on the core. The core does not depend on host DTOs, repository registration, UI state, or API endpoints. QS-90 rule content enters through injected IReviewSensor implementations and per-analysis configuration; it does not own the runner or finding contract.

Operator question 1: useful without the UI?

Yes. The UI is a later viewer and workflow surface, not a prerequisite for analysis.

The package deliberately excludes UI assets, ASP.NET hosting, authentication, repository registration, review-job persistence, Agent Studio HTTP handover, and git/worktree management. Platform pipeline steps retain responsibility for git artifacts.

Operator question 2: extract the core repository?

Recommendation: keep it in this repository for now. Publish a package boundary first and gather consumer evidence before paying a source-repository boundary cost.
CriterionKeep here while…Extraction signal
Release cadence couplingCore, QS API, finding schema and QS-90 rules evolve together and benefit from atomic tests.At least two external consumers need independently scheduled, supported core releases for multiple release cycles.
Cross-repo versioning vs 0-PR pipelineA single change can update core, caller and compatibility tests without package-publish and dependency-bump coordination.Automated publication, compatibility matrices and fenced cross-repo consumption preserve the 0-PR delivery path without manual version-update PRs.
Public-repository policyThe package and Quality Studio share Apache-2.0 source policy, visibility and disclosure constraints.Security, licensing, ownership or public distribution policy requires separate visibility or governance.
Ownership and stabilityThe QS team can own the semantic contract and adapters together.A separate owner accepts API compatibility, deprecation and release-support obligations.

Revisit extraction only when a signal is real and documented. A folder/project rename inside this repository may happen independently; it does not require a repository extraction.
