QS-91 · Architecture and first implementation slice

Quality analysis is now an in-process package boundary

Agent Studio pipeline integration should call the Quality Studio analysis core as a .NET library. HTTP remains an operator and browser boundary; it is not the analysis transport.

Status First slice implemented Package AgentOrchestrator.CodeQuality 0.1.0 Proof caller quality-cli Repository extraction Deferred

Decision

Consume analysis in process. Callers provide a repository path, named analyses, and configuration, then receive versioned Quality Studio finding envelopes plus per-analysis provenance. The package has no ASP.NET Core dependency and no Agent Studio HTTP client.

HTTP concerns and non-HTTP network use

The product-specific leak was AgentStudioTaskClient: it posted task cards and fetched Agent Studio projects from inside the analysis assembly. It now compiles only into QualityStudio.Api. The core still uses HttpClient inside the pinned Gitleaks binary resolver. That is optional tool acquisition by an analysis implementation, not Quality Studio API transport or web hosting; consumers can provide a local binary through existing configuration.

The allowed dependency direction is callers → analysis package. The API also depends on the analysis package. The analysis package does not depend on the API or frontend.

The narrow facade is stable even though the package retains the existing lower-level public sensor and review APIs for compatibility. A caller does not need to assemble sensors or translate ReviewFinding into the QS envelope.

3. Rule-library boundary (QS-90)

Rules are content consumed by the core, not APIs reimplemented by callers. RuleLibraryPath must resolve to existing content inside the repository; the facade passes the normalized relative path into each named analysis configuration. Per-analysis settings remain opaque string dictionaries.

First-slice limit

QS-91 establishes and tests the consumption boundary. It does not invent or duplicate QS-90 rule content. When QS-90 lands, sensors interpret that content behind the same facade; Agent Studio, CLI, and CI should not parse the rule library themselves.

4. Operator question 1: useful without the UI?

Yes. The UI is an inspection and operator surface, not a prerequisite for analysis.

Standalone consumerUsePackage capability required
Agent Studio pipeline steps (AGT-2655)Run against the fenced server-side checkout and attach QS findings to pipeline evidence without an HTTP round trip.Cancellable runner, deterministic configuration, stable finding/provenance contracts, and explicit unavailable outcomes.
quality-cliLocal or scripted quality analyze execution with JSON output and CI-friendly exit codes.Default sensor composition, repository confinement, named analyses, and finding JSON serialization.
CI jobsRun analysis where the repository is already checked out, archive results, and gate on severity or provider availability.Headless execution, no ASP.NET host, cancellation, reproducible versions, schemas, and no UI state.

The package therefore includes the runners and sensors, configuration contracts, QS finding model and schema, provenance/unavailable semantics, and embedded prompts/catalog snapshots required by its implementations. It excludes API routes, ASP.NET hosting, browser assets, repository registry, and Agent Studio task transport.

5. Operator question 2: extract the core repository?

Recommendation: do not extract now

Publish a package from this repository first. The source, schemas, API adapter, CLIs, and tests currently change together. A repository move would add release and consumer-version coordination before an independent cadence is demonstrated.

CriterionStay in this repository while…Reconsider extraction when…
Release cadence couplingFinding-contract, sensor, CLI, and API changes commonly land in one delivery slice.The core has a demonstrably independent cadence across at least two release cycles.
Cross-repository versioning costA split would require package publication, compatibility updates, and consumer PRs for synchronized changes, adding coordination to the 0-PR pipeline path.Automated versioning, compatibility tests, prerelease feeds, and consumer update automation absorb that cost.
Consumer evidenceThe first external pipeline consumer is still being proven through AGT-2655.At least two independently released repositories consume the package without source-level coordination.
Public-repository policyPackage ownership, disclosure, support, and dependency policy have not been separately approved.The operator approves a public repository/package policy and assigns maintainership and security-response ownership.

Extraction is a later operator decision. QS-91 performs no repository move.
