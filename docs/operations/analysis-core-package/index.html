HTTP-only concern found in analysis code

AgentStudioTaskClient performed HTTP task creation and project discovery from the core project. It was referenced only by API dependency injection and API handover/import endpoints. QS-91 moves the implementation and its tests into QualityStudio.Api without changing those endpoints.

GitleaksBinaryResolver and GitleaksSecurityScanner still use the base-class-library HttpClient to acquire the pinned scanner artifact. That is tool acquisition for a built-in analysis, not an ASP.NET/API transport dependency. Both already accept injected resolver/client collaborators. If offline distribution becomes mandatory, tool provisioning should become a caller policy; it does not justify routing analysis through the API.

5. QS-90 rule-library boundary

The rule library is content consumed by analysis, not a host capability. Repository/global rule selection and versioning remain outside the web layer. Callers pass settings to a named analysis or compose IReviewSensor implementations when QS-90 introduces executable rule adapters. The core owns execution, result normalization, and contracts; QS-90 owns rule definitions, identifiers, versions, and policy content.

Deliberate non-goal: this slice does not copy an empty or evolving rule catalogue into the NuGet package. Doing so would couple package releases to content edits and erase the boundary QS-91 is establishing.
