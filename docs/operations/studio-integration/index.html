Quality Studio and Agent Studio: one review substrate, two product decisions

Let Quality Studio own code-quality semantics, structured findings, and reusable review evidence. Let Agent Studio keep exact task-subject authority, delivery grading, council policy, gates, and lane transitions. Converge through an evidence contract and the existing Review Plane, not through a second central review queue.

This decision keeps the distinction already written into the QS repository: Agent Studio reviews a task diff snapshot; QS keeps the standing quality truth of the codebase. The change is that both products stop inventing separate code-finding shapes.

02What the repositories say today

QS has a reusable kernel, but it is not published

The repository ships a core library, CLI, API, and browser. ReviewMetaDocument v2 carries subject hashes, review-input hashes, a numeric grade, aspects, structured findings, threads, deterministic evidence, and usage provenance. The README still says no NuGet package is published.

README.md:9-15, 40-62; ReviewMetaContract.cs:7-63, 135-160

QS already has change-review machinery

ChangeSetReviewService accepts base and head revisions, computes grade, finding, staleness, boundary, coverage, churn, and economy deltas, and can add an optional four-aspect agent judgement. The committed 20-transition sample reports 72.48% fewer evidence characters in aggregate, with savings in 17 of 20 transitions. This is a QS-local measurement, not yet a Studio pipeline benchmark.

ChangeSetReviewService.cs:19-113; docs/change-reviews.md, Economy measurement

The current QS API is standing-review oriented

The API exposes repository-scoped sweep, estimate, run, handover, thread, and finding-state routes. Its review queue resolves a path in a registered local repository and writes sidecars. There is no change-review API route in the current route table. Calling this queue from Studio would add another scheduler without inheriting Studio's immutable Result-SHA, lease, or fence.

QualityStudio.Api/Program.cs:270-309; ReviewJobs.cs:73-103, 143-195

Studio's local grade is delivery judgement

The Studio grade prompt reads the task body, complete task diff, results/ inventory, and card mode. It emits one A-D grade plus free-text finding sentences. This judges whether the delivery solved the card, not the standing quality of a hierarchy unit.

CodeReviewStepService.cs:320-346, 520-555; prompts/runtime/code-review-grade.md

Studio's council, not the grade token, controls the loop

A Grade A with no findings is accepted. Named findings reissue within the shared budget or escalate after exhaustion. B, C, or D without a concrete finding escalates. The grade parser itself maps A/B to pass, C to concerns, and D to block, but the pipeline domain explicitly states that the grade is reporting evidence rather than a success gate.

CouncilReviewReaction.cs:51-120; CodeReviewGrade.cs:131-143; Studio pipeline domain, lines 651-703

Studio's remote path already has the right authority

The Review Plane materializes and proves the exact expected Result-SHA before commands run. It captures command hashes, artifacts, verdicts, host identity, fence, and authority epoch. The read projection deliberately skips local aspect and grade rows for a remote run and projects the Remote Review outcome into the decision row.

ReviewContracts.cs; RemoteReviewWorkspace.cs:130-197, 1181-1200; RemotePipelineExecutionProjection.cs:5-16, 71-116

The repositories already touch, but do not share runtime types

Agent Studio origin/main contains 11 checked-in QS v1 sidecars. A repository search found no package reference to AgentOrchestrator.CodeQuality and no review-meta reader. Studio also has an additive synchronous ICommitCandidateScanner seam whose comments explicitly name Quality Studio, but that seam sees one file's bytes and cannot represent a task change review.

Studio tree inventory at 8daaccf; CommitCandidateGate.cs:87-96, 148-166

The one-way finding handover is already implemented

QS builds a normal Studio bug card from a selected finding and posts it through POST /api/tasks, with dry-run enabled by default. This boundary should stay: QS creates an ordinary task snapshot; Studio owns its later execution and archival.

AgentStudioTaskClient.cs:6-24, 27-40, 75-111, 130-157; docs/concepts/handover.md

What “review as a service” means here

Yes: a reusable review provider

A caller submits an immutable review subject and policy reference. The QS provider returns a schema-valid, content-addressed evidence artifact. It has no authority to alter a Studio task. The first transport is the existing Review Plane command/capability path because it already materializes and fences the exact commit.

No: a second task control plane

The standalone QS API queue continues to serve QS sweeps. Studio does not delegate RunAttempt ownership, retries, ReviewAttempt leases, council, or gates to that queue. This avoids a third task review lifecycle beside Studio local post-processing and Remote Review.

Boundary judgement

This is a presentation-only navigation report. It is not a review result, command, authentication, or mutation contract. Studio's receiver validation is appropriately narrow. QS still sends its current URL to any embedding parent because it uses *. Keep v1 navigation-only and document it. Before adding finding bodies, source snippets, tokens, or commands, version the message and require a configured parent origin. That hardening is not required to use the current address-bar update.

07Approval-ready implementation slices

Slice 1 · Shared finding envelope and preview contract pin

Approve now Owner: Quality Studio. Behavior risk: Low.

  • Add schema v1 and CLR types for an immutable finding envelope under the QS core package. Reuse the current v2 finding vocabulary and add discriminated standing-unit and task-change subjects.
  • Keep grade and mutable disposition outside the common finding. Add converters from ReviewFinding and FindingDeltaItem.
  • Document the exact preview sender contract and add a QS unit test that proves path/kind/repo navigation emits only the v1 navigation message while embedded.
  • Do not change sidecar v1/v2 readers, Studio behavior, or API routes.
Acceptance: schema round-trip tests cover source-located and location-free task findings; legacy sidecar tests stay green; the sender test asserts the exact payload and no mutation message.

Slice 2 · Portable QS change-review artifact

Approve now Owner: Quality Studio. Behavior risk: Low.

  • Extend quality diff with --format json --output <path> while preserving current exit codes and --no-write.
  • The JSON output names base/head, policy and prompt provenance, usage, deterministic delta, agent judgement status, and common finding envelopes. It must not write .quality/changes/ when --no-write is selected.
  • Keep the provider transport-neutral. Do not add a second QS HTTP scheduler in this slice.
Acceptance: a real temporary Git fixture proves exact base/head binding, schema validation, unchanged worktree/index, stable exit codes 0/1/2, and explicit unavailable agent evidence rather than a false pass.

Slice 3 · Agent Studio shadow provider on the Review Plane

Approve now Owner: Agent Studio. Behavior risk: Low because the result is reporting-only.

  • Add an opt-in post-quality-change-review step implemented as a Review Plane capability/command against the already materialized expected Result-SHA and integration baseline.
  • Persist the QS JSON as normal digest-checked ReviewArtifactEvidenceDto. Record provider unavailable and provider failure separately from product findings.
  • Do not change council, lane, integration admission, the existing A-D grade, or existing aspect execution.
  • Run paired evidence on at least 20 completed coding tasks spanning local and remote delivery, code-only and mixed code/docs, and clean and known-finding cases.
Acceptance: every artifact binds the same Result-SHA as the ReviewSubject; 100% parse/schema success in the cohort; zero task state changes attributable to the shadow step; provider cost and duration are visible.

Slice 4 · Structured Studio findings and unambiguous grade names

Conditional Owner: Agent Studio with QS contract dependency. Entry gate: Slice 3 cohort accepted.

  • Make the Studio grade producer persist common finding envelopes. Keep the legacy text sentinel reader during migration; council consumes the structured projection.
  • Feed QS change-review evidence into the delivery-grade prompt as prior evidence instead of asking the grade pass to rediscover code facts.
  • Rename user-facing “Quality Grade” to “Delivery Grade”. Keep existing filenames, tags, and API fields as backwards-compatible storage identifiers. Present Remote Review as “Review outcome”, not another grade scale.
  • Do not remove any aspect in this slice.
Acceptance: every non-A delivery grade has at least one schema-valid actionable finding or takes the existing missing-handoff escalation; legacy review files remain readable; screenshots prove distinct labels in both themes.

Slice 5 · Remove the duplicate code-quality call and adopt policy

Conditional Owner: Agent Studio. Entry gate: paired operator review finds no lost blocking code issue and no subject mismatch.

  • Replace only the narrow Studio code-quality aspect with the QS provider result. Keep requirement-fit, tests-and-evidence, documentation-impact, Delivery Grade, and council.
  • Route QS findings through Studio policy: deterministic critical/high regressions and configured rules can request reissue or escalation, but only the Studio orchestration stage applies that action.
  • Add an “Open in Quality Studio” evidence link using repository, path, kind, and fingerprint. The generic URL Preview may host the page; no QS surface is rebuilt in Studio.
  • Retain a per-project rollback switch to the existing Studio code-quality aspect for one release window.
Acceptance: one code-quality model call is removed per standard task; deterministic gates and council behavior are unchanged; rollback restores the old aspect without rewriting task history; QS and Studio both remain operable alone.

Limits

  • The QS checkout does not contain the enriched AGENTS.md, docs/start/README.md, contribution guide, model-routing policy, or style-reference path. Those sources were available and inspected in the local Agent Studio repository at the snapshot above.
  • No current dataset compares QS provider findings with Studio aspect findings on the same fenced task subjects. This is why the recommendation makes the first runtime adoption a shadow cohort.

  • No model or thinking-level change is proposed. Each implementation card remains subject to Agent Studio's canonical model-routing policy and correctness floors.
