Quality concept for Quality Studio

What an operator-driven review session proves about finding quality per model — and what it cannot prove, because the deep model is uncatalogued and the claude review path emitted nothing. The honest conclusion sets the default review routes per repository class, names the empty rule library as the first gap, and defines what has to be true before any per-model quality signal can feed TE-42.

01The measurable result

Seven review runs were dispatched across both repositories — security and code kinds, 110 files queued — all through cliType=claude, model claude-sonnet-5. The aggregate model-side result was:

Zero across every model metric

0 usage operations · 0 findings emitted · 0 LLM tokens · 0 cost. No review operation returned on this host. The operational failure is documented in the sibling security concept as finding N-01; here it matters because it means the per-model finding-quality comparison the session set out to produce has no data at all.

This is not a null we should paper over. It is the finding: the QS review pipeline, exercised honestly on this host with the models the operator selected, produced no per-model evidence, and reproduces at the source the exact condition the QS-61 dossier reported downstream — that TE-38 holds "zero eligible operational runs" and every model therefore remains unknown / insufficientEvidence. Today shows the feed is empty because the pipeline cannot emit even one operation, not merely because the bridge has not been wired.

One number the pipeline did yield, from the pre-flight estimator rather than a run: a module-scope security review of task-server (24 files) at claude-sonnet-5 was estimated at ~302k input and ~60k output tokens for ~$1.21. That is a planning figure, not an actual spend — actual spend was zero because nothing ran.

03Deterministic evidence as the floor

The only evidence produced in the whole session came from deterministic sensors, at no token cost and with full reproducibility. That contrast is the practical lesson for a quality strategy that has to survive an unreliable model path.

Conditional on the path being fixed

These defaults assume a review path that returns. Until the security concept's M-1 (operation watchdog and resilient queue) lands, no model route is reliable here, and the deterministic floor of section 03 is the only quality signal that can be trusted. Fix the pipeline first; choose models second.

05Gaps in the rule library

The single most actionable non-blocked finding of the session: the rule library is empty in both repositories. The guideline catalogue offers four installable rule sets, and zero are installed on either repo.

security-boundariesnono

testing-confidencenono

With no installed guidelines, review findings cannot cite a repository rule, the guideline-trace join returns empty, and the guideline-impact analyzer has nothing to weigh. Even once the review path returns, findings will be weaker — less actionable and harder to route to a rule — than the QS-61 finding model intends. This is the concrete rule-library work (the QS-90 direction) and it is not blocked by N-01: guidelines install through POST /api/repos/{id}/guidelines/catalog/{catalogueId}/install and take effect deterministically.

Recommended installs

  • quality-studio: security-boundaries + dotnet-api-safety (the API and analysis core are .NET and are the R-01 surface), plus angular-typescript for the frontend and testing-confidence for the test projects.
  • agent-studio: security-boundaries + dotnet-api-safety on the backend and task-server, angular-typescript on the frontend (the token/component-consistency defect class), testing-confidence on the test modules.
  • Install first, then re-run reviews once M-1 lands, so findings carry rule citations from the first real run.

06Feed for TE-42 and the TE-38 gates

QS-61 records TE-38's gates: at least 20 operational runs, at least 20 assessed findings, and at least 70% finding-outcome coverage before any per-model routing signal is emitted, and even then the signal is observational precision, never recall. Today's contribution to those gates is exactly zero eligible operational runs, which keeps every model at insufficientEvidence.

The implication for TE-42 is a sequencing one, not a modelling one:

  • Prerequisite 1 — a returning review path. M-1 from the security concept. Without it the numerator of every quality metric is zero.
  • Prerequisite 2 — a runnable model pair. Restore a supported deep model in the catalog (or accept codex sol vs terra as the comparison), so tokens-vs-findings has two arms that can both execute.
  • Prerequisite 3 — installed rules and captured provenance. The rule installs of section 05 plus the QS-61 S2 execution provenance (requested vs executed model, thinking level) so cohorts are formed on executed route, not card intent.
  • Only then does the token-vs-actionable-findings question become answerable, and it remains an observational precision signal bounded by the model-routing policy's correctness floors.

TE-42 should not consume a per-model quality signal from Quality Studio until these three hold. Today's evidence is that none of them do yet, and that the ordering above is the shortest path to a trustworthy first datapoint.
