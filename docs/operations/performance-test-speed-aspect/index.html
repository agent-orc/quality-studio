Performance and test speed as a measured quality aspect

Make test speed observable, evaluable, and actionable. A repository with no recent timing evidence should show an explicit quality gap, while measured slowdowns should lead to specific improvement work.

Phase Decision readyStatus Decision pendingUpdated 27 October 2026Working option B

01 Alternatives

Option A · Extend the performance review

Ask the existing source-reading ReviewKind.Performance model to infer test speed from code and CI files. This needs little storage work, but cannot establish elapsed time, trends, or whether missing artifacts reflect a slow or an unmeasured repository.

Option B · Separate measured aspect

Add taxonomy aspect performance.test-speed backed by deterministic artifact sensors and a versioned metric series. Keep performance.general for source review. Report measured budgets and measurement coverage separately. This is the recommended path.

Option C · CI dashboard only

Chart timing artifacts outside Quality Studio. This can display trends quickly, but leaves measurement gaps, findings, repository budgets, and improvement suggestions outside the quality model.

02 Recommendation

Option B · A sensor-backed test-speed aspect

Register performance.test-speed in the taxonomy, not as another review kind. Ingest CI artifacts produced by test runs; do not run the suites inside a review sensor. Ship an initial test-timing sensor for TRX and Playwright JSON, per-repository budgets, and explicit unmeasured gaps for Agent Studio and Quality Studio itself.

Aspect boundary

The existing Performance kind remains an LLM source review mapped to performance.general. The new aspect receives measurements, provenance, availability, and deterministic findings. Later performance.build and performance.runtime may use the same contract after their own workload definitions and budgets exist; they are not aliases for test speed. The optional model step receives measured hotspots and source locations only after the deterministic result is stored.

Metric snapshot and storage

Use a separate immutable MetricSnapshot.v1 rather than adding arbitrary numbers to finding prose. A snapshot has repositoryId, commit, branch, runId, lane, capturedAt, producer, toolVersions, hostClass, concurrentSuites, artifact digest and format, test counts, and metric entries with id, value, unit, aggregation, and subject. Per-test entries use a stable framework/test identity and optional repository-relative source path. Preserve source artifacts by digest or trusted artifact URI, not by copying every raw report into the Quality Studio database.

Append snapshots by repository, commit, lane, and run ID; repeated runs at one commit remain separate points. Reject duplicate run IDs with conflicting digests. Mark each metric as complete, partial, or unavailable according to the artifact's actual coverage. A compact summary is a valid first input for reported fields, but an omitted tail of tests remains unknown; an interrupted Playwright run can diagnose failures and retries but cannot establish a full-suite wall baseline. The API exposes latest comparable snapshot, bounded time series, metric availability, budget result, and top offenders. A finding references snapshot ID, metric ID, observed value, threshold, and comparison window through a typed evidence reference; free-text evidence remains human-readable. Keep old snapshot versions readable when the producer changes.

Evaluation

Configure budgets in each repository's sensor configuration: an absolute ceiling and a relative baseline rule. Use five comparable full-run samples for the baseline median; compare only like lane, selection, runner class, and coverage mode. Mark an absolute ceiling breach immediately. Create a regression finding when at least three of the latest five comparable runs exceed the pinned baseline median by both 20% and 60 seconds. Keep a single breach as a warning until repeated evidence exists. Record changed test count and lane selection so a targeted run cannot replace a full-suite trend.

For contention, flag a test only after at least three same-commit or unchanged-test samples have a max/min duration ratio of at least 3, with host load or concurrent-suite evidence attached. It is a diagnostic suggestion, not a code regression. Retry rate is retries divided by executed tests; flaky rate counts tests that failed then passed in the same run. Skipped and quarantined counts remain separate. An unavailable source yields no numeric zero.

Measurement quality

Make freshness a repository setting, defaulting to 14 days for a full-suite run on the tracked branch. Required metrics are suite wall time and per-test duration where a test framework is configured, plus per-spec timing where Playwright is configured. Show a measurement coverage score of 0–100 for performance.test-speed: 100 × fresh required metrics / applicable required metrics, with equal weights. Thus a repository with no timing artifacts scores 0 on measurement coverage and receives perf.metric-missing.<metric> or perf.metric-stale.<metric> gap findings. An inapplicable metric is excluded only with a recorded reason. This score describes evidence completeness, not speed or a combined performance grade; budget statuses remain individual. Historical field Web Vitals stay unavailable when absent.

Suggestions and destination

Deterministic rules first: concentration plus repeated full-host setup suggests sharing a class fixture; many fixed sleeps suggest condition-based waits; one Playwright worker with independent specs suggests an isolated parallel pilot; full-suite rerun after one failure suggests failed-class replay. Each suggestion carries triggering metrics, threshold, estimated upper-bound time saving when calculable, confidence, and source location. Static patterns alone are labelled hypotheses. The optional LLM step may inspect only the measured hotspot's code and propose a concrete refactor with file and line references; it cannot invent timing values or auto-apply changes.

Export an idempotent suggestion payload to Agent Studio with repository, measured commit, metric snapshot IDs, finding fingerprint, title, proposed acceptance, and evidence links. Agent Studio creates a reviewable card draft through its existing task intake; a human or established task policy promotes it. Repeated runs update evidence on the same fingerprint rather than create duplicate cards.

Presentation

The proposed aspect view shows measurement coverage, freshness, one budget status per metric, a trend chart with baseline and absolute ceiling, and ranked tests/classes/specs with duration and source links. It must label wall time separately from summed test time and show unavailable for absent data. These are proposed surfaces; no present UI state is asserted here.

MVP order

  1. Define the snapshot contract and ingest TRX, Playwright JSON, and Agent Studio's retained compact summary JSON from real runs; configure budgets and display per-metric unmeasured gaps on both Agent Studio and Quality Studio until valid, fresh, complete evidence arrives.
  2. Persist append-only series and comparable-run regression evaluation.
  3. Add JUnit/Vitest and build wall time, then static sleep and parallelism signals.
  4. Show the trend and offender view, then export measured suggestions as Agent Studio card drafts.

04 Open decisions

These are decisions for Robert. The recommended option in each row is the working decision for implementation until an operator records another choice.

  1. D1 · Aspect scope. Choose the sensor-backed performance.test-speed aspect now; add build and runtime aspects only when their workload contracts are ready. Keep the existing Performance review kind and performance.general.
  2. D2 · Missing evidence. Choose explicit missing/stale findings plus a 0–100 measurement coverage score within the test-speed aspect. Default freshness is 14 days for the tracked full-suite lane. Do not roll it into a combined performance score.
  3. D3 · Budgets. Choose per-repository absolute ceilings and a five-sample comparable baseline. Flag budget status on an absolute breach; open a regression finding after three of five runs exceed the baseline median by both 20% and 60 s. Pilot thresholds on both repositories before using them as gates.
  4. D4 · Artifact authority and retention. Choose signed or digest-verified CI artifacts and an append-only compact snapshot; keep raw reports in the producer's artifact store. Retain detailed series for 90 days and monthly aggregates thereafter for one year, subject to repository policy.
  5. D5 · Card creation. Choose deterministic suggestions first and Agent Studio draft cards with human promotion. Enable the LLM refactoring step only for measured hotspots with stable code locations and retain its proposal as advisory evidence.
