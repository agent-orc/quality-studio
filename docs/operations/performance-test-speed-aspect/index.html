Performance and test speed as a measured aspect

Tests and code should get faster, and the ability to measure that speed is itself evidence of quality. This dossier defines a sensor-led performance.test-speed aspect, its metric contract, and an ordered first slice using Agent Studio and Quality Studio.

01 Alternatives

Option A · Extend the LLM performance review

Add timing prose to the existing ReviewKind.Performance prompt. This is inexpensive to expose, but the prompt explicitly says “Do not use tools”; source reading cannot establish run duration, freshness, or a reproducible regression.

Option B · Sensor-led test-speed aspect

Add taxonomy aspect performance.test-speed with an artifact-fed sensor and separate metric snapshots. Keep the existing LLM review as performance.general. Budget findings and improvement suggestions refer to recorded numbers; missing evidence remains visible. This is the recommended slice.

Option C · Broad performance platform first

Build test, build, and runtime instrumentation together, then a unified score. It addresses more workloads, but delays the first usable measure and conflicts with the present performance-domain rule that no combined score is defined.

Option B establishes the shared contract so performance.build and performance.runtime can follow without treating their different workloads as one number. The existing performance review remains source-reading analysis; the new aspect is a measured judgement.

02 Recommendation

Working decision · Option B

Start with a test-timing deterministic sensor that ingests completed TRX and Playwright JSON artifacts, records one immutable snapshot per run, evaluates repository budgets, and emits measurement gaps and regressions. Pilot it on Agent Studio and Quality Studio itself. Add other inputs in bounded slices.

Aspect and evidence contract

Register performance.test-speed in the quality taxonomy and map it to sensor evidence. Preserve ReviewKind.Performance for performance.general; do not reuse its string as the new aspect identity. The existing kind is hard-coded at several call sites, so the first implementation must make this mapping explicit and retain existing review and API behavior.

Use a versioned MetricSnapshot rather than inserting arbitrary numbers into free-text finding evidence. Proposed fields: schemaVersion, repositoryId, commitSha, runId, lane, environmentKey (OS, runner class, CPU quota, relevant concurrency), observedAt, metricId, value, unit, sampleCount, status, sourceArtifact (digest and retained reference), and optional test/class/spec identity. Use stable metric IDs and milliseconds for durations. A finding cites snapshot IDs, numeric observed and budget values, and a source location only when one is known. Store source artifacts as bounded, digest-checked inputs; an absolute runner-local TRX path alone is not durable evidence.

Append snapshots per run and commit, with idempotency by repository, run, lane, metric, and subject. Keep raw artifacts under a retention policy and summaries long enough for a useful trend. Expose repository metric-series and snapshot-detail APIs; the UI shows a trend chart with environment/lane filters, budget status, top tests/classes/specs, and a clearly labelled “unmeasured” state. A comparison must not connect unlike environments as a single regression line.

Evaluation

Repository sensor configuration holds budgets by metric and lane: an absolute ceiling and a relative ceiling against an approved baseline. A regression requires both a material absolute delta and a relative delta (working defaults: at least two minutes and 15% for suite wall time), across three comparable completed runs; the absolute budget may still fail on a single complete run. Show the current value, baseline, sample count, host class, and threshold. Baseline changes require an explicit versioned update. For tests with at least three comparable observations, flag high variance when p90/p10 exceeds 3×; label it a contention lead until host load and concurrent-suite evidence support a cause.

Measurement coverage is a separate quality facet: required metric present and fresh, stale, unavailable, or missing. Working freshness: a successful run for the current head within 14 days; an older commit is historical, not current. A producer failure keeps the last snapshot for history but cannot turn the current run green. Emit a perf.metric-missing.<metric> finding for each required absent or stale metric after a configured collection opportunity; mark infrastructure failure as unavailable with its reason. Present an ordinal measurement status alongside budget results, with an explicit quality penalty for missing required measures. Do not calculate one combined performance score: this preserves the performance domain’s current position while making measurement quality consequential.

Suggestions and handover

Use deterministic rules first: a class with large summed time and repeated host setup suggests measuring fixture reuse; fixed sleeps point to named files and counts; one Playwright worker with many specs suggests a controlled parallel pilot; a full-suite rerun after one failure suggests a class-filtered retry. Each suggestion carries triggering snapshots, code locations when known, expected lever, and a verification metric. An optional LLM pass may turn measured hotspots into refactoring proposals, but must cite these facts, inspect bounded source locations, and never invent a measured speedup.

Publish accepted suggestions as structured candidate cards through Agent Studio’s normal task intake, with repository, baseline, target, evidence links, and acceptance measure. Keep Quality Studio as the evidence source and Agent Studio as the task owner; do not create cards automatically from a lone noisy run.

Slice order

  1. Define aspect mapping and versioned metric snapshot contract.
  2. Implement TRX and Playwright JSON test-timing sensor, artifact admission, and “unmeasured” gap.
  3. Persist series and evaluate repository budgets on Agent Studio and Quality Studio.
  4. Render trends and offenders; add deterministic suggestions and card handover.
  5. Extend to Vitest JUnit, builds, static scans, and optional runtime measures.
