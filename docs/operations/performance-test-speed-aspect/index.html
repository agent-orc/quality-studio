Performance and test speed as a measured quality aspect

A fast codebase needs measured test and build work, comparable budgets, and a record of where time goes. The first delivery makes test timing visible and treats absent evidence as a quality gap.

Observed 11 October 2026Phase Decision readyStatus Decision pendingWorking option B

Decision requested

Adopt performance.test-speed as a measured aspect. Ingest test artifacts, keep an append-only numeric history, compare compatible runs against repository budgets, and expose an explicit unmeasured state. Keep the existing file-level performance review as a separate source-reading capability.

01Alternatives

Option A · extend the LLM review

Add timing text to the existing performance prompt and findings. This has low schema cost, but the prompt cannot produce missing measurements, reliable numeric trends, or reproducible budgets. The current prompt explicitly forbids tools.

Fit: source risk review only.

Option B · measured aspect

Give performance.test-speed its own artifact-backed sensor, metric snapshot, evaluation rules, and view. Reuse the sensor framework and keep the source-reading review separate. This adds persistence and API work, but gives a verifiable value and provenance for each claim.

Recommended

Option C · CI dashboard only

Keep timing reports in CI and link them from Quality Studio. This is useful as an interim producer, but cannot express the repository's measurement gap as a Quality Studio quality attribute or turn comparable regressions into findings and proposals.

Fit: interim artifact collection.

The aspect taxonomy should reserve performance.build for build elapsed time and performance.runtime for workload-specific hot paths. They remain separate metric families and are not added to the initial test-timing sensor. performance.general is the proposed name for the existing source-reading review aspect; its kind string remains performance until a deliberate migration.

02Recommendation

Option B, beginning with test timing

Make the first sensor parse TRX and Playwright JSON from Agent Studio and Quality Studio. It records values and gaps without running tests. CI owns the expensive production of reports. Use JUnit XML as a compatible input for Vitest and other lanes once the same contract is proven.

Snapshot and series contract

Use a separate versioned MetricSnapshot instead of adding numeric values to free-text findings. Each immutable snapshot has schemaVersion, repository ID, commit SHA, CI run ID, lane, measured-at time, environment cohort (OS, runner class, CPU class, test/build configuration, worker count), artifact URI and SHA-256, parser version, test counts, wall milliseconds, summed final-attempt milliseconds, and named metric values with units. Per-case observations preserve stable test identity, class/spec path, attempt, duration, outcome, and quarantine marker. The artifact manifest may reference TRX, JUnit, Playwright JSON, build logs/binlog, and a run summary; only explicitly configured paths are read.

Keep the original artifact digest and a bounded top-offender projection, plus normalized observations needed for trends. Append by run ID and artifact digest; a repeat upload is idempotent while two runs at the same SHA remain distinct. Store metric history under the repository's data root, subject to its retention policy; expose repository-scoped latest, trend, and top-N APIs with pagination. A failed producer or parser records an ingestion state and preserves the last successful snapshot, following the coverage precedent.

The sensor's parser may be available while its evidence is absent. Report unmeasured with a reason rather than using SensorAvailability(false) to imply a missing tool. Reserve unavailable for a broken parser, unsupported format, or inaccessible configured source. Reject path traversal, unsafe absolute paths, mismatched commit identities, non-finite values, and implausible negative durations.

Evaluation and scoring

Repository sensor configuration holds applicable lanes, required metrics, artifact locations, absolute budgets, relative budgets, pinned baseline run IDs, and freshness windows. The working default is 14 days since the most recent successful comparable run; a known daily CI lane can use a shorter window. A baseline is pinned from a clean, successful run and never silently redefined by a slower run. Compare only the same lane and environment cohort. Show non-comparable points on the timeline but exclude them from regression decisions.

Use absolute budget failures immediately after a valid run. For a relative regression, compare medians of at least three candidate and three baseline runs in the same cohort; flag suite wall time when it is both over 20% and over 30 seconds slower. Treat a repeated test whose max/min duration exceeds 3× across at least three comparable runs at the same SHA as a contention lead; display variance and samples rather than calling it a code regression. Track trends per commit and by run time so repeated runs remain visible.

Measurement is a quality attribute. Show an evidence-completeness score for performance.test-speed: required, applicable metrics with current valid observations divided by required, applicable metrics, scaled to 0–100. Missing or stale metrics produce perf.metric-missing.<metric> or perf.metric-stale.<metric> findings and lower that score; no artifacts means 0 and an explicit unmeasured status. At initial rollout, both Agent Studio and Quality Studio start unmeasured until their own valid CI artifacts are ingested. Separately show speed budget status as pass, breach, or unavailable. This avoids interpreting an absent timing as a fast test suite. Do not aggregate test speed, build speed, and field Web Vitals into a single performance-domain score. This preserves the current domain rule that has no combined performance score.

Suggestions and Agent Studio handoff

Deterministic rules use measured conditions and separately verified context. A concentrated class with host-start evidence can suggest reusing or sharing a fixture; duration alone can only say “inspect setup”. Static sleep counts can request review of cited source locations without claiming that all sleep time is avoidable. A one-worker Playwright configuration with a long browser lane suggests a bounded multi-worker experiment. A CI log showing full-suite rerun after one failure suggests targeted replay before the full gate. Rank proposals by observed elapsed opportunity and confidence, and include counterexamples or preconditions.

An optional LLM pass can read the top measured hotspots and bounded source excerpts to propose concrete refactors with file locations. It cannot invent metric values, alter the deterministic grade, or submit cards autonomously. Export each accepted proposal as an Agent Studio card draft containing problem, evidence artifact/run links, target files, estimated opportunity, acceptance measurement, and a stable fingerprint. Agent Studio's operator reviews the draft before card creation; repeated exports update the same draft rather than creating duplicates.

MVP order

  1. Define the test-timing snapshot and parse TRX plus Playwright JSON fixtures. Prove missing and malformed artifact behavior.
  2. Have the Agent Studio acceleration tracks and Quality Studio CI retain timing artifacts and a summary JSON on passing and failing runs.
  3. Persist the append-only series and implement configured budgets, unmeasured/stale findings, and repository-scoped APIs.
  4. Show trend, budget status, and top offenders; export evidence-backed suggestions as reviewed Agent Studio card drafts.
  5. Add Vitest JUnit, build timing, fixed-sleep counts, and parallelism signals. Instrumented runtime hot paths remain a later family.
