Quality Studio · security hardening · decision dossier

Separate reviewed code from the Studio host

An end-to-end assessment of repository ingestion, model review, deterministic sensors, credentials, storage, rendering, and handover. The current implementation is suitable only for trusted, local repositories until the two critical host-boundary chains are closed.

Decision requested

Approve Option C and slices S0–S6. Until S0 is accepted, do not enable hosted multi-client operation. Until S1 and S2 are accepted, restrict reviews to repositories controlled by the same operator who owns the Studio host. Prompt wording and “read-only” agent permission are not a security boundary.

The recommended design runs review agents and executable sensors in separate, short-lived workers with a read-only source snapshot, clean service identity, restricted egress, bounded resources, and a brokered, schema-validated result write. The API—not a repository-scoped client—owns repository roots and executable analyzer profiles.

01Scope and method

This assessment traced bytes and authority, not feature names: repository-controlled files and sidecars; prompt construction; review-agent launch; deterministic analyzer execution; response parsing; writes under .quality; Angular and report rendering; and the optional Agent Studio handover. 05Evidence-backed findings

F-01 · Analyzer configuration crosses directly into host command execution

Critical · R-01

Program.cs:177–202 requires registrar privilege only for creating or importing a repository. A client allowed to access repository A may still call PUT /api/repos/A. RepositoryRegistry.cs:267–281 accepts per-sensor configuration. SarifSensor.cs:70–90 expands its command string and passes the first token as an executable; ProcessSensorCommandRunner starts it in the repository working directory while inheriting the host process environment. The scan endpoints at Program.cs:277–280 are not spend-rate-limited. This is a complete authorization-to-command chain, not a prompt-injection hypothesis.

Repository root confinement does not reduce command authority: a configured command such as a shell or PowerShell executable can read beyond its working directory, inspect inherited credentials, use the network, and modify host-visible files. Dependency audits also execute dotnet list … --vulnerable and npm audit --json in repository directories (DependencyVulnerabilitySensor.cs:118–152) without a process sandbox, environment allowlist, output cap, or timeout.

Immediate operating rule

Disable hosted mode and executable analyzer configuration until S0. Treat deterministic sensors as code execution, even when their output is called “evidence.”

F-02 · The review agent is read-only but not isolated

Critical · R-02

ReviewRunner.cs:209–265 reads repository files, repository-resolved guidelines, open threads, and sensor JSON. ReviewPromptBuilder.cs:35–64 substitutes these values directly into the prompt. Templates label source with tags and say “Do not use tools,” but repository bytes can close or imitate those textual boundaries. There is no independent instruction/data channel.

ReviewAgent.cs:60–80 launches the coding CLI with the repository root as its working directory, PermissionMode = "read-only", and ContextMode = "shared". CodingAgentRunner 0.7.0 is the pinned dependency. Its installed package documentation defines shared context as the operator's normal signed-in CLI home/settings/cache/memory. Quality Studio has no model-provider API-key setting in appsettings.json; the review path delegates authentication to that existing CLI context. Therefore a successful prompt injection can attempt reads from every host location the CLI identity can read and can include obtained data in the provider request. Read-only prevents intended writes; it does not provide filesystem, credential, process, or egress isolation.

The correct fix is an OS/container boundary with a clean service identity, not stronger prose in the prompt. A prompt rule remains useful as defense in depth and for model behavior, but it cannot be the enforcement point.

F-03 · Work and spend caps are enforced after an operation, not before it

High · R-03

The file API calls File.ReadAllBytesAsync without a size check (Program.cs:413–433). Review preparation reads an entire file, or concatenates every aggregate member, without byte/file-count bounds (ReviewRunner.cs:462–472). The token/cost cap is checked between completed operations (ReviewJobs.cs:431–455, 850–875), so one very large prompt can exceed a run cap before the next check. The 64 KiB HTTP request-body limit in appsettings does not bound repository content or model output.

The same availability issue exists in review sidecars: ReviewMetaIndex.cs:87–108 parses each matching JSON file and retains its cloned root element after checking only unit.path, kind, containment, and reparse traversal. There is no maximum sidecar size or full schema validation at indexing time. Malformed JSON is caught; oversized or structurally surprising valid JSON is not quarantined.

F-04 · Secret discovery is redacted, but review persistence can amplify secrets

High · R-04

Current and task-range repository scans returned zero findings. A redacted all-ref Gitleaks scan found one generic-api-key match at docs/concept.md:1461 in commit 7994d81d32d…; inspection showed a documented 64-hex content-derived “unit-key,” not a credential. This is a narrow false positive to suppress by fingerprint or precise rule, not a reason to disable history scanning.

The remaining leak path is review output. Raw source is sent to the model, the response permits narrative descriptions/evidence/recommendations, and results are persisted under .quality/reviews. Yet .quality/security/gitleaks.toml:6–17 excludes the entire .quality/reviews tree. A repository secret that is echoed or summarized into review metadata can therefore become durable and may later enter a handover prompt without being checked by the current scanner. The output boundary needs secret detection/redaction before persistence, with values omitted rather than logged.

F-05 · Handover creates a second-order prompt-injection path

High · R-05

The renderer itself is safe: model text is interpolated as text. The boundary changes when an operator clicks “Create task.” review-panel.ts:48–60 sends the model-authored description and recommendation as findingText. Program.cs:1037–1056 trusts those request fields after path normalization. AgentStudioTaskClient.cs:130–157 interpolates them directly beneath a “Finding:” heading in a downstream agent task prompt. A malicious repository can try to make the reviewer emit instructions that survive into that task. One explicit operator action is required, which lowers likelihood but does not make the content trusted.

Handover should accept a finding fingerprint, resolve the canonical finding server-side, show the exact generated task to the operator, and attach untrusted model prose as a structured data field whose downstream contract explicitly forbids treating it as instructions.

F-06 · Hosted credentials are static, and Local mode is a configuration assumption

High · R-06

ApiSecurity.cs:20–64 materializes credential hashes once from startup options. Tokens have no expiry, audience, key identifier, or live revocation. Rotation requires changing configuration and restarting. In Local mode, ApiSecurity.cs:73–76, 100–101 grants wildcard registrar authority and bypasses the mutation client header. The standard launcher correctly binds loopback, but the API does not reject a non-loopback binding while configured Local. State-changing no-body endpoints such as sensor scans also lack a local Origin/CSRF check; browser CORS policy is not a server-side authorization control.

F-07 · QS-53 removed the shipped maintainer path; recurrence prevention is absent

Medium · R-09

Commit 251ce81c78a7b937d5e706892b7cacb4bc332c01 added ../../../agent-taskboard-devspace to the tracked AllowedRoots in src/QualityStudio.Api/appsettings.json. The QS-53 result commit aca322f3d16cad1d29dfc3a7d0a28d470ee6c150 removed it and documented that machine-specific paths belong in environment-specific configuration. The current file contains only ../...

No credential was present in that path. The security issue was disclosure of maintainer filesystem topology and, more importantly, an expanded set of repositories that a registrar—or the R-01 privilege chain—could select. The instance is fixed; CI has no policy that prevents the same class of tracked configuration change.

08Implementation slices

Each slice is independently reviewable and carries explicit exit evidence. Effort is an engineering estimate, not elapsed calendar time.

S0 · Close the authorization-to-command chain Approve now · 1–2 days

  • Require registrar privilege for repository root, global input, sensor, and archive mutations; preferably split immutable host-owned root/sensor configuration from repo-scoped display settings.
  • Reject free-form analyzer commands. Resolve a host-owned analyzer profile ID to an immutable executable and argument template. Disable command-backed analyzers by default in Hosted and Local modes until S1.
  • Apply the spend limiter to sensor scans and other expensive scans. Require a valid Origin plus a per-session anti-CSRF nonce for local mutations, and fail startup when Local mode binds a non-loopback address.
  • Upgrade the Angular 20.3.26 family to a fixed, mutually compatible 20.3 patch and regenerate the lock.
Exit: an A-scoped client cannot change A's root or sensor execution profile; shell/PowerShell command fixtures are rejected; cross-origin local mutation is denied; production npm audit has no high/critical finding; authorization and configuration tests cover all mutation routes.

S1 · Put agents and sensors behind a worker boundary Required for untrusted repos · 4–6 days

  • Create a per-run worker with a read-only, regular-file source snapshot and a separate writable scratch/output mount. Do not mount the Studio registry, host home, Git credentials, sockets, or unrelated repositories.
  • Use a clean service identity and clean CLI context. Supply only a short-lived model credential through a broker or one-run secret mount; never reuse an operator's personal signed-in CLI home.
  • Allow egress only to the approved model endpoint for agent workers. Sensor workers get no network unless their immutable profile requires a specifically approved registry endpoint.
  • Enforce wall-clock, CPU, memory, process, output-byte, and filesystem quotas. The host validates a versioned response schema and is the only component allowed to atomically write .quality results.
Exit: adversarial fixtures ask the agent and analyzer to read planted host-home/environment secrets, access a sibling repository, open a network canary, fork repeatedly, and write outside scratch. Every attempt is blocked and no canary value appears in provider traffic, logs, or artifacts.

S2 · Bound and quarantine repository input 2–4 days

  • Set versioned maximums for file bytes, aggregate files/bytes, prompt bytes/tokens, sidecar bytes/count, response bytes, findings, threads, and individual text fields.
  • Preflight the complete operation against the remaining run budget before launching a model; reject or deterministically partition oversized aggregates.
  • Stream or size-check file responses before allocation. Apply one regular-file/no-reparse opener to API, hierarchy, review, and sidecar reads.
  • Validate review sidecars against the same versioned schema used at write time; quarantine invalid/oversized files and expose a bounded diagnostic instead of their payload.
Exit: oversized file/aggregate fixtures produce a stable 413/422 before agent launch; a valid-but-huge or schema-invalid sidecar cannot raise steady-state memory, break the tree, or enter handover; cap tests prove no single operation starts above remaining budget.

S3 · Make secret handling end-to-end 2–3 days

  • Add an explicit “never reproduce credentials; cite location/type only” review rule, then independently run redaction/DLP over model output before logs, persistence, rendering, or handover.
  • Replace the blanket .quality/reviews Gitleaks exclusion with a safe metadata scan or dedicated redactor. Add an all-ref CI scan with a narrow, reviewed suppression for the documented unit-key false positive.
  • Add a tracked-config policy that rejects machine-specific AllowedRoots, absolute maintainer paths, cleartext credential fields, and secret-like values. Keep deployment paths and credential hashes in environment/secret-store configuration.
  • Document identification, revocation, and rotation without ever copying the secret into an incident artifact.
Exit: seeded fake secrets in source and malicious model output are absent from .quality, API responses, handover requests, and logs; current plus all-ref scans pass with only fingerprint-specific, reviewed suppressions; a QS-53-style appsettings diff fails CI.

S4 · Preserve rendering safety and make handover data-only 2–3 days

  • Keep Angular interpolation and report HTML encoding; add regression fixtures containing tags, event handlers, Markdown links, control characters, template syntax, and bidi characters.
  • Change handover input from free-form finding fields to repository ID + finding fingerprint. Resolve the stored finding server-side and verify its subject hash/staleness.
  • Present the exact downstream card for confirmation. Put model prose in a typed JSON attachment or quoted data block, label it untrusted, and keep task instructions in a host-owned template. Record source commit, finding fingerprint, prompt-template version, and approver.
Exit: a finding containing “ignore previous instructions,” HTML, and terminal/control sequences renders as text and cannot change the host-owned task instructions; altered/stale/client-forged finding data is rejected; no task is sent before preview confirmation outside dry-run tests.

S5 · Add a hosted credential lifecycle 3–5 days

  • Adopt short-lived, audience-bound signed client assertions, or reloadable high-entropy bearer hashes with key ID, expiry, repository scope, and a revocation source. Keep constant-time validation.
  • Separate roles for repository administration, review spending, sensor execution, state mutation, and handover. Deny by default on every route and test the complete route inventory.
  • Emit audit events for credential ID, action, repository, decision, and result—never the credential. Prove revocation without an API restart.
Exit: expired, wrong-audience, revoked, wrong-repository, and wrong-role credentials fail; revocation takes effect within the declared bound without restart; audit records identify the key and authorization decision.

S6 · Establish a continuous supply-chain gate 1–2 days

  • CI runs npm ci, frontend build/unit tests, and a production audit that fails on high/critical. Retain a separate full-tree audit so dev-only findings remain visible.
  • CI runs NuGet vulnerable-package checks for the solution and out-of-solution spike, generates an SBOM, and records advisory-query timestamps.
  • Pin GitHub Actions to immutable commit SHAs and enable scheduled dependency updates with a test-backed patch lane.
Exit: a deliberately vulnerable fixture fails the appropriate gate; a clean locked graph produces retained npm, NuGet, SBOM, frontend test, and history-secret-scan evidence.
