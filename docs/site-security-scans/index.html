Concept Dossier · Quality Studio

Security scans of public sites

Once a project is hosted publicly, Quality Studio should check its site from the outside as well as reviewing its code. This Dossier defines a site scan in three layers, the tools packaged for it, a versioned prompt library for the agent-driven part, the safety rules, where the sensitive results live, and how Agent Studio triggers scans and receives their results.

00 Decision summary

Each decision has a recommended working option. Implementation proceeds on it unless the operator records another choice.

  1. Layers. Three layers: outside view (on for every verified site), safe active checks (off by default; a switch per site with an expiry) and agent-driven review (off by default; a switch per site and environment, and staging unless production is named).
  2. Tools. A lean set, added in stages. Native checks in the worker, plus testssl.sh and Gitleaks for the outside view. Nuclei with pinned templates for known vulnerabilities. ZAP baseline later, in a separate optional image, for crawling and authenticated crawling. Skip Nmap, sslyze, Nikto, Wapiti, sqlmap and hosted scanners. Defer Trivy and Grype to artefact scanning.
  3. Scanner placement. One pinned scanner-worker image that pulls jobs from Quality Studio. It runs as a separate container on the Quality Studio host first, and on a host outside the targets' network for production scans.
  4. Ownership. A site may be scanned only after a token proof, either a DNS TXT record or a file under /.well-known/. The proof is re-checked if it is more than 24 hours old. For sites it hosts, Agent Studio places the token automatically.
  5. Evidence home. A restricted sites/ area in the Quality Studio data root. It is never in a checkout, never in an export, and never in logs. Only a redacted summary leaves Quality Studio.
  6. Consequences. Advisory first. After a measured trial, block promotion to production on conclusive critical outside-view findings on staging, then on judged critical findings. A production scan after a deploy creates a card and never rolls back automatically.

02 Scan layers

A site scan has three layers, ordered from harmless to active. A lower layer never depends on a higher one. Each layer has its own switch, request budget and schedule.

Outside view (L0)

L0 sends only requests that an ordinary visitor's browser, a DNS resolver or a port check would send. Every check is deterministic, and each has its own rule id so that its severity can be configured in a site-baseline rule pack:

L0 does not crawl. It requests the start page, the redirect chain, the assets that page references on the same host, the health URL and the fixed path list. A check whose tool fails is reported as unavailable, never as clean. A scan that hits its budget sets complete: false and lists what it omitted, in the same way the boundary inventory does.

Safe active checks (L1)

L1 sends requests that a visitor would not send, but that are designed not to change state. Nuclei runs with a pinned template set restricted to HTTP, SSL and DNS templates. It excludes the intrusive, dos, fuzz and default-login tags, code and headless templates, and DAST fuzzing mode. ZAP baseline crawls for a bounded time and applies only passive rules. Its authenticated variant logs in with a test account. L1 hits are raw: a template match is an observation until it is either conclusive by construction or judged (see From tool hit to judged finding).

Agent-driven review (L2)

L2 covers what tools cannot judge: whether role B can reach role A's objects, whether a business flow can be skipped or repeated, and whether an API exposes more than its client uses. The agent's only tool is a scoped HTTP client in the worker. That client enforces the verified hostnames, the method policy, the budget and the rate limit. It logs in on the agent's behalf and refers to accounts by role name, so the agent never sees a credential. Every exchange is recorded as evidence.

03 Alternatives

Two choices drive everything else: which tools to package, and where the scanner runs. A third, where evidence lives, follows from the sensitivity rule and is listed for completeness.

Tool sets

T1 · Lean, in stages

Native checks in the worker (HTTP, cookies, redirects, DNS, TCP connect, exposed files), testssl.sh for TLS and the already pinned Gitleaks for L0. Nuclei with pinned templates for L1. ZAP baseline is added later in a separate optional image for crawling and authenticated crawling.

For: a small first image, permissive licences apart from testssl.sh, and no runtime downloads. Each tool adds a distinct capability.

Against: crawl coverage arrives only with the ZAP slice. Some checks have to be written natively and maintained.

T2 · ZAP-centred

ZAP does almost everything, with baseline, API and authenticated scans driven by its automation framework, plus testssl.sh for TLS depth.

For: one mature engine with passive rules, crawling, an AJAX spider and authentication support. Its report format is well known.

Against: it needs a Java runtime and a browser, and the official image is well above 1 GB. That weight is carried even for a daily header check. It is slow to start, there are no template-style known-vulnerability checks, and passive alerts are noisy without triage.

T3 · Broad toolbox

ZAP, Nuclei, testssl.sh, Nmap, Trivy or Grype, Gitleaks and Nikto in one image.

For: the widest coverage on paper.

Against: overlapping and noisy results. Nmap's NPSL restricts redistribution. Trivy and Grype download a vulnerability database at run time, which breaks the no-download rule, and they scan artefacts rather than sites. Nikto is intrusive. The image is the largest of the three and has the most pins to maintain.

Where the scanner runs

P1 · Inside the Quality Studio container

The tools run as child processes of the API, in the same way as Gitleaks today.

For: nothing new to deploy.

Against: it sees the site from wherever Quality Studio runs, which may be the target's own network. A scanner defect or a hostile response handler runs next to the repositories, the data root and the API tokens. The Quality Studio image would grow by every scanner. The existing Gitleaks documentation already notes that its process limits "do not isolate the scanner … from the host".

P2 · Separate worker container on the Quality Studio host

A quality-site-scanner image claims jobs from Quality Studio over HTTPS and posts results back. It runs non-root with a read-only root filesystem, all capabilities dropped, memory and process limits, and no repository, data-root or Docker-socket mounts.

For: it isolates the host and is cheap. It is the same image as P3.

Against: it has the same network vantage as Quality Studio, so it is wrong when Quality Studio and the target share a host or network.

P3 · The same worker on an external vantage host

The worker runs on a small host with a different provider and network from every target. It only connects outwards: to Quality Studio for jobs, and to the targets.

For: it sees exactly what an outsider sees, it cannot reach the operator's internal networks, and its egress address is stable, so site owners can recognise it.

Against: one more host to run and patch, at a small monthly cost.

P4 · Third-party scanning service

A hosted DAST or monitoring service scans the site and Quality Studio imports the report.

For: no infrastructure.

Against: unfixed findings sit with a third party, which breaks the sensitivity rule. Provenance and pinning are outside our control, and credentials for authenticated scans would leave the secret provider.

Where scan evidence lives

E1 · In the repository (.quality/ or results/)

Rejected. The repositories are public, and committed history cannot be recalled.

E2 · Restricted area in the Quality Studio data root

<base>/sites/<site-key>/, outside every checkout, readable only by clients with a site-security grant. This option is the recommendation.

E3 · In Agent Studio

Rejected as the primary store. Agent Studio cards are copied into agent prompts and card results, and those can end up in commits. Agent Studio receives a redacted summary only.

04 Recommendation

Recommended default

Use tool set T1, run in one pull-based scanner-worker image that starts as P2 and moves to P3 for production scans. Keep evidence in the restricted data-root area (E2). The outside view is enabled for every site with a token proof. Safe active checks and agent review are switched on explicitly and expire. Results reach Agent Studio as a redacted summary, as cards and, after a measured advisory period, as a gate on promotion to production.

The main reason is that this delivers a useful scan of a real site in the first slice with a small image and no runtime downloads, and it keeps unfixed findings away from anything public.

Tools as sensors

Each tool becomes a Quality Studio sensor with the existing contract. The sensor ids are site-outside-view (native checks plus testssl.sh), site-served-secrets (Gitleaks), site-templates (Nuclei) and site-crawl (ZAP). Each normalises its output into ReviewFinding:

  • Locations[0].Path is site://www.product.example:443/path, with no range.
  • Source is FindingSource(Deterministic, sensorId, producer, producerVersion), for example producer testssl.sh with its pinned version.
  • Fingerprint is a hash of the site key, the rule id, the origin and the normalised path, port or parameter, so the same weakness keeps its lifecycle identity across scans.
  • Evidence holds a redacted excerpt: response status, the relevant headers, and at most 2 KiB of body after Gitleaks redaction.

The scan provenance records the following:

  • the worker id and vantage label, its egress address and the image digest;
  • every tool version and the template commit;
  • the hostnames and resolved addresses, and the proof id with its verification time;
  • the layer and the switches in force;
  • the request count, the duration, and complete with its omissions.

The images pin every tool as the Dockerfile pins Gitleaks today. The pinned version and SHA-256 are build arguments, the download is verified during the build stage, and the version is checked at worker start. Nothing is downloaded when a scan runs. The Nuclei template update check is disabled, and templates move only when the image is rebuilt.

Ownership and safety

  • Proof. When a site is registered, Quality Studio issues a random token. The operator, or Agent Studio for a site it hosts, publishes the token as a DNS TXT record at _qs-site-verification.www.product.example or as a file at https://www.product.example/.well-known/qs-site-verification/<token-id>. The worker checks the proof before a scan if the last check is more than 24 hours old. A failed check stops the scan with status unverified, which never counts as clean. A run-target hosting declaration does not count as proof, because Agent Studio's domain suffixes are an allow-list.
  • Scope. Only the exact verified hostnames are in scope, with no wildcards. Redirects are followed only to other verified hostnames. Third-party resources are listed in the inventory but not requested. A resolved address that is loopback, link-local, private or a cloud metadata address is refused, using the same rule as Agent Studio's HealthCheckAddressPolicy. Tests use an injected seam that production configuration cannot set.
  • Port probes. Ports are probed only on addresses that belong to the operator: the Agent Studio host address, or addresses declared on the site record. A site behind a CDN edge (Edge: cloudflare) records omitted: third-party-edge instead, because probing the CDN's address would scan a third party.
  • Rate and distress. Each layer has a budget (Scan layers). The worker backs off on 429 and 503 responses. It aborts with aborted: target-distress when more than 5% of responses in a minute are server errors, or when median latency triples against the first ten requests.
  • Non-destructive defaults. L0 and L1 send only GET, HEAD and OPTIONS requests, TLS handshakes and DNS queries. L2 follows a method policy for each site. State-changing methods are allowed only in a test tenant, and never against production unless production is switched on by name.
  • Switches. L1 and L2 have switches per site (L2 also per environment). Each switch records who set it, the reason and an expiry, which defaults to 90 days, and each change is written to the audit log. A global kill switch and a kill switch per site stop running jobs within 10 seconds.
  • Identification. The user agent is QualityStudio-SiteScan/<version> (scan <scan-id>), and the egress address is documented, so the site's own logs can attribute every request.
  • Credentials. Quality Studio stores only references such as secret://shop/staging/scan-user-admin. The worker resolves them at job start through an Agent Studio workload grant scoped to <project>/<environment>. ISecretProvider.GetForWorkloadAsync exists today, and exposing it remotely to the worker is part of the Agent Studio credentials slice. Values never reach evidence, logs or prompts.
  • Worker containment. The worker runs non-root with a read-only root filesystem, all capabilities dropped, memory, process and CPU limits, and a temporary filesystem for tool output. It has no repository, data-root or Docker-socket mounts. Its worker token can only claim jobs and post results.

Sensitive results

  • Where evidence lives. Site data lives in <base>/sites/<site-key>/: site.json (registration, proofs, switches), scans/<scan-id>/ (provenance, normalised findings, raw tool output), inventory.json, findings/state.json and attacks/coverage-ledger.jsonl. Directories are created with mode 0700. The site area is not part of any project directory, so quality migrate-data, project exports and run reports never pick it up.
  • Who can read it. In Hosted mode a client needs repository access to the site's owning registration and a new CanReadSiteSecurity flag next to CanRegisterRepositories. Without both, site routes answer 404. Local mode keeps its rule that every loopback request is the operator.
  • What leaves. Agent Studio and logs receive the scan id, site key, layer, status, completeness, counts by severity and gate verdict. Finding titles, paths, payloads and excerpts never leave Quality Studio. Agent Studio cards carry a redacted title ("Site security finding, high, staging of shop") and a Quality Studio link. A fix run reads the details through a read grant scoped to that card. Delivery rules forbid copying the details into repository files or card results.
  • Exports. quality report and the JSON exports leave site findings out. An explicit --include-site-findings flag writes them only to a path outside every registered checkout.
  • Retention. Raw tool output is deleted after 90 days. Normalised findings and their lifecycle are kept. Host-specific details are never published, even after a fix. Public documents may cite counts or classes only.

Coverage matrix

A live site becomes a second source of boundaries. The worker writes sites/<site-key>/inventory.json (schema site-inventory.v1) with entries of six kinds:

  • site-origin: scheme, host and port;
  • site-route: a crawled route template;
  • site-api-operation;
  • site-auth-flow;
  • site-dns;
  • site-port.

The catalogue changes in two ways:

  • New narrow entries. QS-SITE-TLS, QS-SITE-HEADERS, QS-SITE-COOKIES, QS-SITE-EXPOSED-FILES, QS-SITE-DNS and QS-SITE-PORTS carry deterministicRuleIds for the site/* rules and are conclusive in both directions, like QS-CONTROL-*. A clean L0 scan is therefore a real pass for those cells.
  • Wider existing entries. OWASP-API8-MISCONFIGURATION also applies to site-origin and site-port. OWASP-API9-INVENTORY applies to site-route and site-api-operation, so a route that is live but absent from the code inventory becomes visible. OWASP-API1-BOLA, OWASP-API5-FUNCTION-AUTH and OWASP-A01-ACCESS-CONTROL apply to live routes and operations. OWASP-API2-BROKEN-AUTH, SESSION-CSRF and AUTH-BRUTE-FORCE apply to site-auth-flow. These broad cells stay notYetChecked until L2 judges them, so an L0-only site cannot look covered.

Site judgements go to the site's own ledger, which has the same append-only contract and provenance. Staleness gains deploymentChanged (a new Release.CommitSha is live) and siteInventoryChanged. When the site's repository is registered, a live route is linked to the code boundary with the matching template. The matrix then shows the live behaviour (for example "401 without credentials") next to the code fact "authentication unknown", and that corroborates or contradicts it. The matrix view gains a source filter: code, site, or both.

From tool hit to judged finding

A false-positive verdict is recorded against the fingerprint with the judging model and prompt hash, so the same hit is not triaged again until the template or the deployed commit changes. Contradicting judgements keep the conservative result and raise needsHumanAttention, as the matrix does today.

Triggers and consequences

  • From Agent Studio to Quality Studio. DeployService.SyncLocked already reconciles deployments and creates production-failure cards. After it, a new step finds succeeded deployments of stage or production environments with Hosting.Domains. For each one, it registers or updates the site with PUT /api/sites/{siteKey} (on the first public deployment it also places the proof file on the edge). It then requests the scan with POST /api/sites/{siteKey}/scans, sending layer, reason, deploymentId, releaseId, commitSha and environmentId. The deployment id and layer serve as the idempotency key. Quality Studio owns the schedule, because it knows the layers and switches.
  • From Quality Studio to Agent Studio. GET /api/sites/{siteKey}/scans/{scanId}/summary returns the redacted summary. A new critical or high finding becomes a redacted Agent Studio card through AgentStudioTaskClient, idempotent per fingerprint. For the gate, Quality Studio publishes a site-security verdict keyed by project, environment and commit, in the same way the release-suite verdict is published today.
  • Gate stages.
    • Stage 0, advisory, from slice 3: the status is shown and nothing blocks.
    • Stage 1, after at least 4 weeks and 20 scans of production environments with no more than one conclusive finding later judged false: promotion to production is blocked when the staging scan of the same commit has a conclusive critical L0 finding (exposed credentials or VCS metadata, invalid certificate, data-store port open).
    • Stage 2: judged critical findings from L1 or L2 also block.
    Every block can be overridden with a recorded reason and an expiry. A scan of production after a deploy cannot block a deploy that has already happened. It creates a card and never rolls back automatically.
  • Overlap with health checks. Agent Studio's health checks keep their certificate-expiry warning as an operational signal. Quality Studio does not create a card for site/tls-certificate-expiring while that warning is active for the same environment.

Surfaces
